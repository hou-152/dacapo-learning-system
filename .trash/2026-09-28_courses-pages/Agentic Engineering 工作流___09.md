# 09｜总图：把 Agentic Engineering 迁移到自己的工作流

## 本篇基于的反馈

- 第 8 篇没有新增长笔记，划线集中在 Agent 太快导致人不能逐行审、验证问题清单、原始意图检查、合并冲突例子和端到端行为证据。
- 你已经能把 No Mistakes 拆成“底层风险 → 对应动作”，说明验证流水线已经从工具名变成风险闸门。
- 你前面多次把课程迁移到自己的语境：工业机器人状态、错题本、元 skill、工作树文件夹、谁检查、谁变成大脑。
- 现在适合收束总图：减少新工具，把船长、船、memory / skill、worktree、First Mate 和验证流水线串成一套可执行工作流。
- 本篇保持小步收束，最后留一个口头费曼入口，用来决定后面是否补“元 skill 实战”。

## 这一篇要解决的问题

这一篇解决一个问题：学完这套 Agentic Engineering 工作流以后，你怎么把它迁移成自己的 Codex / Reader / 本地项目工作方式？

## 正文

这门课从第 1 篇走到第 8 篇，其实一直在回答一个问题：

人怎样从“亲自做事的人”，变成“能带一组 Agent 工作的船长”？

这套系统既不把事情全丢给 AI，也不把 Agent 管成没有判断空间的脚本。

更准确的说法是：人设计方向、边界、状态和验收；Agent 在这个系统里执行、探索、验证和回报。

现在把整套系统收成一张图。

```text
船长
  ↓ 给方向、定边界、做取舍
船
  ↓ 终端 / 项目目录 / Reader / 本地文件 / 工具环境
船员
  ↓ 单 Agent 执行具体任务
memory / skill
  ↓ 统一规则、沉淀错题、按需加载流程
worktree
  ↓ 隔离文件、状态和实验空间
First Mate
  ↓ 拆任务、派 Agent、追状态、升级判断
验证流水线
  ↓ 关风险闸、收证据、准备 PR
人类判断
  ↓ 看 what / why / 风险 / 证据 / 是否合并
```

这张图就是你自己的迁移框架。

### 1. 第一层：船长负责方向

船长要避开两个极端：什么都亲自做，或者什么都不看。

船长负责 5 件事：

1. 什么值得做；
2. 为什么现在做；
3. 不能牺牲什么；
4. 完成后看什么证据；
5. 哪些取舍必须回到人这里。

这对应你说的 what 和 why。

Agent 可以帮你找路径，但它不应该替你决定什么重要。

所以每个任务开始前，先写一张最小目标卡：

```text
目标：
当前状态：
期望状态：
边界：
输出：
验证：
需要人判断的点：
```

如果这张卡写不出来，先不要开一堆 Agent。

先让一个 Agent 帮你把目标问清楚。

### 2. 第二层：船是稳定工作面

它是一整套稳定工作面：

- 终端；
- 项目目录；
- Reader 反馈；
- 本地课程文件；
- AGENTS.md / memory；
- skill；
- 测试命令；
- 截图、日志、PR、证据文件。

稳定工作面的意义是：你每次启动任务，都知道材料在哪里、规则在哪里、输出放哪里、反馈从哪里回来。

这门课本身就是一个例子：

```text
Reader 里划线和评论；
本地 00-学习计划.md 记录状态；
01.md 到 09.md 存连续课程；
INDEX.md 记录全局进度；
每篇同步回 Reader；
下一篇读取 Reader 反馈再调整。
```

这就是一个学习版的船。

### 3. 第三层：memory / skill 是船员入职材料

Agent 每次进来都是新船员。

它不知道你的偏好、项目结构、常见错误、测试方式、输出格式和禁区。

memory / skill 的作用是 onboarding。

可以这样分：

| 类型 | 放什么 | 使用场景 |
|---|---|---|
| global memory | 所有项目都适用的短偏好 | 每次 Agent 启动都要知道 |
| project memory | 项目结构、术语、测试方式、常见坑 | 进入某个项目时要知道 |
| skill | 条件触发的长流程 | 只有特定任务需要时再加载 |
| 课程 / 笔记 | 人自己的理解系统 | 帮人和 Agent 对齐概念 |

你的“错题本”理解很关键。

Agent 犯错以后，不只是修一次。

要问：

```text
这个错误以后还会出现吗？
如果会，它应该进 memory 还是 skill？
它是全局偏好、项目规则，还是特定流程？
```

这就是让船员越来越熟练的方法。

### 4. 第四层：单 Agent 先跑通

多 Agent 前，先跑通单 Agent。

单 Agent 要跑通 4 个动作：

1. 读懂目标；
2. 找到相关上下文；
3. 做出可检查输出；
4. 根据反馈修正。

如果单 Agent 都跑不顺，多 Agent 会放大问题。

所以早期练习可以很小：

```text
让 Agent 只做一件事；
输出必须带证据；
完成后你做一次低成本验收；
发现错误后沉淀到 memory 或 skill。
```

单 Agent 是基本功。

多 Agent 是放大器。

基本功不稳，放大器会放大混乱。

### 5. 第五层：多 Agent 先分流

第 5 篇讲过多 Agent 分流。

现在把它放进总图：

| 任务状态 | 推荐模式 |
|---|---|
| 目标还模糊 | 单 Agent 澄清 |
| 有先后依赖 | 线性接力 |
| 子任务独立 | 并行分工 |
| 状态多、任务多、切换成本高 | First Mate 调度 |

这里最重要的是不要被“多开”吸引。

多 Agent 的核心是任务结构。

一个任务适不适合并行，要看：

```text
目标是否清楚；
子任务是否独立；
文件是否重叠；
状态是否共享；
输出是否能合并；
失败是否能回滚。
```

这张分流卡可以做成你的元 skill。

### 6. 第六层：worktree 给每个 Agent 独立空间

worktree 的迁移理解可以很简单：

一个 worktree 就是一张独立工作桌。

也可以按你自己的说法：它像一个文件夹，里面放这个任务需要的上下文、记忆和 skill。

但要记住边界：

worktree 主要隔离文件和工作目录。

它不自动隔离：

- 外部服务；
- API 配额；
- 数据库；
- 测试账号；
- 端口；
- 人脑里的状态；
- 任务之间的产品取舍。

所以 worktree 要配合：

```text
任务范围；
禁区；
共享资源说明；
输出格式；
合并规则；
回滚方式。
```

这就是第 6 篇的隔离检查卡。

### 7. 第七层：First Mate 管状态

First Mate 进入的时机，是人开始被状态切换拖住。

你不想一直问：

```text
谁在做？
做到哪了？
卡在哪里？
证据有没有？
能不能合并？
哪个需要我判断？
```

First Mate 要维护状态表：

| 任务 | Agent | worktree | 状态 | 证据 | 是否需要人判断 |
|---|---|---|---|---|---|
| A | Agent A | wt-a | 实现中 | 暂无 | 否 |
| B | Agent B | wt-b | 验证中 | 日志 | 否 |
| C | Agent C | wt-c | 阻塞 | 冲突说明 | 是 |

它的价值是把状态从人脑里拿出来。

你只处理升级上来的判断。

### 8. 第八层：验证流水线关风险闸

第 8 篇已经把 No Mistakes 拆成风险闸门。

现在放进总图里：

```text
原始意图
  ↓
rebase 到最新主分支
  ↓
合并冲突处理
  ↓
对抗式 review
  ↓
端到端测试
  ↓
证据记录
  ↓
文档更新
  ↓
lint / 静态检查
  ↓
PR 准备
  ↓
人类判断
```

这条链的目标是把“Agent 做完了”变成“人可以判断了”。

人最后看：

```text
意图是否对；
证据是否够；
风险是否可接受；
产品取舍是否正确；
是否值得合并。
```

这就把人从逐行审查拉回判断位。

### 9. 迁移到你的 Codex 工作流

你可以从一个很小的版本开始，不要一上来做完整 First Mate。

最小迁移版：

```text
1. 先写目标卡。
2. 单 Agent 做任务。
3. 输出必须包含证据。
4. 你做最终判断。
5. 错误沉淀到 memory / skill。
```

进阶迁移版：

```text
1. 用元 skill 问清目标、范围、禁区、输出、验证、回滚。
2. 判断任务适合单 Agent、线性接力、并行分工还是调度。
3. 并行任务放进独立 worktree。
4. 每个 Agent 输出统一格式。
5. 主线程合并，冲突升级给你。
```

成熟迁移版：

```text
1. First Mate 接目标卡。
2. First Mate 拆任务、派 Agent、追状态。
3. Agent 在 worktree 里执行。
4. 验证流水线跑证据。
5. 人看 PR、证据和风险。
6. 通过后合并，错误沉淀回 memory / skill。
```

你现在可以先从最小版开始。

最好的下一步，是把“目标卡 + 隔离检查卡 + 验证证据”先用在一个真实小任务上。

### 10. 一张总提示词

你可以把这张提示词当成总入口：

```text
我要用 Agentic Engineering 工作流处理这个任务。

目标卡：
- 当前状态：
- 期望状态：
- 边界：
- 输出：
- 验证：
- 需要我判断的点：

请先判断任务模式：
- 单 Agent 澄清
- 线性接力
- 并行分工
- First Mate 调度

如果适合执行，请给出：
- 子任务拆分
- 每个 Agent 的范围和禁区
- 是否需要 worktree
- 共享资源风险
- 输出格式
- 验证证据
- 合并规则
- 需要人判断的升级点
```

它先让 AI 帮你把任务变成可调度对象。

这就是你前面说的元 skill 方向。

### 11. 这门课暂时收在哪里

这门课到这里，主链条已经完整：

```text
船长
船
船员
memory / skill
单 Agent
多 Agent 分流
worktree 隔离
First Mate 调度
验证流水线
人类判断
```

继续往后，不应该再机械加章节。

更好的做法是进入反馈驱动：

- 你做一段 2-6 分钟口头费曼；
- 或者你拿一个真实任务试用目标卡；
- 或者你挑一个方向做实战篇，比如“目标元 skill”“隔离检查 skill”“验证证据模板”。

下一步由你的反馈决定。

这才符合交互式学习。

## 小结

- 整套 Agentic Engineering 工作流的主线是：人定方向，Agent 执行，First Mate 调度，验证流水线收证据，人做最终判断。
- memory / skill 负责让船员越来越熟，worktree 负责隔离并行空间。
- 多 Agent 的关键是任务结构，Agent 数量只是执行形式。
- 验证流水线把“完成”变成“有证据、可判断、可合并”。
- 迁移时先从最小版开始：目标卡、单 Agent、证据、判断、沉淀。
- 课程主链条到这里可以先收束，后续根据你的口头费曼或真实任务反馈补漏洞。
