# 02｜组装船：先搭一个稳定的指挥中心

## 本篇基于的反馈

- 你在 Reader 里标出了“船长负责方向、边界和质量门槛”，并补充：船长很不容易，因为模糊目标要被翻译成 Agent 能执行的清晰指令。
- 你关注 onboarding 的边界和 loop 的关系：项目偏好、项目结构、核心约定能不能变成一种元技能。
- 你认同一个约束：单 Agent 循环没有跑通前，不应该直接启动多 Agent 并行。
- 你把可视化方案讨论联想到 chatroom，说明你关心“先开小会、再执行”的协作形态。
- 你把验证流水线理解成目标审计、逻辑编排和工程治理，本篇会沿这个方向继续推进。

## 这一篇要解决的问题

这一篇解决一个问题：为什么 Agentic Engineering 的第一层叫 Ship？这里的 Ship 可以先理解成一个稳定的指挥中心，它让人能持续发出清晰指令、观察执行状态、沉淀反馈，并决定任务能不能升级到多 Agent。

## 正文

上一讲里，我们把整套工作流压成一个比喻：人是船长，Agent 是船员，工具和环境是船。

这一讲先讲船。

视频里一上来讲 terminal、WezTerm、tmux、Neovim、语音输入，表面看是工具清单。放进 Agentic Engineering 里看，这些工具共同解决一个更基础的问题：

船长需要一个稳定的指挥中心。

这个指挥中心要承接 4 件事：

1. 发出指令。
2. 观察执行。
3. 保留上下文。
4. 形成下一轮反馈。

如果这 4 件事分散在很多地方，船长会被界面、文件、聊天窗口、测试日志和任务状态撕开。Agent 越多，撕裂感越明显。Ship 的价值就在这里：它把工作流压到一个可以持续操作的平面上。

### 1. 船长的难点：把模糊目标翻译成可执行指令

你在 Reader 里的反馈很关键：人脑可以接受模糊，Agent 对模糊的承受力低很多。

人类团队里，一个很强的成员拿到“把这个体验做得更顺一点”，可能会自己猜用户场景、自己补边界、自己找优先级。Agent 也能补，但它补出来的东西容易偏。它可能理解错产品意图，也可能把局部代码改对了，却没有解决真实问题。

所以船长的第一项能力是翻译。

模糊目标：

> 这个功能体验有点乱，帮我优化一下。

更适合给 Agent 的指令：

> 先阅读当前功能入口、用户操作路径和相关测试，整理 2-3 个体验问题。每个问题给出：用户看到什么、为什么会卡住、最小修复方案、需要验证的行为。先不要改代码，等我确认方向。

这段指令做了 4 个动作：

1. 限定探索范围。
2. 要求先整理问题。
3. 规定输出格式。
4. 明确暂时不能改代码。

船长给出的指令越清楚，Agent 的自由度越可控。这里的清楚并不等于把每一步都写死。好的指令会留下执行空间，同时锁住方向、边界和验收方式。

### 2. Ship 先解决“连续指挥”的问题

视频作者偏爱 terminal，不只是因为它快。

他的组合大概是这样：

- terminal emulator：提供一个稳定入口。
- tmux：把多个窗格、多个会话和持久状态留在同一个地方。
- editor：快速读写代码和文本。
- voice input：把长指令快速说出来。
- agent harness：让 Agent 接收任务、读上下文、执行命令。

这些东西连起来以后，船长可以在同一个工作面里完成一轮循环：

1. 说出任务。
2. 看 Agent 探索。
3. 打开文件检查。
4. 运行命令验证。
5. 记录修正。
6. 开下一轮任务。

这就是稳定工作面的含义。

它追求的是：指挥动作不要断。你发出一个任务后，还能看见上下文、日志、文件和结果；你切到另一个任务后，回来还能接上。

tmux 的持久会话就是这个原则的具体体现。Agent 执行到一半，你可以离开；回来以后状态还在。你可以在一个窗格里让 Agent 跑，在另一个窗格里看文件，在第三个窗格里自己跑命令。这个工作面像驾驶舱，所有关键仪表都在眼前。

### 3. 语音输入解决“高质量长指令”的成本

你说“能把一个东西描述清楚，至少考验了 99% 的人”。这句话抓到了 Agentic Engineering 的入口门槛。

很多人给 Agent 的指令短，是因为懒得打。短指令容易省掉背景、约束、验收和风险。语音输入的意义在这里：它降低长指令的成本。

比如你要让 Agent 改一个页面按钮。打字时你可能写：

> 优化一下这个按钮。

用语音时，你更容易说：

> 这个按钮现在的问题是用户不知道点它之后会发生什么。你先看一下这个页面的交互路径，确认这个按钮对应哪个状态变化。不要先改样式，先告诉我现在文案、位置和点击反馈各有什么问题。然后给两个方案，一个最小改动，一个稍微完整一点的体验改动。

这段话更长，但信息密度更高。Agent 收到的是一个小任务定义，里面有目标、范围、顺序和输出要求。

当语音输入质量足够好，船长可以把脑子里的判断快速倒出来。Agent 处理自然语言很强，关键是你要给它足够多的有效上下文。

### 4. Single crewmate 是进入并行前的门槛

你在 Reader 里提到：如果单 Agent 循环没过，就不让启动多 Agent。这可以变成一个硬规则。

一个任务想进入多 Agent 并行，先要通过 Single crewmate 门槛。

门槛可以这样定义：

1. 同类任务已经用单 Agent 跑过至少 2 次。
2. 每次都有明确输入、输出和验收标准。
3. 常见错误已经写入 memory 或 skill。
4. 验证方式已经稳定，比如测试、截图、日志、人工验收清单。
5. 任务之间能隔离，文件和状态不会互相踩。

如果这 5 条还没满足，多 Agent 会放大问题。

举个例子：你想让 3 个 Agent 同时优化一个学习系统。

还没过门槛时，3 个 Agent 可能分别改目录结构、改课程风格、改验收问题。最后你得到 3 份方向不同的输出，还要自己合并。

过了门槛以后，你可以把任务拆成：

1. Agent A 只读反馈，提取学习状态。
2. Agent B 只改下一篇文章。
3. Agent C 只做验收检查和索引更新。

这里能并行，是因为每个 Agent 的边界清楚，输出能检查，文件冲突少。

### 5. Onboarding 和 loop 的关系

你问到 onboarding 的边界和 loop 的关系，这个问题很值得往下讲。

可以先用一句话记住：

onboarding 是把过去几轮 loop 的经验，写成下一轮 Agent 上船前就知道的规则。

loop 是过程：

1. 给 Agent 任务。
2. Agent 执行。
3. 你检查结果。
4. 发现问题。
5. 修正提示、流程或工具。

onboarding 是沉淀：

1. 这个项目的偏好是什么？
2. 这个项目的结构是什么？
3. 这个项目的核心约定是什么？
4. 上次 Agent 犯过什么错？
5. 下次怎样避免？

memory 和 skills 都属于 onboarding 的材料。

memory 更适合放常驻、短小、高频的信息，比如：

- 这个项目的主要目录是什么。
- 用户偏好什么输出风格。
- 哪些命令是常用验证命令。

skill 更适合放按需触发的流程，比如：

- 写学习文章时怎么提取反馈。
- 做前端改动时怎么截图验收。
- 修 bug 时怎么先复现再改。

你提到的“项目偏好、项目结构、核心约定”很适合先做成一个项目元提示词。等它变长、变稳定、触发条件更清楚，再拆成项目级 skill。

### 6. 验证流水线让船长能少看细节

你在 Reader 里写到一个很现实的点：很多时候代码细节看不懂，只能看前端 UI 互动。

这不是失败。Agentic Engineering 本来就要让人把注意力转到证据上。

验证流水线要回答 3 个问题：

1. 原始目标是什么？
2. Agent 做的改动是否覆盖这个目标？
3. 有什么证据能说明它真的生效？

证据可以是：

- 测试通过记录。
- 端到端操作日志。
- 前后截图。
- 短视频。
- 性能数据。
- PR 风险说明。

如果是 UI 改动，截图和交互路径比 diff 更接近用户体验。如果是后端逻辑，测试和日志更有说服力。如果是数据处理，输入输出样例更关键。

船长可以减少钻进细节的次数，把主要精力放在证据系统上。证据系统帮助船长判断：这个结果能不能交付，哪里还需要人工看。

### 7. 本篇形成一个操作卡

你可以把第 2 篇收束成一张卡：

**Ship = 稳定指挥中心**

- 它让指令、执行、观察、反馈留在一个连续工作面里。
- terminal、tmux、editor、voice input、agent harness 都是这个目标的部件。
- 长指令的关键是锁住方向、边界、输出和验收。
- Single crewmate 门槛决定任务能不能进入多 Agent 并行。
- onboarding 是把 loop 里学到的经验写进 memory 或 skill。
- 验证流水线让船长根据证据做判断，减少被 diff 拖住的时间。

如果你只能做一个动作，就先做这个：

选一个你最近反复交给 Agent 的小任务，跑 2 次单 Agent loop。每次记录：

1. 你原始怎么说。
2. Agent 哪里理解偏了。
3. 你怎么改指令。
4. 下次应该写进 memory 还是 skill。

这就是从使用 Agent，走向训练自己的工程船员。

## 小结

- Ship 可以先理解成稳定指挥中心，核心作用是承接指令、观察、上下文和反馈。
- 船长的第一项能力是把模糊目标翻译成可执行指令，锁住方向、边界、输出和验收。
- 语音输入降低长指令成本，让船长更容易把背景和判断说完整。
- 单 Agent 跑通是多 Agent 并行前的门槛，同类任务至少要有稳定输入、输出、验收和隔离方式。
- onboarding 是把 loop 中暴露的问题沉淀成 memory、skill 或项目元提示词。
