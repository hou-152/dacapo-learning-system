# 03｜Skill 不该教模型“认真思考”，而该规定“何时介入”

## 要解决的真实问题

如果 RSS 与 AI 内参是来源池，证据包是当前工作台，那么 Skill 还剩下什么价值？

答案不是替模型重复通用思考方法，而是在特定状态下规定：该做什么、何时停止、怎样知道做对了。

## 最小知识地图

### 1. 强模型吃掉的是通用脚手架，不是你的局部判断

「请认真思考」「先分析再回答」「使用第一性原理」「从多个角度讨论」这类规则，过去能提升弱模型的稳定性。模型变强后，它们的边际价值下降：既占用上下文，也可能把本可自由调整的推理锁成机械步骤。

但模型并不会自动知道你这个系统的局部边界。例如：什么时候必须回到 RSS／AI 内参核实？什么时候只能使用你已形成的判断记录？什么时候一篇内容该停止打磨，交给人决定？这些不是通用智力，而是你的工作流政策。

### 2. 一个可调用 Skill 至少要有 4 个字段

把厚 Skill 压缩成可进入 Loop 的模块时，先写清：

- **触发条件**：什么状态出现时调用？
- **输入**：它解决问题所需的最小信息是什么？
- **动作**：它具体做什么，而不是要求“全面分析”？
- **验证**：怎样知道它有效，或何时应退出？

这四项不是格式洁癖。它把“文件里有一段好提示词”变成“系统在正确时机执行了一项可检查动作”。

### 3. 以你的内容工作流为例

一个坏的“选题 Skill”可能写成：

> 你是顶级内容策划，请深度洞察用户、使用第一性原理，给出爆款选题。

它没有说明何时需要它，也没有成功定义。

一个可调用的版本更像：

> 触发：已有一个个人判断，但尚未找到支持它的近期案例或反例。  
> 输入：当前判断、目标受众、来源池检索结果。  
> 动作：选出 1 个支持证据与 1 个反例，指出判断的适用边界。  
> 验证：如果两者都不能改变或限定判断，停止继续检索；转入表达阶段。

这里真正被复用的不是“顶级策划”的人设，而是「何时检索、检索什么、何时收敛」的决策规则。

### 4. Loop 是调度者，不是永动机

Loop 的职责是观察当前状态，并选择：继续、调用某个局部 Skill、回退修复、交给人，还是停止。

因此，Loop Engineering 不会消灭 Skill；它削弱的是用户手动记住 100 个文件、决定调用顺序的必要性。Skill 从用户界面的按钮，退到 Loop 在特定状态下调用的“策略模块”。

## 最小来源集

- RSS 的 Harness 实测：说明每增加常驻规则、工具或子 Agent 都有成本，因此局部模块不应默认全部加载。
- GitHub 的 code review 案例：说明同一工具在不同任务中需要不同的任务锚点、失败恢复和停止规则。
- 你的工作流观察：说明内容生产不是固定线性流水线，而会在材料、判断、表达与验证之间往返。

## 费曼到任务

从你现有的 DBS 或视频工作流里任选一个最常用的 Skill，把它改写成「触发条件、输入、动作、验证」四行。目标不是把它写得更长，而是让另一个 Loop 不靠猜就知道何时应调用它。

## 检查站

1. 你认为自己现有的一个 Skill，里面哪些内容是在重复模型的通用能力？
2. 选一个 Skill，按“触发条件、输入、动作、验证”重写成四行。
3. 在什么情况下，Loop 应该停止调用 Skill，直接把判断交回给你？
