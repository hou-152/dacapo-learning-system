### 2. 你的系统已经是 Harness——逐层拆开看

Harness 不是一个独立软件。它是**模型外面的所有规则、约束、工具、记忆、验证机制的总和**。你的系统里已经有这些东西了：

**第一层：规则文件（CLAUDE.md）**

你 CLAUDE.md 里的 Agent 路由表——

> 「龙虾日报：每日凌晨 cron / 手动指令」
> 「精选入库：日报『精选入库？』✅ → 文章入库 skill → 阅读提醒 skill」  

这个跟工作流的区别是什么？

就是这个系统文件，我记得我给它备注的，更多的是一些记忆或者文风之类类似提示词的东西。

这些不是 prompt。它们不是写给模型看的「请认真思考」。它们是**系统级规则**——告诉调度程序在什么条件下启动什么流程。这就是 Harness 的「调度」层。

**第二层：记忆系统（memory 文件）**

你 `/Users/housibo/.claude/projects/-Users-housibo-Documents/memory/` 下的 memory 文件，不是每次对话的上下文。它们是跨会话持久化的判断记录。Harness 的「上下文管理」层就是干这个的——什么东西应该跨轮记住，什么东西只在当前轮有效。

**第三层：工具边界（MCP、飞书桥、wx CLI）**

你的飞书桥、微信 CLI、内参 API——这些工具不归模型管。模型可以调用它们，但它们的权限、限流、错误处理，都是 Harness 层在控制。Harness 的「工具边界」层决定了模型能碰什么、不能碰什么、碰了之后怎么兜底。

**第四层：验证规则（你正在学的）**

你从 02 到 04 学到的检索规则——「检索前先写任务锚点、找到 1—3 篇证据后停止扩展」——是一条验证规则。它不是让模型「更懂搜索」，而是规定了什么情况下可以搜、什么情况下应该停。Harness 的「验证」层就是一系列这样的规则：做完之后怎么知道做对了？什么情况下应该停止而不是继续？

**第五层：公理和边界（AI不外包判断）**

你整个系统里最重要的一条 Harness 规则，是你自己写下的：**AI 可以提供知识，但不能替代人的判断责任。** 这条规则不活在任何一个 prompt 里。它活在 Harness 层——它约束所有 Agent 的行为边界，不管它们用的是哪个模型、执行的是哪个 Skill。

### 3. 所以「Harness 变厚」到底意味着什么

04 的 Harness 文章说：

> 「Harness 的对象不只是模型本身，而是围绕模型建立一套系统——基建、tooling、安全保障、sandbox 与 host service 的交互、启动时间、latency，以及系统如何持续 improve。」

你不理解这句话，可能是因为它读起来像一个技术清单。但换到你自己的系统里，它的意思很简单：

| Harness 文章说的 | 你的系统里的对应物 |
|-----------------|------------------|
| 基建 | 你的 Mac + VS Code + 终端环境 |
| Tooling | 微信 CLI、飞书桥、内参 API、MCP |
| 安全保障 | `~/.claude/projects/` 的权限控制、凭证管理（API Key 不写进 CLAUDE.md） |
| Sandbox 与 host service 的交互 | Claude Code 的 sandbox 模式、Bash 工具的执行边界 |
| 启动时间、latency | 每次会话启动时加载 CLAUDE.md + memory 的时间成本 |
| 系统如何持续 improve | 你正在做的这件事——学 dbs-learning、改规则、写新 Skill |

你不需要建一个 AWS 集群才叫 Harness Engineering。**你把 CLAUDE.md 里的一条模糊规则改成一个明确的触发条件+验证步骤——这就是 Harness Engineering。**

Harness 变厚，不是坏事。它意味着：
- 以前靠人临时判断的东西（「这个文章要不要入库？」），现在有了明确的决策规则
- 以前每次手动重复的操作（「每天早上搜一下内参有什么新东西」），现在有了自动触发条件
- 以前模型可以随便做的事（「随便搜、随便读」），现在有了边界（「先写任务锚点再搜」）

控制权从模型内部移到 Harness 层，不是模型被削弱了。是**你的判断被写成了系统规则，而不是每次都靠嘴说一遍。**

### 4. 「AI不外包判断」是 Harness 的第一条公理，不是 prompt 里的一句叮嘱

你 04 里写：

> 「当控制权从模型内部向模型外部移动时，我直觉上的第一判断是：模型变强了。我们可以把一些能够自动化的东西外包给它，但是核心的判断是绝对不能外包的。」

然后你加了一个限定：
> 「像那种简单的、工程化的判断，它是可以让 AI 去直接介入的……是或非，零或一。」

这两句话放在一起，就是一条完整的两层 Harness 规则：

```
第一层（硬边界）：任何涉及价值判断、领域判断、发布判断的决策，必须交给人。
第二层（软边界）：纯工程判断（yes/no、0/1、格式校验、存在性检查）可以由 AI 自动执行，
                 但执行结果必须有可追溯的验证记录。
```

这条规则如果只写在 prompt 里——「请注意，重要判断要交给人哦」——模型可能遵守，也可能在某次长会话里忘掉。但如果它被写进 Harness 层——成为每个 Agent 调用前必须检查的约束——那它就不依赖模型记性了。

这就是为什么 Harness 比 prompt 可靠：**prompt 是请求，Harness 是约束。请求可以被忽略，约束在执行前就被检查。**

### 5. 来感受一下你的 Harness 在什么时候起作用

你现在回想一下刚才发生的事——你说「等一下，我还没有呢，我还没学完你就推是什么鬼？」然后我撤回了 05。

这件事里，你的 Harness 已经在工作了：

- **规则层**：dbs-learning 的 Skill 规则说「必须读上一轮反馈再写下一篇」。我跳过了这一步。
- **验证层**：你发现 04 的反馈你没写、05 已经推过来了——系统状态和规则不匹配。
- **人的判断介入**：你叫停了我。

如果 Harness 不存在——如果一切都只是 prompt 里的「请注意教学节奏」——我不会自己发现自己跳步了。是你（人）在 Harness 层做了一个判断：「规则被违反了，暂停。」

这就是「Harness 变厚」的真正价值。不是系统能跑得更快，而是系统在跑偏时有人（或规则）能发现、能叫停、能修正。

## 小结

1. 你的系统已经有一层 Harness——CLAUDE.md 的路由表、memory 文件、工具权限边界、「AI不外包判断」公理。你不是从零开始建 Harness，你是让已有的 Harness 从「隐性的」变成「显性的」。
2. Harness 五个核心层：规则（调度触发）、记忆（跨轮持久化）、工具边界（权限和兜底）、验证（停止条件和成功标准）、公理（不可违反的硬边界）。
3. 「Harness 变厚」不是坏事——它是你的判断从「每次都靠嘴说」变成「写成系统自动执行的约束」。
4. Prompt 是请求，Harness 是约束。请求可以被模型忽略，约束在执行前就会被检查。
5. 你已经有一条两层 Harness 规则：硬边界（核心判断不外包）+ 软边界（工程判断可自动但需验证）。
