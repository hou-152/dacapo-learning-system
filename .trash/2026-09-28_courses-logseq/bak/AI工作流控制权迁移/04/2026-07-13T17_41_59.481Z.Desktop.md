# 04｜Prompt → Skill → Workflow → Loop：一条演化线，三种驱动力

## 要解决的真实问题

02 和 03 反复提到 Prompt → Skill → Workflow → Loop 这条演化线。你在 02 的费曼练习里说「我去找一些文章，准备推翻你」，然后真的选了 3 篇直接相关的证据。这一篇就用你自己的证据来回答：这条演化线到底是被什么力量推动的？是模型越变越强，自动吞噬了上层的工程结构？还是控制点本身在迁移——从模型内部移到了模型外部的调度系统？

你选的 3 篇文章恰好各指了一种驱动力。我们一个一个来。

## 最小知识地图

### 1. 演化线四阶段：每一步解决了什么，又制造了什么

先不要去想「驱动力」。先把这四个阶段本身讲清楚——每一步在解决前一步的什么问题。

**Prompt 时代（2023）**：
人写一段指令 → 模型生成结果。核心动作是「写好 prompt」。问题是：每次从头写，好的 prompt 经验无法复用，换了任务就得重新琢磨措辞。

我对提示词时代的理解，是觉得提示词其实是一个特定思维的包装。

比如说：
• 第一性原理
• 贝叶斯
• 剃刀原则
• 费曼

**Skill 时代**：
把高频 prompt 封装成可调用单元。核心动作从「写 prompt」变成「选 Skill」。解决了复用问题，但制造了新问题——Skill 多了之后，人记不住、管不过来、不知道什么时候该用哪个。你在 01 里说的「100 个 Skill 不等于每次都带上它们」，就是这个阶段的核心矛盾。

然后，在 Skill 的时代，我个人理解的核心其实是“默会”。我对 Skill 时代的理解是，它实际上是在包装知识，也就是把隐性知识给显性化。

因为有很多知识 AI 并不懂，这就需要一个垂直领域的人，去把一些可以显性化的隐性知识包装出来。但有些东西确实没有办法，这就是 Skill 时代的局限性。因为有些默会知识和暗知识是无法用言语表达出来的。

怎么说呢，它可能是一个经验导向的东西，或许跟个人的语言表达能力有关，也可能跟个人对工作流颗粒度的熟悉程度有关。

**Workflow 时代**：
把多个 Skill 串成线性步骤。A 做完自动触发 B，B 做完触发 C。解决了「人记调用顺序」的问题，但制造了新问题——线性流程处理不了中途出现的意外。如果第三步发现第一步的假设错了，Workflow 不会自己回头修正，它只会继续往下跑。

关于工作流时代，其实我确实不是很了解。但我能清楚地知道，工作流是由很多个 Skill 组成的。

但是，中间如果出错，具体错在哪了，它并不知道。

**Loop 时代**：
不在每一步之间加死链接，而是在每一步之后加一个判断——「当前结果是否符合预期？下一步应该继续、切换、回退、还是交给人？」。你 03 里写的「每个任务都有是/否的阶段，通过了才推进下一个」，就是 Loop 的核心动作。

关于 Loop 时代，我最近实践的经历是这样的：

Loop 的核心在于把一些判断丢给 AI，让 AI 实现自动化。

比如说我写了五个 Loop，每一个 Loop 阶段的产出都由 AI 来判断。只要 AI 判断“OK，你过”，你就可以直接进入下一个阶段，这样一直往后推进。

用一句话概括这四个阶段的关系：

> Prompt 回答了「做什么」。Skill 回答了「怎么做一次」。Workflow 回答了「做完了 A 之后做什么」。Loop 回答了「做完之后，怎么知道要不要继续做」。

### 2. 驱动力 A：模型能力内化——你选的《Skills》提供的证据

你选的《Skills 把 Agent 从聊天工具推向可复用工作流》里有一段关键判断：

> 「好的输入不再只是更漂亮的 prompt，而是可复用、可传递、可验收的任务上下文。」

这句话背后是一个更深的变化：模型在变强。当模型能从模糊指令中自动补全意图时，你就没必要在每个 Skill 里写「请认真思考」「请从多个角度分析」这类通用脚手架了。模型自己会做这件事。

对的，对的。因为在体感上面，我会越来越觉得，当智能越来越强的时候，有些东西它就不用提。

我感觉整个事情是这样的：我觉得当个人的 AI 智能上升之后，对工作态度还是有影响的。我不知道这个比喻是否合适，但确实，人聪明一点，工作态度就会好一点，这是我对人的联想。

但我现在可能还属于那种不够聪明的人，所以没法去证实它，也没法去证伪它。

这就是**驱动力 A：模型能力内化**。

- 2023 年的模型需要你在 prompt 里写清每一步思考过程。
- 2025 年的模型在 prompt 里写「先分析再回答」反而是干扰——它本来就会分析，你的指令只是在浪费上下文。
- 所以 Skill 在变薄。不是 Skill 不重要了，而是 Skill 里「教模型怎么思考」的部分在被模型自身能力吃掉。

但这个驱动力**解释不了全部**。如果只是模型变强，那应该所有 Skill 都在变薄、所有规则都在消失。但你的系统观察是相反的——Harness 在变厚，规则在增加，调度系统在变复杂。


这就引出了第二种驱动力。

### 3. 驱动力 B：工程控制点迁移——你选的《Harness Engineering》提供的证据

你选的《Harness Engineering：AI-First 组织的信任机制重构》把过去几年的大模型工程演进分成了三段：

> 「2023 年是 Prompt Engineering，2024 年是 Context Engineering，到 2026 年，硅谷开始讨论 Harness Engineering。」

注意这句话——它说的不是「模型从 GPT-3.5 升级到 GPT-5」，它说的是**工程焦点的迁移**：

| 阶段 | 工程焦点 | 控制点在哪 |
|------|---------|-----------|
| Prompt Engineering | 怎样写好提示词 | 模型内部的文本 |
| Context Engineering | 怎样给模型更完整上下文 | 模型外部的信息组织 |
| Harness Engineering | 怎样围绕模型建立一套系统 | 模型外部的调度、验证、安全、反馈 |

控制点不在模型内部了。它在模型外面的那层壳——Harness——里。

我觉得很奇怪。

关于 Prompt Engineering，我可以理解，因为我能感受到提示词的作用。在之前 GPT-o3 的那个时代，我能明显感受到一个好的提示词和一个坏的提示词在产出文本和 tokens 上的区别。

上下文 Window 也是，我能够感受到它的变化。拿 GPT 5.6 来举例子，5.6 出来之后，像我之前要给它交代一个任务时，会把很多东西都丢给它；但现在不用了，我只需要给它指个地方，让它自己去找，它自己就能找到更完整的上下文，甚至可能比我说的还要更全一点。

而 Harness Engineering 我不是很理解，比如外部模型的调度、验证、安全和反馈，这个我是真不理解。

文章里的 Peter 说得更直接：

> 「Harness 的对象不只是模型本身，而是围绕模型建立一套系统——基建、tooling、安全保障、sandbox 与 host service 的交互、启动时间、latency，以及系统如何持续 improve。」

这就是**驱动力 B：工程控制点迁移**。不是模型变强所以不需要外部结构，而是外部结构的形态从「写好 prompt 文本」变成了「设计调度系统」。

回到你的演化线：
- Prompt → Skill：控制点从「每次手写指令」移到「封装好的可复用单元」。
- Skill → Workflow：控制点从「单个 Skill 的内容」移到「Skill 之间的串联逻辑」。
- Workflow → Loop：控制点从「固定步骤」移到「状态判断和调度决策」。

每一步，控制权都在从「模型内部」往「模型外部」移动。不是模型被削弱了，而是怎样组织、调度、验证模型这件事本身，变成了一门独立的工程学科。

哎，我想起一个很有意思的观点。

玩 AI 其实很有学问，它跟管理学、哲学、心理学都有关。它要求的是你的内功，而不是外功，就跟武术一样，太有说法了。

当控制权从模型内部向模型外部移动时，我直觉上的第一判断是：模型变强了。我们可以把一些能够自动化的东西外包给它，但是核心的判断是绝对不能外包的。

它能外包你的思考过程，但不能外包你理解本身。你必须对组织、调度、验证模型这件事，有你自己的理解。

### 4. 驱动力 C：人的注意力是硬瓶颈——你选的《Agent 注意力瓶颈》提供的证据

前两种驱动力——模型内化、控制迁移——都是「系统端」的变化。但你选的第三篇文章指向了一个「人端」的约束：

你选的《Agent 工作流的新瓶颈：人的注意力》里，Peter Steinberger 把过去一年的约束分成了三段：

> 「早期受 token 限制，后来受本地 CPU 限制，现在真正稀缺的是人的注意力。」

这句话的关键词是**「真正稀缺的」**。Token 可以加，CPU 可以扩，但人的注意力有硬上限。你一天只有这么多小时能坐在屏幕前做判断。

文章的核心洞察：

> 「真正的优化不是多喊几次模型，而是减少人工介入频率。人的角色因此从盯着过程、催促模型，转向做更高阶的系统判断。」

这就是**驱动力 C：人的注意力是硬瓶颈**。

如果 AI 每做一步都需要你确认——「这个对吗？」「继续吗？」「要不要改？」——那 AI 再强，你的产出上限还是你的注意力。Loop Engineering 的真正目标不是让模型更聪明，而是把人的介入频率降到最低，同时把每次介入的信息质量提到最高。

文章里给出了一组具体做法：Transcript skill（让 reviewer 看到过程而不只是结果）、Auto-review skill（在原始 session 里 review 而不是另起 agent）、CrabBox（把验证移到干净环境）、视觉验证（截图/GIF 代替逐行读代码）。这些做法有一个共同目标：**让人不用盯过程，只在高价值节点介入做判断。**

对，我觉得这个也可以，这个也是挺有说法的。

### 5. 三种力量不是互斥的，是叠加的

把三篇证据放在一起看：

```
模型能力内化（Skills 文章）
    ↓
Skill 里「教模型思考」的部分被吃掉 → Skill 变薄
    ↓
但系统需要的控制没有消失——它转移到了 Harness 里
    ↓
工程控制点迁移（Harness 文章）
    ↓
Harness 在变厚：调度、验证、安全、反馈回路
    ↓
为什么 Harness 必须变厚？因为人的注意力跟不上
    ↓
人的注意力是硬瓶颈（Agent 注意力瓶颈文章）
    ↓
Loop 的优化目标：让人只在必须做判断的节点介入
```

三种力量同时在推同一条演化线：
- **模型内化**：吃掉 Skill 里通用脚手架的部分
- **控制迁移**：把被吃掉的通用逻辑替换成调度和验证逻辑，放在模型外面
- **注意力瓶颈**：决定了迁移的终点——不是全自动，而是「人只做必须人来做的判断」

你选的三篇文章不是碰巧相关的。它们各解释了这条演化线的一种驱动力。

### 6. 回到你自己的任务锚点——注意一个细微偏差

你在 03 的费曼练习里写的任务锚点是：

> 「我要去找什么文章才能去支持或者是推翻这些观点？」


这句话描述的是一个**搜索任务**，不是一个**内容判断**。它回答的问题不是「工作流控制权是否在迁移」，而是「我怎么找文章来验证这个说法」。

差别小，但重要：

| 层级 | 锚点 | 验证方式 |
|------|------|---------|
| 搜索任务（你写的） | 我要找什么文章来支持或推翻 | 找到了文章 = 任务完成 |
| 内容判断（锚点本意） | 工作流控制权正在从 Prompt 迁移到 Loop，驱动力是控制点外移而非模型内化 | 证据支持/推翻/限定了这个判断 = 任务完成 |

你的三篇证据是在做内容判断——它们分别支持了模型内化、控制外移、注意力瓶颈三种驱动力。但你写的锚点把自己框在了「找文章」这个动作里。

这不影响你实际做的事（你确实在用证据验证判断），但影响你**什么时候知道任务完成了**。搜索任务的完成条件是「找到了」，内容判断的完成条件是「形成了可被验证的结论」。前者停得太早。

对，你确实说对了。从结果上面来说，区别并不大，但是从过程来说，区别还是有一点大的：

1. 一个是为了找文章
2. 一个是找到文章之后，要做一个内容判断

我确实明白你的意思。
## 小结

1. Prompt → Skill → Workflow → Loop 的每一步，都在解决前一步制造的问题——但每一步也都把控制权从「模型内部」往「模型外部」推了一步。
2. 演化线的驱动力不是单一的。你选的三篇证据正好对应了三种：模型能力内化（Skills 文章）、工程控制点迁移（Harness 文章）、人的注意力瓶颈（Agent 注意力瓶颈文章）。
3. 三种力量是叠加的——不是某一种在主导，而是它们同时在推。模型变强吃掉通用部分 → 控制转移到外部调度系统 → 因为人的注意力有限，调度系统的目标不是全自动，而是精准的人机判断分界。
4. 你的任务锚点目前停在了「搜索任务」层。往下沉一层——从「找什么文章」变成「要验证什么判断」——会让你的证据包有更明确的停止条件。

其实这两者都有。一方面，模型能力（从 Opus 4.8、Fable 5 到 GPT 5.6）在不断变强，许多原本需要外在设计的能力已经内化到了模型之中。

另一方面，则是工程控制点的前移——我愿意称之为“人在回路”（Human-in-the-Loop）。虽然人的介入频率越来越低，但核心判断和真正关键的地方是不会被取代的。

这种“人在回路”控制点的迁移，其实与我们人类注意力稀碎、碎片化的现状密切相关：
1. 流媒体（如抖音等）和一些短平快的内容，导致我们的注意力变得非常稀碎。
2. 同样的，在工作中如果要求你高频地去介入、切换注意力，时常会让我们忘记真正重要的是什么。也就是说，你的认知带宽根本无法支撑你走完一个完整的任务，导致目标发生偏移（走着走着，突然就发现出问题了）。

所以，这整个过程背后的驱动力主要有两个：
• 模型能力提升带来的能力内化。
• 工程控制点的迁移：让 AI 去介入一些可以自动化的判断，而把我们宝贵的注意力投射在真正有用的地方。
