## 这一篇要解决的问题

这一篇解决一个问题：多个 Agent 并行之前，怎样设计隔离层，让它们有空间发挥，同时避免互相踩文件、踩状态、踩上下文，最后把合并压力全甩给人？

## 正文

第 5 篇讲了三种模式：线性接力、并行分工、总调度。

现在往下一层拆：并行分工的地基是隔离。

你可以把多个 Agent 想成几个人同时在一个项目里做事。如果大家都坐在同一张桌子上，改同一叠纸，用同一个笔记本记录状态，再共用一支笔，效率很快会变成混乱。

worktree 的第一层意义很朴素：给每个 Agent 一张独立工作桌。

桌子分开以后，每个 Agent 可以在自己的区域里试、改、跑、回滚。你最后再看每张桌子上的结果，决定哪些合并，哪些丢掉。

### 1. 并行到底会“踩”什么

多 Agent 并行容易踩 4 类东西。

第一类是文件。

两个 Agent 同时改同一个文件，或者一个 Agent 改组件，另一个 Agent 改同一组件的样式，最后 diff 会互相覆盖。即使 git 能提示冲突，人也要花时间判断谁对谁错。

第二类是状态。

比如同一个 dev server、同一个数据库、同一个测试账号、同一个端口、同一个分支。一个 Agent 改了状态，另一个 Agent 看到的环境已经变了，它还以为是自己任务导致的结果。

第三类是上下文。

Agent A 记住的是一套目标，Agent B 记住的是另一套目标；Agent A 读了项目规则，Agent B 没读；Agent A 使用了最新约定，Agent B 还在按旧约定做。最后输出看起来都努力，放在一起就打架。

第四类是责任。

每个 Agent 都尽力了，每个 Agent 都给出一份看起来有道理的结果。到了合并时，冲突、取舍、返工都集中到一个人身上。这就是你说的“谁尽力谁犯罪”。

所以并行前要先隔离，不然并行只是把一个人的混乱扩展成多个人的混乱。

### 2. worktree 解决的是文件系统隔离

视频里作者说，如果一个目录里已经有 Good Night Have Fun 在跑，再开另一个 Agent，它们会互相踩。

默认解法是 `git worktree`。

你可以把它理解成：同一个 repo，可以创建多个独立工作目录。每个目录都有自己的文件状态，可以在不同分支上工作。

比如：

```text
highbit/          原始目录，Agent A 正在跑长任务
highbit-two/      worktree 目录，Agent B 做另一个任务
highbit-three/    worktree 目录，Agent C 做第三个任务
```

Agent B 在 `highbit-two/` 里改文件，Agent C 在 `highbit-three/` 里改文件。它们可以避免直接把同一个工作目录里的文件改来改去。

这一步保护的是文件系统边界。

它没有自动解决目标拆分、权限约束、测试证据、合并责任。worktree 给了独立空间，工程化流程要决定这些空间怎么用。

### 3. 先手搓一次，才知道能不能并行

你在 Reader 里写到：这些判断要建立在亲身实践经验上。这个点很关键。

很多人一上来想开多个 Agent，其实自己还没手搓过一遍任务拆分。没手搓过，就容易不知道：

1. 目标能不能一句话说清；
2. 输出能不能检查；
3. 任务能不能拆到最小单元；
4. 哪些文件会互相影响；
5. 失败后怎么回滚；
6. 最后由谁合并。

这时强行并行，Agent 的能力会被用在错误方向上。它们很聪明，但跑道没画出来，聪明只会让它们更快跑散。

所以第一个练习可以很小：

```text
只开 2 个 Agent。
只做 2 个互相独立的小任务。
每个 Agent 只允许改自己的范围。
最后只合并一个最清楚的结果。
```

比如一个网站验收任务：

```text
Agent A：只检查移动端布局，输出问题清单和截图证据。
Agent B：只检查桌面端布局，输出问题清单和截图证据。
合并者：只汇总问题，不让两个 Agent 同时改代码。
```

这个练习的目的放在判断能力上：任务能不能拆、边界能不能画、证据能不能收。

### 4. 并行前隔离检查卡

每次开多个 Agent 前，先填这张卡。

| 检查项 | 要问的问题 | 一个合格写法 |
|---|---|---|
| 目标 | 任务能不能一句话说清 | 检查移动端首页布局是否有遮挡、溢出、按钮不可点 |
| 范围 | 每个 Agent 允许碰哪里 | 只看 `/app/home` 相关页面和样式 |
| 禁区 | 哪些文件或状态不能碰 | 不改路由、不改数据库、不动登录逻辑 |
| 共享资源 | 是否共用端口、账号、外部服务 | 每个 Agent 只读本地页面，不提交外部请求 |
| 输出 | 结果交到哪里 | 输出 `发现 / 证据 / 建议 / 风险` 四段 |
| 验证 | 怎么证明结果有效 | 给截图、命令输出、复现步骤或测试结果 |
| 合并 | 谁负责最后合并 | 主线程合并，Agent 只给建议 |
| 回滚 | 出错后怎么撤 | 每个 Agent 在独立 worktree，失败直接丢弃该 worktree |

这张卡回答的是“能不能开并行”。

如果这张卡填不出来，先回到单 Agent 或线性接力。让一个 Agent 帮你把卡填出来，也是一种好用法。

### 5. memory / skill 是并行前的统一入职材料

并行不只需要分工作区，还需要统一规则。

视频里讲 memory / skill 时有一个很重要的逻辑：

- global memory 放所有项目都要知道的短偏好；
- project memory 放这个项目的结构、术语、测试方式和约定；
- skill 放特定任务才需要的长流程；
- 每次 Agent 犯错，把可复用的纠正沉淀到 memory 或 skill。

放到并行语境里，这些材料就是统一入职材料。

如果 Agent A、B、C 分别进入 3 个 worktree，但它们读到的项目规则不同，最后输出会自然分裂。一个按旧测试方式跑，一个按新测试方式跑，一个直接跳过测试。合并时你会发现，它们已经偏离了同一套项目规则。

所以并行启动前，要给每个 Agent 同一份入口说明：

```text
本项目必须遵守：
- 读取 AGENTS.md / 项目 memory。
- 需要改代码时，先说明改动范围。
- 输出必须包含证据。
- 不确定产品取舍时停下来。
- 不能改禁区文件。
```

memory 给所有 Agent 同一套短规则。

skill 给特定任务一套按需流程。

worktree 给每个 Agent 独立空间。

这三层合起来，才像一个可以并行工作的工程环境。

### 6. 怎么让 Agent 发挥智商

你问的核心是：怎样工程化地让 Agent 发挥智商。

答案可以拆成一句话：

把边界放在目标、权限、证据、交付物和合并口，把方法空间留给 Agent。

边界要清楚：

```text
目标：解决什么问题。
权限：能碰什么，不能碰什么。
证据：完成后怎么证明。
交付物：输出成什么格式。
合并口：谁判断、谁合并、什么时候升级给人。
```

方法空间要留出来：

```text
允许 Agent 自己搜索代码。
允许 Agent 提出多个方案。
允许 Agent 选择局部实现路径。
允许 Agent 发现更小的问题并修掉。
允许 Agent 说“这个任务不能并行”。
```

如果你把每一步动作都写死，Agent 会变成高级脚本执行器。

如果你只给一句模糊目标，Agent 会在太大的空间里乱跑。

工程化的做法是在中间：边界清楚，路径开放。

这也是 worktree 的价值。它把“路径开放”的风险圈在一个独立空间里。Agent 可以在自己的 worktree 里探索，主线可以避开探索过程里的直接污染。

### 7. 处理“谁尽力谁犯罪”

并行任务里最容易出问题的地方是合并。

每个 Agent 都尽力，最后结果却互相冲突：

- Agent A 建议改组件结构；
- Agent B 建议改样式系统；
- Agent C 建议改文案层级；
- 三个建议都合理，但合在一起就变成大改。

这时合并者会承担所有代价。

所以并行前要先定合并规则。

可以直接写：

```text
合并规则：
1. 每个 Agent 只给发现和建议，不直接改共享文件。
2. 如果建议涉及同一个文件，主线程先选择一个方向。
3. 如果两个建议互相冲突，列为取舍问题，不自动合并。
4. 涉及产品判断、信息架构、核心数据模型时，停下来问人。
5. 没有证据的建议，只进入待验证列表。
```

这套规则会减少“努力型事故”。

最终解释权要提前指定。

### 8. Treehouse 解决的是 worktree 状态债务

裸 `git worktree` 可用，但它会带来新的管理负担。

视频里作者讲得很直接：

- 你要给 worktree 起名字；
- 你要记住每个 worktree 在干什么；
- 你要记住里面有没有 Agent 还在跑；
- 你要清理不用的 worktree；
- 你要知道哪个 worktree 可以复用。

这些东西都会进入人脑，变成状态债务。

Treehouse 做的是把 worktree 生命周期管理起来：

- 给你一个干净 worktree；
- 让你看到哪些 worktree 在用；
- 关闭后释放；
- 下次复用空闲 worktree。

所以 Treehouse 可以理解成“工作桌管理员”。

worktree 给桌子。

Treehouse 管桌子。

First Mate 再往上一层，负责决定谁坐哪张桌子、干什么、什么时候交结果、什么时候跑验证。

本篇先把桌子和桌子管理员讲清楚。下一篇再讲 First Mate 这个总调度层。

### 9. 一个可以马上用的并行提示词

你下次可以这样开一个小规模并行任务：

```text
我要做一个小规模并行分工。

总目标：
{一句话说清目标}

共享规则：
- 每个 Agent 先读取项目规则。
- 只处理自己的范围。
- 不确定产品取舍时停止并说明。
- 输出必须包含证据。

Agent A：
- 任务：
- 允许范围：
- 禁止范围：
- 输出格式：

Agent B：
- 任务：
- 允许范围：
- 禁止范围：
- 输出格式：

合并规则：
- 最终合并者：
- 冲突处理：
- 验收证据：
- 回滚方式：
```

这段提示词的重点是：让 Agent 有任务空间，但提前把边界、证据和合并口写清楚。

你刚才给我的截图，本质上就是这个格式的一个内容版：

```text
Agent A 分析 memory / skill。
Agent B 分析 multi Agent / worktree。
Agent C 分析 Reader 真实卡点。
最后合并成下一篇课程。
```

它有效，因为三个子任务的信息源不同、输出可以合并、最后有一个明确合并者。

如果这三个 Agent 同时去改同一个 `06.md`，就会产生冲突。让它们只做分析，再由主线程合并，边界就清楚很多。

这就是并行分工的基本手感。

## 小结

- 并行前先隔离，隔离的目标是防止文件、状态、上下文和责任互相踩。
- worktree 给每个 Agent 独立工作目录，主要保护文件系统边界。
- memory / skill 给多个 Agent 统一入职材料，避免每个 Agent 按不同规则工作。
- 让 Agent 发挥智商的关键是：边界清楚，路径开放。
- “谁尽力谁犯罪”通常来自合并规则缺失；并行前要先指定合并者、冲突处理和证据标准。
- Treehouse 管 worktree 生命周期，First Mate 管更高层的任务调度。
