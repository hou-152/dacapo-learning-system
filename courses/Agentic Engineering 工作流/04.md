# 04｜验收：给 Agent 自查，也给你判断

## 本篇基于的反馈

- 你在 Reader 里问：常见错误能不能全部丢进一个建站元技能。
- 你也问：memory、skill、项目元提示词的判断条件记不住，能不能交给 AI。
- 你继续标出了 onboarding、loop 和错题本关系，说明这条主线已经接住。
- 你对“给 Agent 验收”和“给我验收”的区别有兴趣，本篇就沿这个问题推进。
- 本篇只讲验收，不展开 First Mate 和多 Agent 调度。

## 这一篇要解决的问题

这一篇解决一个问题：怎样设计一套双层验收，让 Agent 能先自查，你也能低成本判断交付能不能收？

## 正文

你问了两个很实用的问题。

第一个：常见错误能不能全部丢进一个建站元技能？

第二个：memory、skill、项目元提示词这些分类条件记不住，能不能丢给 AI？

答案可以合并成一句话：

可以把判断交给 AI，但要给 AI 一个分流器，不能把所有错误都堆进一个地方。

你不用背所有条件。条件应该变成一张验收分流卡，让 Agent 自己先判断：这条经验应该放哪里，这次交付应该怎么证明。

### 1. 为什么不能把常见错误全丢进一个元技能

常见错误全丢进一个元技能，短期很爽，长期会变重。

它会出现 3 个问题：

第一，噪声变多。

建站元技能里如果同时塞进 UI、文案、路由、部署、SEO、移动端、可访问性、用户反馈、组件命名、截图验收、性能、表单边界，Agent 每次做一个小任务都要读一堆无关规则。

第二，触发不准。

一个改按钮文案的任务，不一定需要部署规则。一个改移动端布局的任务，不一定需要 SEO 规则。规则堆在一起，Agent 很难判断哪些是当前任务的硬约束。

第三，维护困难。

错误越积越多，元技能会变成垃圾箱。你想改一条规则时，很难知道它影响哪些任务。

所以常见错误可以先进入“收集箱”，但不能一直留在一个大元技能里。

更好的做法是三步：

1. 先收集：把最近错误都放进项目元提示词或错误收集区。
2. 再分流：让 AI 按任务类型、触发条件、稳定度分类。
3. 后沉淀：高频短规则进 memory，长流程进 skill，具体历史留在日志。

你不需要自己记住所有分类条件。你只要保留一个分流动作。

### 2. 把分类条件丢给 AI：可以，但要用固定问题

你说“我记不住这个条件，可以丢给 AI 吗”。可以。

但不能只说：

```text
帮我整理一下这些错误。
```

这句话太松。Agent 会整理得像总结，未必能帮你做工程决策。

更好的问法是：

```text
请把下面这些常见错误分流到 4 类：
1. 适合进 memory：常驻、短小、高频、稳定。
2. 适合进 skill：条件触发、多步骤、长流程。
3. 适合留在项目元提示词：还在试用、触发条件不清、近期会变。
4. 适合留在 changelog / 学习计划：具体历史、单次反馈、进度记录。

每条错误请输出：
- 推荐位置
- 为什么
- 触发条件
- 建议写法
- 如果不确定，先留在哪里观察
```

这就是分流器。

分类条件不用在你脑子里长期保存。你把条件写进分流器，之后让 AI 执行。你的工作是审一下它分得是否合理。

### 3. 双层验收：Agent 自查一层，你判断一层

验收也可以用同样思路。

一次 Agent 交付，最好分两层：

1. Agent 自查层。
2. 人类判断层。

Agent 自查层回答：有没有按规则完成。

人类判断层回答：结果值不值得收。

这两个问题不同。

Agent 自查可以检查：

- 文件是否创建。
- 序号是否连续。
- 标题是否齐全。
- 测试是否通过。
- Reader 是否同步。
- 链接是否能打开。
- 有没有命中禁用句式。

这些检查适合机器做，因为它们清楚、重复、可验证。

人类判断要看：

- 这篇是否接住了你的真实反馈。
- 解释是否让你更容易行动。
- 例子是否贴近你的使用场景。
- 文章有没有变成大框架。
- 你读完是否知道下一步做什么。

这些判断适合你做，因为它们涉及目标、语感、场景和取舍。

### 4. 给 Agent 的验收清单应该具体

给 Agent 的验收清单要像机器任务。

比如这门课的 Agent 自查清单可以这样写：

```text
交付前请自查：

文件：
- 00-学习计划.md 存在并已更新。
- 本轮文章文件存在，序号连续，没有跳号。
- 没有创建未来文章占位文件。

文章结构：
- 包含 本篇基于的反馈。
- 包含 这一篇要解决的问题。
- 包含 正文。
- 包含 小结。
- 包含 口头费曼检查。
- 包含 下一篇预告。
- 包含 学习反馈。

反馈：
- 已读取上一篇本地学习反馈。
- 已读取上一篇 Reader highlights / notes。
- 已忽略默认模板行。
- 已在学习计划中记录本轮反馈摘要。

Reader：
- 已创建 Reader 文档。
- 已读回 Reader 内链。
- notes 里写明 Reader 内链和本地路径。
- 没有使用 codex.local 作为 source URL。

风格：
- 没有命中禁用句式。
- 一篇只解决一个主要问题。
```

这类清单可以交给 Agent 跑。它跑完以后，应该告诉你哪些通过、哪些没跑、哪些需要人工判断。

### 5. 给你的验收要降低判断成本

给你的验收不能变成“请完整阅读全文并判断质量”。这会把工作又丢回你身上。

给你的验收应该让你在 1-3 分钟内做判断。

比如：

```text
请给我人工验收摘要：

1. 本篇接住了哪 3 条真实反馈？
2. 本篇只解决了哪 1 个主要问题？
3. 哪个例子最贴近我的真实使用场景？
4. 哪一段最可能太抽象或太散？
5. 下一篇为什么应该讲这个方向？
6. 我如果只看 30 秒，应该看哪一段？
```

这份摘要不是给 Agent 自嗨的。它是给你省时间的。

你看完这 6 条，大致能判断：这篇能不能收、要不要返工、下一篇方向是否对。

### 6. 验收证据要按任务类型匹配

不同任务需要不同证据。

写学习文章：

- Agent 自查：章节齐全、序号连续、计划更新、Reader 同步。
- 给你判断：反馈是否接住、例子是否有用、下一篇是否自然。

改前端 UI：

- Agent 自查：构建通过、截图生成、移动端和桌面都检查。
- 给你判断：截图或短视频展示真实交互。

修 bug：

- Agent 自查：先有复现，再有修复，再有回归测试。
- 给你判断：用一段日志或操作路径说明用户问题消失。

做资料整理：

- Agent 自查：来源记录完整、文件路径正确、索引更新。
- 给你判断：摘要能不能帮你做决策，是否漏掉关键材料。

所以验收不是一个万能清单。它是一个证据匹配问题：任务是什么，就给什么证据。

### 7. 回到你的建站元技能问题

如果你有一个建站元技能，可以这样处理常见错误。

先在技能里放一个“错误分流”小节：

```text
遇到新的常见错误时，不要直接追加到技能正文。先按以下规则分流：

1. 如果是所有建站任务都高频用到的短规则，建议进入 memory。
2. 如果是某类任务才需要的多步骤流程，建议拆成子 skill 或技能小节。
3. 如果是最近刚发现、还没稳定的偏好，建议留在项目元提示词。
4. 如果只是某次任务的历史反馈，建议留在 changelog。
5. 不确定时，先放入“待观察错误”，累计 2 次后再决定。

每次分流都要给出：推荐位置、触发条件、建议写法、风险。
```

这样你可以把“记不住条件”的负担交给 AI，但又避免它把所有东西都塞进一个技能。

换句话说，你让 AI 帮你分类，而不是让 AI 帮你堆垃圾。

### 8. 本篇形成一张验收分流卡

你可以先记这张卡：

| 问题 | 交给谁 | 输出 |
|---|---|---|
| 这条错误该放哪里 | Agent 分流 | memory / skill / 项目元提示词 / changelog |
| 这次交付有没有按规则完成 | Agent 自查 | 通过项、失败项、没跑项 |
| 这次结果值不值得收 | 你判断 | 收、返工、改方向 |
| 证据是否贴合任务 | Agent 提供，你确认 | 截图、日志、测试、摘要、操作路径 |
| 规则是否该沉淀 | Agent 建议，你批准 | 追加、拆分、观察、删除 |

这张卡的核心是：人不背规则，人设计分流；Agent 不替你做价值判断，Agent 先把证据摆到你能快速判断的位置。

## 小结

- 常见错误可以先收集，但不适合长期全部堆进一个元技能。
- 你可以把 memory、skill、项目元提示词的分类条件交给 AI，但要给固定分流问题。
- 验收分两层：Agent 自查规则完成度，你判断结果值不值得收。
- 给 Agent 的验收要具体、可重复、可检查。
- 给你的验收要降低判断成本，让你快速看到反馈、主问题、证据和下一步。
- 任务类型不同，验收证据也要不同。
