## 正文

第 9 篇把 Agentic Engineering 收成一张总图：

```text
人定方向
Agent 执行
First Mate 调度
验证流水线收证据
人做最终判断
错误沉淀回 memory / skill
```

这张图已经能解释角色分工。新的三篇材料补的是另一层：这套系统怎样运转起来。

运转的关键是 loop。

一个 loop 至少有 5 个部件：

```text
触发方式
状态
工具动作
反馈信号
停止条件
```

少了触发方式，Agent 不知道什么时候启动。少了状态，它不知道自己处在哪一步。少了工具动作，它只能说建议。少了反馈信号，它不知道结果有没有变好。少了停止条件，它会过早交付，或者一直空转。

所以，从 Prompt 到 Loop 的变化，可以写成一个短句：

```text
Prompt 让 Agent 听懂一句任务。
Loop 让 Agent 反复执行、检查、修正，并知道何时停。
Harness 让这套 loop 在真实组织里可用、可信、可维护。
```
Loop 不是最后才出的吗？为什么 harness 这个 Loop 它的优先度更高呢？

### 1. Prompt 解决的是单次理解

Prompt 的目标是让 Agent 明白这次要做什么。

例如：

```text
帮我修一下登录页按钮错位。
```

这句话能启动一次工作，但它没有告诉 Agent：

- 去哪里看当前状态；
- 用什么工具验证；
- 修完后看什么证据；
- 如果失败最多试几次；
- 什么时候需要回来问人；
- 哪些改动不能碰。

Agent 可能真的改出一版，但你仍然要亲自盯过程、猜风险、读代码、重新验收。

这就是人的注意力被拖回 loop 的地方。

### 2. Loop 解决的是重复工作周期

把上面的任务改成 loop，形态会变成这样：

```text
触发：用户提交登录页错位问题。
状态：读取 issue、相关组件、样式文件、最近失败截图。
动作：修改样式，启动 dev server，打开登录页。
反馈：截图对比、console、相关测试、移动端视口检查。
停止：截图通过 + console 无新增错误 + 测试通过；最多尝试 3 次。
升级：超过 3 次仍失败，或发现设计规范冲突，交回人判断。
```

现在 Agent 从“做一下”进入了有边界的工作周期。

每一轮都能回答：

```text
我为什么启动？
我现在掌握了什么状态？
我做了什么动作？
反馈说明什么？
我该继续、停止，还是升级给人？
```

这就是 loop 的工程价值。

### 3. Harness 解决的是组织能不能信任这个 loop

单个 loop 跑通以后，组织里还会出现更大的问题。

多个 Agent 同时工作，PR 数量变多，测试环境不一致，reviewer 不知道一个改动背后有没有真实理解，市场和产品还要判断哪些想法值得继续。

Harness Engineering 处理这一层。

它更像给 Agent 配一整套工作间：

```text
工具权限
sandbox
测试环境
日志
review 规则
PR 证据
自动修复边界
人工升级点
失败复盘入口
```

Harness 的问题意识是：模型单次回答再强，也不能直接变成可信生产系统。可信来自外围机制。

三篇材料里反复出现的机制可以归成 4 类。

第一类是过程透明。

例如 sanitized transcript。它把 Agent 工作过程、尝试路径和推理痕迹整理给 reviewer。代码 diff 像最后答案，transcript 像草稿纸。草稿纸不能保证答案正确，但能降低 reviewer 判断成本。

第二类是上下文内 review。

让 review 回到原始工作会话里，Agent 能用完整上下文判断一条反馈是实际 bug，还是有意的设计决策。若是设计决策，就把原因写进 PR description，避免后面的人重复误伤。

第三类是干净验证环境。

Agent 在一个类似 CI 的干净 box 里安装、运行、测试、截图，减少本机缓存、配置和历史状态污染。平台相关问题要去真实平台验证，不能只在开发者本机上自证。

第四类是视觉和证据压缩。

截图、GIF、VNC、可访问原型，把验证结果变成人容易消费的证据。人可以先看结果是否符合预期，再决定是否深审全部代码。

### 4. 新瓶颈是人的注意力

以前的瓶颈常常是模型能力、上下文长度、token 和本地算力。

当 Agent 可以并行写代码、跑测试、提交 PR 后，瓶颈会迁移到人的注意力：

```text
哪个 PR 值得看？ 哦，哪个 PR 能够说人话？
哪个结果可信？   哪个有吹牛逼？
哪个失败需要人介入？ 
哪个设计决策不能交给 Agent？
多个局部改动合起来是否仍然合理？
```

所以闭环工程的目标是调整人在系统里的位置。

更准确的目标是降低低价值人工介入，把人放回高价值判断点。

低价值介入：

- 每 5 分钟看一次 Agent 有没有跑完；
- 手工复现它声称修好的问题；
- 反复问它有没有测试；
- 从几千行 diff 里猜它到底理解没有。

高价值判断：

- 这个需求值不值得做；
- 这个改动是否符合系统整体；
- 风险是否能接受；
- 证据是否足够；
- 是否需要改路线。

Loop 和 Harness 的价值，就在这里。

它们减少 babysitting，把人的注意力留给判断。

### 5. 最小可行闭环

一开始先把任何一个 Codex 任务写成最小闭环。

模板如下：

```text
任务：
触发：
当前状态：
Agent 可用工具：
禁止触碰：
验证证据：
停止条件：
最大尝试次数：
需要人判断的升级点：
沉淀入口：
```

举个本地文件任务：

```text
任务：修复某个脚本的失败测试。
触发：测试命令失败。
当前状态：失败日志 + 相关脚本 + 最近改动。
Agent 可用工具：rg、测试命令、官方文档、局部编辑。
禁止触碰：无关文件、历史用户改动、全局配置。
验证证据：失败测试变绿；新增或相关测试通过；diff 只包含必要修改。
停止条件：测试通过且 diff 可解释。
最大尝试次数：3 次。
升级点：测试失败原因跨模块、需要产品取舍、或发现历史数据不一致。
沉淀入口：若错误可复现，写入项目 AGENTS.md 或对应 skill。
```

这个模板会逼你把抽象目标压到动作接口。

它也正好接上你在《钱势金生》里的稳定弱项：最后一步必须写清“谁、什么时候、做什么、怎样算完成”。

### 6. 四种 loop 怎么选

材料里可以抽出 4 种 loop。

| 类型 | 触发 | 适合任务 | 风险 |
|---|---|---|---|
| 回合制 loop | 人发消息 | 小任务、探索、短反馈 | 人容易频繁 babysit |
| 目标导向 loop | 明确目标 | 有可量化验收标准的任务 | 尝试次数失控 |
| 时间触发 loop | 间隔或计划 | 定期检查、周期总结、外部状态轮询 | 频率过高会空转 |
| 主动式 loop | 事件或队列 | bug triage、依赖升级、反馈处理 | 需要更强边界和审查 |

选择顺序很简单：

```text
先用最低复杂度。
能回合制解决，就不先上主动式。
能用脚本解决，就不让大模型反复推理。
能明确验收，就写成目标导向。
外部状态变化慢，就降低轮询频率。
```

复杂 loop 的成本会被重复执行放大。自动化越强，越要有成本边界。

### 7. 这篇和旧课题的连接

现在把新材料接回 Agentic Engineering 旧总图：

```text
船长
  定义价值、边界、升级点

First Mate
  判断任务适合哪类 loop，拆分状态和子任务

Agent
  在 loop 中执行动作、收集反馈、尝试修正

memory / skill
  保存验证规则、常见失败、沉淀后的流程

worktree / sandbox
  隔离文件状态和执行环境

验证流水线
  把完成变成证据包

人类判断
  看证据、风险、取舍和系统整体感
```

这就是从 Prompt 到 Loop / Harness / 验证的完整位置。

Prompt 是入口，loop 是工作周期，harness 是可信系统，验证是人类判断的证据压缩。

## 小结

- Prompt 解决单次理解，loop 解决重复工作周期，harness 解决组织信任和长期运行。
- 一个 loop 至少要写清触发方式、状态、工具动作、反馈信号和停止条件。
- 人的注意力会成为 Agent 工作流的新瓶颈，所以证据包、上下文内 review、干净环境和视觉验证都在降低判断成本。
- 好的闭环会保留人类判断，把人的注意力从过程监控挪到价值、风险和系统整体判断。
- 下一步要把抽象闭环压到一个真实任务：用最小模板写出可执行、可验证、可停止的 Codex loop。
