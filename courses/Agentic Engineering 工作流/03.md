# 03｜Onboarding：把错题本变成 Agent 入职卡

## 本篇基于的反馈

- 你在 Reader 里抓住了长指令的关键问题：语音输入能拉满输出带宽，但容易变成思考泄洪，需要训练出高质量长指令。
- 你把 onboarding 理解成错题本：loop 先暴露问题，再把问题沉淀成硬规则和硬约束。
- 你关注多 Agent 模式的形态差异，尤其是线性模式和总调度模式，但本篇先不展开并行架构。
- 你提出验收要区分对象：有些证据给 Agent 看，有些证据给你看。
- 本篇沿着 onboarding 往下走，先解决 memory、skill、项目元提示词分别放什么。

## 这一篇要解决的问题

这一篇解决一个问题：Agent 犯过错、你修正过提示、项目积累了经验之后，怎样把这些经验沉淀成下一轮 Agent 上船前就能读懂的入职卡？

## 正文

上一讲我们把 onboarding 讲成一句话：

onboarding 是把过去几轮 loop 的经验，写成下一轮 Agent 上船前就知道的规则。

你在 Reader 里的“错题本”比喻很准确。一个学生做题，错题本记录自己反复错在哪里、下次遇到同类题该怎么处理。Agent onboarding 也一样。

它不应该变成一本百科全书。它应该回答 4 个问题：

1. 这个项目是什么。
2. 这个项目怎么做事。
3. Agent 以前容易错在哪里。
4. 下次遇到同类任务先看哪条规则。

### 1. Loop 负责暴露错误，onboarding 负责保存错误

先跑 loop，再写 onboarding。

loop 的任务是让问题浮出来。你给 Agent 一个任务，它执行，你检查，发现偏差，然后修正。偏差可能有很多种：

- 它误解了项目目标。
- 它改了不该改的文件。
- 它用了你不喜欢的表达风格。
- 它跳过了端到端验证。
- 它写了很长的方案，但没有给可选决策。
- 它给了很多证据，但这些证据只适合 Agent 自查，你看起来很费劲。

这些偏差第一次出现时，先修任务。第二次出现时，写入 onboarding。第三次还出现，就说明规则写得不够清楚，或者放错了位置。

这就是错题本的逻辑：偶发错误先观察，重复错误要沉淀。

### 2. 项目元提示词：先放还没稳定的经验

项目元提示词可以理解成“临时入职卡”。

它适合放还在试用、还没稳定、还没拆清触发条件的信息。

比如：

```text
这个项目的输出偏好：
- 默认使用中文。
- 不写空泛总结，优先给可执行动作。
- 写课程时必须保留学习反馈区。

这个项目的结构：
- 课程文件在 /Users/housibo/Documents/dbskill-learning/{课题名}/。
- 学习计划固定叫 00-学习计划.md。
- 文章用 01.md、02.md 这种序号命名。

最近常见错误：
- 容易把 Reader 反馈区模板当成用户反馈。
- 容易把下一篇写得太大，超出当前反馈。
- 容易忘记同步 INDEX.md。
```

这类内容先放在元提示词里，方便快速改。它像草稿区。你还在观察哪些规则真的有用，哪些规则只是当时情绪上想加。

判断一个规则适合留在元提示词里，可以看 3 个信号：

1. 最近才出现，还没重复验证。
2. 表述还不够稳定，经常需要改。
3. 触发条件还不清楚，暂时不知道什么时候该调用。

### 3. Memory：放常驻、短小、高频的规则

memory 是 Agent 一上来就会看到的东西。它的位置很宝贵。

适合放进 memory 的规则，要同时满足 3 个条件：

1. 高频：很多任务都会用到。
2. 短小：几句话能说清。
3. 稳定：短期内不会经常变。

比如全局 memory 可以放：

```text
- 技术决策不要过度放大发展成本；AI 实现速度常常比人类估算更快。
- 修 bug 时先尽量复现用户路径，再改代码。
- 输出给用户时简洁说明修改、验证和剩余风险。
```

项目 memory 可以放：

```text
- 本项目课程文章必须包含：本篇基于的反馈、这一篇要解决的问题、正文、小结、口头费曼检查、下一篇预告、学习反馈。
- 继续下一篇前，必须读取上一篇本地反馈区和 Reader highlights / notes。
- 如果反馈信号很少，小步推进，避免一次引入大框架。
```

memory 的危险是膨胀。越写越多以后，Agent 每次启动都背着一大包不一定用得上的东西。它会消耗上下文，也会稀释真正重要的规则。

所以 memory 要像驾驶舱里的常用仪表，少而关键。

### 4. Skill：放条件触发的流程

skill 适合放“只有某类任务才需要”的流程。

比如：

- 写学习文章时，才需要 `dbs-learning` 的反馈提取、学习状态判断、文章结构和验收规则。
- 做前端改动时，才需要截图、移动端检查、视觉重叠检查。
- 修 bug 时，才需要复现路径、失败用例、回归测试。
- 上传 Reader 时，才需要去重、创建文档、读回确认和避免假 source URL。

skill 的价值是按需加载。Agent 先看到一个很短的描述，判断需要用时，再读完整流程。这样可以把大量流程知识放进去，同时不压垮每次对话的上下文。

一条经验什么时候该从 memory 拆成 skill？

看 4 个信号：

1. 它变长了，超过几行。
2. 它有明确触发条件。
3. 它包含多个步骤。
4. 它只服务某类任务。

比如“写学习文章前读取 Reader 反馈”可以先放 memory。等你发现它背后有完整流程：读计划、找最大序号、过滤模板反馈、读 Reader notes、判断学习状态、写文章、更新索引、同步 Reader，这时它就应该进 skill。

### 5. 入职卡可以这样写

你可以把项目 onboarding 做成一张卡，而不是一篇大文档。

```text
项目：Agentic Engineering 工作流课程

目标：
- 把 Reader 视频拆成连续学习文章。
- 每篇根据上一轮 Reader highlights / notes 调整。

工作流：
1. 读 00-学习计划.md。
2. 找到最大序号文章。
3. 提取本地学习反馈和 Reader notes。
4. 形成 3-5 条学习状态判断。
5. 只解决一个主要问题。
6. 更新学习计划和 INDEX.md。
7. 同步到 Reader，并读回确认。

常见错误：
- 把反馈区模板当成用户反馈。
- 没有读 Reader notes 就继续写。
- 下一篇跨度太大。
- 创建 Reader 文档时使用不可打开的 source URL。

验收：
- 本地文章结构齐全。
- 序号连续。
- 学习计划记录反馈和下一步。
- Reader 条目能直接打开。
```

这张卡同时包含项目偏好、项目结构、核心约定和错题本。它可以先放在项目元提示词里。稳定以后，再拆：

- 高频短规则进 memory。
- 完整流程进 skill。
- 具体历史记录留在学习计划或 changelog。

### 6. 高质量长指令怎么训练

你提到一个重要分辨：语音输入能拉满输出带宽，但高质量长指令需要训练。

可以把长指令训练成 6 个槽位：

1. 背景：现在发生了什么。
2. 目标：这次要解决什么。
3. 范围：只看哪里，先别碰哪里。
4. 输出：你希望 Agent 回来给什么格式。
5. 验收：什么证据说明它做对了。
6. 停顿点：什么时候先停下来问你。

比如：

```text
背景：我在做 Agentic Engineering 工作流课程，上一篇 Reader 反馈提到 onboarding 像错题本。
目标：写下一篇，只讲 memory、skill、项目元提示词分别放什么。
范围：不要展开 First Mate，也不要讲多 Agent 并行模式。
输出：生成 03.md，更新 00-学习计划.md 和 INDEX.md。
验收：文章结构齐全，计划记录 Reader 反馈，Reader 同步后能直接打开。
停顿点：如果 Reader 没有真实反馈，先说明基于可见上下文小步推进。
```

这类长指令的质量来自结构，不只是字数。你说得越长，但没有槽位，Agent 接到的是一团意识流。你说得有槽位，Agent 接到的是可执行任务。

### 7. 验收也要进 onboarding

你提到验收要分对象：给 Agent 验收，给你验收。

这个判断很有价值，可以直接写进 onboarding。

给 Agent 的验收适合机器可检查：

- 文件是否存在。
- 测试是否通过。
- 章节标题是否齐全。
- 链接是否返回成功。
- 序号是否连续。

给你的验收适合人类判断：

- 这篇是否接住了上一轮反馈。
- 解释是否讲清楚。
- 例子是否贴近你的真实使用场景。
- 这篇是否太大、太散、太像讲课。
- 你看完是否能拿去做下一步动作。

一个成熟的 onboarding，不只告诉 Agent 怎么做，也告诉 Agent 怎么证明自己做完了。证明分两层：先让 Agent 自查，再让你用低成本判断。

### 8. 本篇形成一个判断表

先用这张表记住边界：

| 类型 | 放什么 | 什么时候用 |
|---|---|---|
| 项目元提示词 | 还在试用的偏好、结构、常见错误 | 刚开始沉淀，规则还会变 |
| Memory | 常驻、短小、高频、稳定规则 | 每次 Agent 上船都该知道 |
| Skill | 条件触发、多步骤、长流程 | 只有某类任务需要时加载 |
| 学习计划 / changelog | 具体历史、反馈、进度 | 回顾上下文和下一步 |
| 验收清单 | 给 Agent 和给人的证据要求 | 每次交付前检查 |

如果只做一个动作，就从项目元提示词开始。先把你最近 3 次纠正 Agent 的话写下来。不要急着抽象成 skill。等同类错误重复出现，再决定它该进 memory、skill，还是留在某个项目文档里。

## 小结

- Loop 负责暴露错误，onboarding 负责保存重复出现的错误和修正方式。
- 项目元提示词适合放还没稳定的偏好、结构和常见错误。
- Memory 只放常驻、短小、高频、稳定的规则。
- Skill 放条件触发、多步骤、只服务某类任务的流程。
- 高质量长指令可以训练成 6 个槽位：背景、目标、范围、输出、验收、停顿点。
- 验收要区分对象：给 Agent 的机器检查，给你的低成本判断。
