# 05｜多 Agent 模式：线性接力、并行分工和总调度

## 本篇基于的反馈

- 你没有新增长反馈，所以本篇基于当前可见上下文小步推进。

- 本篇把这个分流思路迁移到多 Agent：先判断任务适合哪种协作模式。
- 本篇不讲具体工具安装，只讲线性接力、并行分工、总调度的边界。

## 这一篇要解决的问题

这一篇解决一个问题：什么时候该让 Agent 一个接一个做，什么时候可以同时开多个 Agent，什么时候该引入一个总调度 Agent？

## 正文

多 Agent 的关键是分流：一个任务到底适合哪种协作形态。

上一篇我们讲了验收分流卡。现在把同一套思路用到多 Agent：

1. 先判断任务有没有资格进入多 Agent。
2. 再判断它适合线性接力、并行分工，还是总调度。
3. 最后给每种模式配对应的验收方式。

如果这三步没做，多个 Agent 很容易把问题放大。一个 Agent 理解偏了，你只要修一个方向；三个 Agent 同时理解偏了，你会得到三份要收拾的结果。

### 1. 进入多 Agent 前，先过资格门槛

多 Agent 之前，先问 5 个问题：

1. 目标是否清楚？
2. 输出是否能检查？
3. 任务能不能拆成互相独立的小块？
4. 文件或状态会不会互相踩？
5. 失败后能不能回滚或重做？

如果答案大多不清楚，先用单 Agent 跑。

比如“帮我优化这个产品体验”就太大。单 Agent 先做用户路径梳理、问题列表、方案草图更合适。

如果任务已经变成：

- A 负责检查移动端布局。
- B 负责检查桌面端布局。
- C 负责检查文案和交互反馈。

这时才有并行的基础。

多 Agent 的前提是边界清楚。

### 2. 线性接力：适合有先后依赖的任务

线性接力像流水线。

一个 Agent 做完，结果交给下一个 Agent。后一个 Agent 的输入依赖前一个 Agent 的输出。

适合场景：

- 先研究，再写作，再校对。
- 先复现 bug，再修复，再回归测试。
- 先提取反馈，再写下一篇，再验收结构。
- 先做需求澄清，再做实现方案，再开始编码。

比如这门课程本身就很适合线性接力：

1. Agent A：读取 Reader highlights / notes，提取真实反馈。
2. Agent B：根据反馈写下一篇文章。
3. Agent C：检查文章结构、禁用句式、索引和 Reader 同步。

线性接力的好处是方向稳定。每一步都可以吃上一轮结果。

风险是前面一环错了，后面会沿着错误继续走。所以线性接力要在每一环设置“停顿点”：

```text
如果没有真实反馈，请停下来说明。
如果发现方向分散，请先列出取舍，不要直接写文章。
如果验收失败，请先修本地文件，再同步 Reader。
```

线性接力最需要的是交接格式。

一个好的交接格式可以很简单：

```text
上一步输出：
- 目标：
- 关键发现：
- 决策：
- 未解决问题：
- 下一步输入：
```

### 3. 并行分工：适合互相独立的任务

并行分工像同时派出几组人查不同区域。

每个 Agent 处理一个独立子任务，最后把结果合并。

适合场景：

- 多个文件或模块互不影响。
- 多个候选方案可以同时探索。
- 多个资料源可以分别阅读。
- 多个 UI 状态可以分别截图检查。
- 多个竞品可以分别分析。

比如你要做一个建站项目的验收，可以分成：

1. Agent A：只看移动端页面。
2. Agent B：只看桌面端页面。
3. Agent C：只看文案、按钮和表单反馈。
4. Agent D：只看构建、链接和控制台错误。

并行分工的好处是快。不同 Agent 同时工作，互相等待少。

风险是合并成本。每个 Agent 都可能提出一套修法，最后冲突到一起。

所以并行分工要有 3 条硬约束：

1. 每个 Agent 的范围要窄。
2. 每个 Agent 的输出格式要一样。
3. 合并前先做冲突检查。

输出格式可以这样写：

```text
子任务：
发现：
证据：
建议修复：
风险：
是否阻塞发布：
```

并行分工的核心能力是隔离。代码任务里通常需要 worktree。内容任务里也要隔离，比如每个 Agent 只写自己的分析文件，最后由一个合并步骤整合。

### 4. 总调度：适合任务多、状态多、切换成本高的情况

总调度模式里，会有一个上层 Agent 负责分配任务、看状态、拉结果、提醒人做决策。

它适合下面几种情况：

- 同时有很多任务在跑。
- 每个任务需要独立工作区。
- 任务之间有优先级和阻塞关系。
- 人不想不断切换窗口盯状态。
- 背景任务跑完后还要进入验证流水线。

视频里的 First Mate 就是这种角色。它主要帮船长管理 Agent：开工作树、派任务、看状态、跑验证、整理 PR。

总调度的好处是减少人的上下文切换。

风险是你离实际细节更远。总调度如果理解错方向，下面多个 Agent 会一起跑偏。

所以总调度要有更强的“指挥约束”：

1. 先复述总目标。
2. 拆任务前先列出任务边界。
3. 每个子任务要有验收证据。
4. 遇到产品取舍要停下来问人。
5. 定期给状态摘要，而不是只等最终结果。

总调度适合成熟工作流。刚开始学习时，先别急着上来就总调度。先跑通单 Agent，再跑线性接力，再跑小规模并行。

### 5. 三种模式怎么选

可以用一张分流表：

| 任务特征 | 推荐模式 | 例子 |
|---|---|---|
| 有明确先后顺序 | 线性接力 | 研究 → 写作 → 校对 |
| 子任务互相独立 | 并行分工 | 分别检查移动端、桌面端、文案 |
| 任务很多且状态复杂 | 总调度 | 多个项目、多条 PR、多批后台 Agent |
| 目标还很模糊 | 单 Agent 探索 | 先整理问题和方案 |
| 验收方式不清楚 | 单 Agent 或线性接力 | 先做验收清单 |

这张表的重点是：先看任务结构，再决定 Agent 数量。

### 6. 每种模式的验收不同

线性接力要验收交接：

- 上一步有没有留下清楚输出。
- 下一步有没有正确使用上一步结果。
- 中间有没有停顿点。

并行分工要验收合并：

- 每个 Agent 是否只做自己的范围。
- 输出格式是否一致。
- 建议之间有没有冲突。
- 谁负责最终合并。

总调度要验收状态：

- 总目标是否被复述。
- 子任务是否被正确拆分。
- 每个子任务状态是否可见。
- 阻塞点是否及时上报。
- 最终证据是否能让人判断。

这就是上一篇“双层验收”的延伸。Agent 可以自查模式是否跑完整；你来判断模式是否选对。

### 7. 一个具体例子：继续写这门课程

如果用线性接力：

1. Agent A 读 Reader 反馈，输出学习状态。
2. Agent B 写下一篇文章。
3. Agent C 做结构、索引、Reader 同步验收。

如果用并行分工：

1. Agent A 分析原始视频中 memory / skill 部分。
2. Agent B 分析原始视频中多 Agent / worktree 部分。
3. Agent C 分析用户 Reader 反馈里的真实卡点。
4. 最后合并成下一篇课程。

如果用总调度：

你只说：

```text
继续 Agentic Engineering 工作流课程。请管理读取反馈、写下一篇、验收、Reader 同步这几个步骤。每完成一步给我状态摘要；遇到方向取舍先问我。
```

总调度 Agent 自己决定谁读反馈、谁写、谁验收、谁同步。

这三种模式都能做同一个大目标，但它们适合的成熟度不同。刚开始时，线性接力最稳。并行分工适合子任务边界清楚以后。总调度适合任务多到你不想自己盯状态时。

### 8. 本篇形成一张多 Agent 分流卡

你可以先记这张卡：

| 问题 | 如果答案是 | 模式 |
|---|---|---|
| 任务有先后依赖吗 | 有 | 线性接力 |
| 子任务能独立完成吗 | 能 | 并行分工 |
| 状态多到人盯不过来吗 | 是 | 总调度 |
| 目标还模糊吗 | 是 | 单 Agent 探索 |
| 验收方式还没定吗 | 是 | 先做验收清单 |

这张卡帮助你在每次开多个 Agent 前，先做一次分流。

## 小结

- 多 Agent 的第一步是分流，开窗口只是执行形式。
- 线性接力适合有先后依赖的任务，关键是交接格式和停顿点。
- 并行分工适合互相独立的子任务，关键是范围窄、格式一致和合并检查。
- 总调度适合任务多、状态多、切换成本高的情况，关键是目标复述、状态摘要和取舍上报。
- 目标模糊或验收不清时，先回到单 Agent。
- 模式选对以后，再谈 worktree、Treehouse、First Mate 这些具体工具。
