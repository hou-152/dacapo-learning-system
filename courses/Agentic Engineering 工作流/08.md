## 这一篇要解决的问题

这一篇解决一个问题：Agent 做完以后，为什么不能直接相信“我完成了”，而要经过一条验证流水线，把结果变成有证据、可判断、可合并的 PR？

## 正文

第 7 篇讲 First Mate：它负责拆任务、派 Agent、追状态、提醒人处理升级判断。

现在进入下一层：结果出来以后，怎么判断它能不能交付？

Agent 很快。

快带来的第一个问题是：你来不及逐行审。

快带来的第二个问题是：它说“完成了”，不等于结果已经可靠。

所以作者把完成后的代码送进 No Mistakes 这样的验证流水线。流水线的目标很朴素：把“Agent 说完成”变成“人可以判断是否合并”。

### 1. 验证流水线解决的是信任问题

在传统开发里，人会习惯性看 diff、跑测试、手动点页面、看 PR。

Agent 写代码很快以后，这套方式会把人卡住。

每个任务都靠人从头审一遍，人就变成瓶颈。人一天能认真看的 diff 很有限，Agent 一天能产出的改动会越来越多。

验证流水线的作用，是先替人完成一批可机械化、可证据化、可重复执行的检查。

它不替人做价值判断。

它先回答这些问题：

```text
它理解的目标对吗？
它基于最新代码吗？
它有没有引入冲突？
它有没有被独立视角审过？
它有没有端到端跑通？
它有没有留下证据？
它有没有更新相关文档？
它能不能形成可审的 PR？
```

这些问题答完，人再判断产品方向、风险和合并。

### 2. 你的风险表就是核心

你在 Reader 里写了一个很好的表。稍微整理后，它就是本篇主线：

| 底层风险 | No Mistakes 对应动作 |
|---|---|
| 需求理解错了 | 理解原始意图 |
| 代码基于旧世界写的 | rebase 到最新主分支 |
| 冲突只是机械解决，逻辑坏了 | 解决合并冲突 |
| 自己看自己永远顺眼 | 对抗式 review |
| 局部能跑，整体爆炸 | 端到端测试 |
| 做了但没证据 | 记录证据 |
| 行为变了但文档没变 | 更新文档 |
| 风格 / 静态错误没过关 | 检查 lint |
| 还不能交给别人审 | 推分支和准备 PR |

这个表很关键。

它说明验证流水线的重点不在“跑一堆检查”。

它是针对风险逐项关闸。

每一步都在问：这个风险有没有被处理掉？

### 3. 第一闸：理解原始意图

Agent 最危险的错误之一，是很努力地解决了错误问题。

所以验证流水线第一步要回到原始意图。

它要看：

```text
用户最初想解决什么？
Agent 最后交付的东西是否对应这个目标？
中间有没有把任务偷偷换掉？
有没有只修了表面问题，漏掉原始目的？
```

比如原目标是：

```text
让孩子知道语音按钮可以长按说话。
```

Agent 可能会改按钮颜色、加动画、改 tooltip。这些都可能有用，但验证要问：孩子能不能更清楚地知道“可以长按”？

这一步对应人的 what / why。

验证流水线不能替人定义价值，但它可以检查 Agent 是否偏离了最初的 what / why。

### 4. 第二闸：rebase 到最新主分支

Agent 在一个 worktree 里做事时，它看到的是某个时间点的代码世界。

但主分支可能已经变了。

如果不 rebase，Agent 的代码可能基于旧世界：

- 它改的文件已经被别人改过；
- 它用的接口已经换了；
- 它假设的结构已经不存在；
- 它的测试在旧代码上能过，新代码上会炸。

rebase 的意义是把结果放回最新现实里检查。

这一步很像问：

```text
你这个结果在当前世界还成立吗？
```

Agent 在独立 worktree 里探索，最后必须回到主线现实接受检查。

### 5. 第三闸：解决合并冲突

合并冲突不只是文本冲突。

文本能合上，逻辑也可能坏。

比如两个 Agent 都改了同一个组件：

- Agent A 加了一个状态字段；
- Agent B 改了这个组件的 props；
- git 冲突解决了，但状态和 props 的关系断了。

所以流水线里的冲突处理要包括两层：

```text
机械冲突：文件能不能合上。
逻辑冲突：合上以后行为还对不对。
```

机械冲突适合自动处理。

逻辑冲突一旦涉及产品含义，就要升级给人。

### 6. 第四闸：对抗式 review

Agent 自己看自己写的代码，容易顺眼。

这和人一样。自己刚写完的东西，很容易只看到意图，看不到漏洞。

对抗式 review 的作用，是换一个新上下文来找问题。

它可以问：

```text
这个改动有没有遗漏边界情况？
有没有破坏已有行为？
有没有把简单问题复杂化？
有没有偷换需求？
有没有安全、性能、权限、数据风险？
有没有缺少测试或证据？
```

这里的重点是“新上下文”。

同一个 Agent 沿着自己的思路继续看，很容易沿着同一条错误路径走。换一个视角，就像让另一个 reviewer 进来找茬。

### 7. 第五闸：端到端测试

你前面一直关注“谁检查”：人检查，还是 Agent 检查。

端到端测试给的是行为证据。

它不只问代码有没有通过单元测试，还问用户路径有没有跑通。

比如一个 UI 改动，端到端测试应该尽量接近真实使用：

```text
打开页面。
点击按钮。
输入内容。
提交。
看到预期反馈。
截图或录屏留下证据。
```

这一步对应作者在 memory 里强调的偏好：bug fix 和产品行为要尽量贴近用户体验。

局部测试能证明某个函数没错。

端到端测试更接近“这个改动在真实路径里能用”。

### 8. 第六闸：记录证据

没有证据的“完成”，只能靠信任。

有证据的“完成”，可以被判断。

证据可以是：

- 截图；
- 录屏；
- 测试日志；
- 命令输出；
- PR 描述里的验证步骤；
- 失败修复记录；
- 风险评估。

证据的作用不只是装饰 PR。

证据让人不用重新跑完整过程，也能快速判断：

```text
它有没有做对？
它覆盖了哪些路径？
它没覆盖哪些路径？
这个风险高不高？
我还需要看 diff 吗？
```

低风险改动，如果证据充分，人可以少看 diff。

高风险改动，即使证据充分，人也要回到判断位。

### 9. 第七闸：更新文档

行为变了，文档没变，会制造未来错误。

这一步很容易被忽略，因为它不影响当前代码能不能跑。

但 Agentic Engineering 的核心是让后续 Agent 也能接住上下文。

如果代码改了，文档、memory、skill、README、测试说明都没更新，下一个 Agent 会读旧规则。

它会在旧地图上继续走。

所以文档更新有实际作用。

它是在维护组织记忆。

### 10. 第八闸：lint 和静态检查

lint 看起来低级，但它很适合自动化。

它能拦住：

- 格式错误；
- 未使用变量；
- 类型问题；
- import 问题；
- 一些静态风险；
- 团队约定违规。

这些问题不值得人肉反复检查。

能让机器拦的，就让机器拦。

人的注意力要留给 what、why、风险和取舍。

### 11. 第九闸：准备 PR

PR 是把结果交给协作系统的形式。

一个好 PR 至少要让人快速看懂：

```text
原始意图是什么；
改了什么；
怎么验证；
有哪些证据；
风险在哪里；
哪些地方需要重点看；
有没有自动修过问题；
是否还有未解决问题。
```

这一步把 Agent 的工作从“本地改动”变成“可协作对象”。

本地改动只存在于一个 worktree。

PR 进入团队协作、CI、review、合并和回滚链条。

### 12. 人最后看什么

到了这里，可以回到你说的分层：

```text
人负责 what 和 why。
Agent 实现 how。
验证流水线检查 how good。
```

人最后不应该从零开始查所有细节。

人应该看：

1. 原始意图有没有被正确理解；
2. 证据是否覆盖关键用户路径；
3. 风险评估是否可信；
4. 有无产品取舍需要判断；
5. 是否值得合并；
6. 是否需要进一步让 Agent 修一轮。

这样，人就从“代码审查机器”回到“判断者”。

这也是整套 workflow 的目标：中间过程交给 Agent 和流水线，人守住开头和结尾。

## 小结

- 验证流水线解决的是信任问题：把“Agent 说完成”变成“人可以判断是否合并”。
- No Mistakes 的每一步都对应一个底层风险，目的在于逐项关掉失败模式。
- rebase、冲突处理、对抗式 review、端到端测试、证据记录、文档更新、lint 和 PR 准备，分别关掉不同风险。
- 证据让人减少重复检查，把注意力留给 what、why、风险和取舍。
- 人最终看的是意图、证据、风险和合并价值，避免被迫从头盯每一行。
