# 07｜First Mate：把并行状态交给第一副手

## 本篇基于的反馈

- 你澄清“目标”是误输入，实际意思是 OK，继续按 learning skill 往下一章走。
- 第 6 篇 Reader 反馈说明你已经接住了隔离层：文件、状态、上下文和合并责任要分开处理。
- 你对“状态”很敏感，用工业机器人里的 Set / Reset、FB 块完成状态类比 Agent 任务状态。
- 你追问“最后由谁合并，谁变成大脑”，说明下一步要讲清人、Agent 和调度层的职责分配。
- 本篇按原学习计划推进 First Mate：它接管并行任务里的状态、分配、验证和提醒，避免这一章变成新概念堆叠。

## 这一篇要解决的问题

这一篇解决一个问题：当 worktree 和多个 Agent 已经能并行跑起来以后，为什么还需要 First Mate，它具体替船长接管哪些状态管理工作？

## 正文

第 6 篇讲了隔离。

隔离解决的是“多个 Agent 不要互相踩”。但隔离以后，一个新的问题出现了：你要记住每个 Agent 在哪里、做什么、做到哪一步、有没有卡住、最后要不要合并。

这时人会从“写代码的人”变成“盯状态的人”。

视频里的作者也遇到了这个点。Treehouse 让他可以开多个 worktree，多开几个 Agent 并行做事。但跑了一段时间后，他发现自己开始疲于切换窗口：

```text
这个 tab 在干什么？
那个 worktree 里面还有 Agent 吗？
哪个任务已经完成？
哪个任务还要跑 No Mistakes？
哪个结果需要我看？
```

First Mate 就是在这个位置出现的。

它的角色是替船长管理船员，同时把方向判断留给船长。

### 1. First Mate 解决的是状态调度

worktree 管文件隔离。

Treehouse 管 worktree 生命周期。

First Mate 管任务状态和调度。

可以把它理解成一个上层协调者：

```text
船长给方向。
First Mate 拆任务、分配 worktree、启动 Agent、追状态、跑验证、汇报阻塞。
普通 Agent 在自己的 worktree 里执行具体任务。
船长只在关键取舍和最终验收时介入。
```

这里的关键是状态。

没有 First Mate 时，你自己要维护这些状态：

| 状态问题 | 人要记什么 |
|---|---|
| 任务状态 | 哪个任务开始了，哪个任务完成了 |
| worktree 状态 | 哪个工作区在用，哪个可以清理 |
| Agent 状态 | 哪个 Agent 正在跑，哪个卡住了 |
| 验证状态 | 哪个结果已经测试，哪个还没有证据 |
| 合并状态 | 哪个 PR 可合并，哪个需要人判断 |

First Mate 的价值是把这些状态从人脑里拿出来，变成可见、可追踪、可汇报的工作面。

### 2. 它接到任务后先判断能不能拆

视频里作者给 First Mate 的任务是：给 3 个项目都加一个 CLI update 命令。

First Mate 识别出这个目标可以拆成 3 个可并行任务：

```text
项目 A：加 update 命令。
项目 B：加 update 命令。
项目 C：加 update 命令。
```

这一步对应第 5 篇的多 Agent 分流。

First Mate 先判断任务结构：

1. 目标是否清楚；
2. 子任务是否独立；
3. 每个子任务是否需要独立 worktree；
4. 是否可以并行执行；
5. 完成后是否能用统一方式验证。

如果这些条件成立，它才会分配多个 Agent。

如果目标还很模糊，First Mate 应该先把任务拉回澄清，暂停开一堆 Agent。

### 3. 它把任务放进独立 worktree

First Mate 会调用 Treehouse，为每个子任务创建或复用独立 worktree。

这一步继承第 6 篇的隔离原则：

```text
任务 A -> worktree A -> Agent A
任务 B -> worktree B -> Agent B
任务 C -> worktree C -> Agent C
```

每个 Agent 都在自己的工作区里做事。

这样做的好处是：

- 一个 Agent 的中间改动可以避开对另一个 Agent 的直接污染；
- 一个任务失败，可以丢掉对应 worktree；
- 每个任务的结果可以独立验证；
- 最后是否合并，由上层统一判断。

First Mate 开 Agent 的前提是隔离已经设置好。

### 4. 它持续维护一张状态表

你提到工业机器人里的 Set / Reset 和 FB 块完成状态。First Mate 很像在维护一张 Agent 工作流里的状态表。

这张表可以长这样：

| 任务 | worktree | Agent | 当前状态 | 证据 | 需要人判断吗 |
|---|---|---|---|---|---|
| 项目 A 加 update 命令 | wt-a | Agent A | 实现中 | 暂无 | 否 |
| 项目 B 加 update 命令 | wt-b | Agent B | 验证中 | 测试日志 | 否 |
| 项目 C 加 update 命令 | wt-c | Agent C | 阻塞 | API 设计冲突 | 是 |

这张表就是“谁在做什么”的外部化。

没有这张表，人会不断切换窗口，用脑子记状态。

有了这张表，人只需要看：

```text
哪里完成了？
哪里卡住了？
哪里需要我判断？
哪里可以继续自动推进？
```

这就是从“盯每个 Agent”变成“看状态面板”。

### 5. 它把验证流水线接上

视频里 First Mate 不只负责开 Agent，还会跑 No Mistakes。

No Mistakes 做的是验证和 PR 准备：

- 理解原始意图；
- rebase 到最新主分支；
- 解决合并冲突；
- 做对抗式 review；
- 做端到端测试；
- 记录证据；
- 更新文档；
- 检查 lint；
- 推分支和准备 PR。

这些环节让 First Mate 不只是任务分发器。

它更像一个任务推进器：从目标进入任务队列，经过执行、验证、证据、PR，再交回给人判断。

你前面一直问“谁检查”。

这里可以拆成三层：

| 层级 | 检查什么 |
|---|---|
| Agent 自查 | 代码是否能跑，输出是否符合任务 |
| 验证流水线 | 是否通过测试、review、lint、证据记录 |
| 人类判断 | 产品方向、风险取舍、是否值得合并 |

First Mate 管前两层的推进，把第三层留给人。

### 6. 它负责提醒，让人不用一直盯

一个好的 First Mate 要减少人的轮询。

轮询就是你不停问：

```text
你做完了吗？
你卡住了吗？
你测了吗？
你能合并了吗？
```

First Mate 应该主动汇报：

```text
状态更新：
- 3 个任务中，2 个已进入验证，1 个阻塞。
- 阻塞点：项目 C 的 CLI 参数命名会影响现有命令。
- 需要你判断：是否采用 `update` 还是 `self-update`。
- 其余任务无需介入，验证通过后我会准备 PR 摘要。
```

这就是把人从“监工”位置移开。

人可以少盯过程，把注意力放到升级上来的判断。

### 7. First Mate 的升级规则

First Mate 不能什么都自己决定。

它需要明确升级规则。

可以先用这张表：

| 情况 | First Mate 应该怎么做 |
|---|---|
| 子任务边界清楚 | 自动分配 Agent |
| worktree 冲突 | 停止对应任务，汇报冲突 |
| 测试失败但原因明确 | 让 Agent 自修 |
| 产品方向不明确 | 升级给人 |
| 两个方案都可行 | 给对比表，让人选 |
| 缺少证据 | 不进入合并 |
| 风险高 | 要求人确认 |

这个表的作用是防止 First Mate 过度自作主张。

First Mate 可以管理任务，但方向判断仍然在人这里。

### 8. 它回答“谁变成大脑”

你在第 6 篇反馈里问：“OK，谁变成大脑？”

到了 First Mate 这一层，可以这样分：

```text
人：方向大脑。
First Mate：调度大脑。
普通 Agent：执行大脑。
验证流水线：质量闸门。
memory / skill：组织记忆。
worktree：隔离空间。
```

人决定什么值得做。

First Mate 决定怎么拆、怎么排、怎么追状态。

Agent 决定具体实现路径。

验证流水线决定结果有没有证据。

每一层都有大脑，但大脑的职责不同。

混乱通常来自职责重叠：人管太细，First Mate 被压成传话筒；First Mate 管太宽，人失去方向判断；Agent 管太大，合并时没人兜底。

### 9. 一个 First Mate 提示词

你可以把 First Mate 的启动提示词写成这样：

```text
你是这个项目的 First Mate。

总目标：
{一句话目标}

你的职责：
1. 先复述目标和边界。
2. 判断任务适合单 Agent、线性接力还是并行分工。
3. 如果并行，给每个子任务分配独立 worktree。
4. 为每个 Agent 写清任务、范围、禁区、输出和验证方式。
5. 持续维护状态表。
6. 能自动修复的执行问题交给 Agent 自修。
7. 涉及产品判断、风险取舍、合并冲突时升级给我。
8. 每次汇报只给：已完成、进行中、阻塞、需要我判断、下一步。

验收要求：
- 每个完成项必须有证据。
- 没有证据的结果不能进入合并。
- 高风险变化必须先问我。
```

这个提示词把 First Mate 放在正确位置：它是调度层，最终决策者仍然是人。

### 10. 和你的元 skill 想法怎么接

你说隔离检查卡可以变成一个交互式元 skill。

这和 First Mate 可以组合起来：

```text
元 skill：先问清目标、范围、约束、输出、验证、回滚。
First Mate：拿到目标卡后，拆任务、派 Agent、追状态、跑验证。
Agent：在自己的 worktree 里执行。
人：处理升级问题和最终判断。
```

这样链条就完整了。

元 skill 解决“任务入口不清”的问题。

First Mate 解决“任务太多、人盯不过来”的问题。

worktree 解决“并行互相踩”的问题。

验证流水线解决“结果能不能信”的问题。

这几层合在一起，才是可扩展的 Agentic Engineering 工作流。

## 小结

- First Mate 解决的是多 Agent 并行后的状态调度问题。
- 它接管任务拆分、worktree 分配、Agent 启动、状态追踪、验证推进和阻塞汇报。
- 人不应该一直盯每个 Agent，人应该看状态表和处理升级判断。
- First Mate 要有升级规则，产品方向、风险取舍和高风险合并必须交回给人。
- “谁变成大脑”的答案是分层：人管方向，First Mate 管调度，Agent 管执行，验证流水线管证据。
- 你的元 skill 想法适合放在 First Mate 前面，先把任务入口问清楚。
