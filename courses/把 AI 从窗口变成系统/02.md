# 02｜把你的 loop 变成任务状态

## 这一篇要解决的问题

本篇基于 Notion 评论生成。你问“任务状态离开聊天窗口”到底是什么意思，并补充了自己的真实流程：Claude Code 设计 loop，Codex 执行，Claude Code 和人工分别验收。这一篇先把这个流程讲透：任务状态外化，就是把你的 loop 写成 Agent 和人都能接手、检查、复盘的对象。

## 正文

你现在的流程已经有系统雏形。

你大致这样工作：

1. 你把需求告诉 Claude Code。
2. Claude Code 帮你设计一个交互式审计 loop。
3. loop 写出来后，你丢给 Codex 执行。
4. Codex 返回结果。
5. Claude Code 看一遍。
6. 人工再看一遍。
7. 最后分成两套验收：一套给人看，一套给 Agent 验收。

这套流程很有价值，因为它已经把“写代码”拆成了几种职责：需求理解、loop 设计、执行、机器验收、人工判断。问题也在这里：如果这些职责只存在聊天里，每次换工具、换窗口、换任务，你都要重新解释一遍。

“任务状态离开窗口”，就是把这套职责写成稳定结构。

### 1. 窗口里保存的是聊天，系统里保存的是任务

聊天窗口适合讨论。你可以在窗口里说：我想做一个页面，我想修这个 bug，我想把这个流程自动化。

任务系统要保存另一组东西：

1. 这个任务要解决什么问题。
2. 输入材料在哪里。
3. 哪些约束必须遵守。
4. 现在处于哪个 phase。
5. plan 是什么。
6. 预期结果是什么。
7. 哪些 bad case 已经出现。
8. 验收标准是什么。
9. 谁负责执行，谁负责检查。
10. 最后证据放在哪里。

你在 Notion 评论里写的那串词很关键：gate，input，约束，phase & plan，结果，bad case，验收标准。

这基本就是任务状态的骨架。

如果这串东西只散在聊天里，Codex 接手时要读一长段上下文；Claude Code 回看时也要重新理解；人工验收时还要问“当时到底要求什么”。如果这串东西被写成任务卡，任何执行者都能从同一张卡开始工作。

### 2. gate：先决定任务能不能进系统

gate 是入口检查。

它回答的问题是：这个任务现在是否足够清楚，能不能交给 Agent 执行。

一个任务进入系统前，至少要过 4 个 gate：

1. 目标 gate：要解决的问题能否用一句话说清。
2. 输入 gate：所需文件、链接、材料是否齐全。
3. 约束 gate：哪些文件不能动，哪些风格要保留，哪些风险要避开。
4. 验收 gate：完成后用什么证据判断通过。

例如你说“帮我优化一下建站元技能”。这个任务还不能直接执行，因为它缺少 gate 信息。

更稳定的任务卡会这样写：

```markdown
## Gate

- 目标：优化 Codex 的建站元技能，让它减少常见前端实现错误。
- 输入：现有 skill 文件、近期失败案例、用户给出的 AGENTS.md 编码准则。
- 约束：只改 skill 相关文件；不重构无关内容；保留可回滚备份。
- 验收：用 3 个 smoke prompt 测试，确认 skill 能触发正确检查。
```

gate 的作用，是阻止模糊需求直接进入执行层。模糊任务一旦进入执行层，后面会出现大量返工。

### 3. input：让执行者拿到同一批材料

input 是材料清单。

你现在会把 loop 给 Codex 执行。Codex 如果没有读到完整 input，就会自己补上下文。补得越多，偏差越大。

input 要写清楚 3 类材料：

1. 必读材料：执行前必须读。
2. 可选材料：需要时再读。
3. 禁用材料：看起来相关，但本轮不能用。

例如：

```markdown
## Input

### 必读

- `/Users/housibo/.codex/skills/web-development/SKILL.md`
- `/Users/housibo/Documents/工程化 skill/output/recent-failures.md`

### 可选

- 最近 3 次建站失败截图
- Playwright 验证日志

### 禁用

- 不读取无关项目目录
- 不根据泛泛前端最佳实践重写整个 skill
```

这样写以后，Agent 的探索范围会收窄。它知道从哪里开始，也知道哪里不能乱碰。

### 4. 约束：把“别犯蠢”翻译成可检查规则

你说这些工具有时会“犯蠢”。这个判断很真实，但 Agent 无法直接执行“别犯蠢”。

约束要把这种经验翻译成可检查规则。

例如：

```markdown
## 约束

- 不新增超出用户需求的功能。
- 不顺手重构旁边代码。
- 不改没有证据支持的问题。
- 修改前先说明假设。
- 每个 diff 都能追溯到任务目标。
- 如果触碰已有用户改动，先读清楚再继续。
```

这些约束来自你的 AGENTS.md 准则，也来自你对 Codex、Claude Code、小龙虾执行风险的经验。它们不该只留在人的脑子里。写进任务卡后，Agent 可以自查，人也可以拿它验收。

### 5. phase & plan：让任务有阶段，不靠窗口记忆推进

phase 是当前阶段，plan 是下一步路线。

很多跨天任务失败，原因是系统不知道当前处于哪个阶段。一个窗口里可能同时出现研究、方案讨论、实现、验证、修补、总结。窗口还开着时，人能靠上下文判断；窗口断掉后，接手者就很难判断。

任务卡可以这样写：

```markdown
## Phase

当前阶段：实现前审计

## Plan

1. 读取现有 skill 和失败案例。
2. 提取 3 个最高频错误模式。
3. 改 skill 的触发规则和验收规则。
4. 跑 smoke prompt。
5. 记录结果和回滚路径。
```

这会让任务拥有进度感。下一位执行者打开任务卡时，能直接知道当前处于哪里。

### 6. 结果：让产物有固定落点

结果不能只是一句“done”。

结果要写清楚产物路径、验证证据和剩余风险。

例如：

```markdown
## 结果

- 修改文件：`/Users/housibo/.codex/skills/web-development/SKILL.md`
- 备份文件：`/Users/housibo/.codex/skills/web-development/backups/2026-07-06-SKILL.md`
- 验证命令：`node scripts/smoke-web-dev-skill.mjs`
- 验证结果：3/3 pass
- 剩余风险：尚未用真实建站任务验证
```

这样的结果能被 Claude Code 复查，也能被人工快速判断。它把“执行完成”变成“证据可读”。

### 7. bad case：把犯错记录变成下一次的防线

bad case 是你这套 loop 里最重要的学习材料。

Agent 犯过的错误，如果只在聊天里骂一句，下一次还会发生。bad case 要写成结构：

```markdown
## Bad Case

- 现象：Agent 把简单页面做成复杂后台系统。
- 触发条件：用户只说“做个页面”，没有明确成功标准。
- 根因：任务 gate 太弱，允许 Agent 自行扩展需求。
- 防线：实现前必须写出“本轮不做什么”。
- 验收：diff 中不能出现无关模块和新增复杂依赖。
```

这就是学习层的入口。bad case 进入任务系统后，可以变成约束、skill、测试或 checklist。

### 8. 验收标准：分成人看和 Agent 看

你说验收分两版：给人看的，给 Agent 验收的。这个分法是对的。

人的验收看判断：

1. 目标是否达成。
2. 方案是否符合你的真实意图。
3. 风格是否对。
4. 风险是否能接受。
5. 下一步是否值得继续。

Agent 的验收看证据：

1. 文件是否存在。
2. 命令是否跑通。
3. 测试是否通过。
4. 禁用句式是否扫过。
5. 页面是否截图验证。
6. 索引是否同步更新。

同一个任务要有两套验收，因为人和 Agent 的强项不同。Agent 适合做可枚举检查，人适合做方向、价值和边界判断。

### 9. 你的 loop 可以写成一张任务卡

把上面合在一起，你的 Claude Code → Codex → 人工验收流程可以变成这样：

```markdown
# Task Card

## Gate

- 目标：
- 输入是否齐全：
- 约束是否清楚：
- 验收是否可检查：

## Input

- 必读：
- 可选：
- 禁用：

## Phase & Plan

- 当前 phase：
- 下一步 plan：

## Roles

- Claude Code：设计 loop，审计方案，做机器复查。
- Codex：执行文件修改、验证、同步产物。
- 人工：判断目标、边界、质量和真实可用性。

## Result

- 产物路径：
- 验证证据：
- 剩余风险：

## Bad Case

- 已知失败模式：
- 本轮防线：

## Acceptance

### Agent 验收

- 文件存在：
- 命令通过：
- 索引更新：
- 禁用规则扫描：

### 人工验收

- 目标达成：
- 风格正确：
- 风险可接受：
- 下一步明确：
```

这张卡就是“任务状态”。它不属于任何一个窗口。Claude Code 可以读，Codex 可以读，人也可以读。

### 10. 本篇的关键判断

任务状态离开窗口，含义是把任务拆成可接手、可执行、可验收、可复盘的结构。单纯复制聊天记录，仍然无法形成稳定任务系统。

你现在已经有 loop。下一步要把 loop 的关键节点固定下来，先形成小而稳定的任务系统：

1. gate 决定能不能执行。
2. input 决定读什么。
3. 约束决定不能怎么做。
4. phase & plan 决定推进路径。
5. result 决定产物落点。
6. bad case 决定下一次防线。
7. acceptance 决定人和 Agent 分别验什么。

这就是从“我在窗口里指挥 AI”走向“我有一个可迁移的任务系统”的第一步。

## 小结

- 你当前的 Claude Code → Codex → 人工验收流程已经有系统雏形。
- 任务状态外化，就是把 loop 写成 gate、input、约束、phase & plan、结果、bad case 和验收标准。
- Claude Code 更适合设计 loop 和复查方案，Codex 更适合执行和验证，人负责最终判断。
- 人的验收看目标、边界、风格和风险；Agent 的验收看文件、命令、测试和证据。
- bad case 要进入任务卡，成为下一次执行前的防线。
