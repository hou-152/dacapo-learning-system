# 01｜Why：什么时候值得从一个 Agent 升级到一支 Agent 团队

## 这一篇要解决的问题

这一篇只解决 Why：一个任务在什么情况下值得引入多 Agent？我们先检验“像团队交互”这个联想，再把判断落到一个你亲历的任务里。

## 正文

### 1. 当前可见的学习信号

你已经给出第一条联想：“我觉得有点像团队交互。”

这条联想抓住了原文中的几个机制：有角色分工、有任务归属、有协调者，Agent 之间还能直接发消息。它已经足够作为学习起点。现在还缺一层：团队为什么要出现？如果一个 Agent 已经能低成本完成任务，增加成员只会增加拆分、同步、合并和验收的工作。

所以，Why 要回答的是一个升级阈值：单 Agent 遇到了哪一种结构性瓶颈，多 Agent 带来的收益才有机会覆盖编排成本？

### 2. 多 Agent 自带一笔“协调税”

每增加一个 Agent，系统都会多出几项工作：

- 把总任务切成边界清楚的子任务。
- 给每个 Agent 配置足够的上下文和限制。
- 避免重复调查或同时修改同一状态。
- 传递相互依赖的信息。
- 合并不同结果并处理冲突。
- 用证据验收结果，把最终审批交回用户。

这笔成本可以叫作“协调税”。多 Agent 的价值需要先覆盖它。

为了方便判断，本课采用一个学习用公式：

```text
升级净收益
= 并行、专业化、减少上下文切换带来的收益
- 拆分、同步、合并、验收带来的协调成本
```

这是基于原文提炼出的判断工具，不是原作者给出的数学定律。

### 3. 四类任务更容易跨过升级阈值

第一类，资料或代码上下文分散，而且可以分区调查。几个 Scout 各查一块，能够缩短等待时间。

第二类，子任务彼此独立，串行执行会形成明显排队。例如分别检查移动端、桌面端、文案和构建状态。

第三类，任务数量和状态已经超过人的持续跟踪能力。Coordinator 可以记录职责、阻塞和进度，让人保留方向判断。

第四类，存在多个可以独立验证的假设。不同 Agent 分头找证据，最后由 Coordinator 汇总矛盾并交给人裁决。

只有“任务很难”这一条信号还不够。目标模糊、验收不清时，多 Agent 很容易同时沿着几个错误方向前进。此时先让一个 Agent 澄清目标和验收方式，通常更省。

这个怎么办，交给 agent 吗

### 4. “团队交互”这个类比目前成立到哪里

它在协作结构上成立：

- 角色有差异，例如 Scout、Worker、Smart worker。
- Coordinator 管任务归属和重复调查。
- Agent 可以把发现直接发给需要它的队友。
- 用户保留产品取舍、高风险动作和最终审批。

它在责任结构上有明显边界：

- Agent 只拥有任务范围内的执行职责，责任仍然归于发起和审批这套系统的人。
- 新上下文不会自动继承任务限制；关键权限和安全边界要重新写清。
- 共享消息可以减少转发等待，也可能放大错误信息，因此证据和验收仍然要独立存在。

所以，你的联想已经抓住“协作结构”。下一步要用真实任务检验：你想要的究竟是并行速度、专业分工、状态管理，还是多视角证据？

### 5. 用这次学习本身做一次对照

“读取今天的 AI 内参，再进入交互式学习”有明确先后依赖。先读材料，后讨论概念；这条主链适合线性推进。

如果今天要同时比较 5 篇互相独立的多 Agent 实操材料，再核对官方文档，多个只读 Scout 就可能带来收益。它们可以分头取证，最后由一个 Coordinator 消解冲突。

任务结构决定团队是否出现。Agent 数量只是后续配置。

## 小结

- 多 Agent 会产生拆分、同步、合并和验收成本。
- 升级条件来自任务结构，以及收益能否覆盖协调税。
- 分散调查、独立子任务、复杂状态和可独立验证的假设，更容易适合多 Agent。
- “团队交互”在角色、归属和通信层面成立；责任与审批仍然收敛到人。
- 本轮学习结果要由你的真实任务回答来补齐。
