# 02｜What：多 Agent 编排到底在编排什么

## 这一篇要解决的问题

你问：“这个怎么办，交给 agent 吗？”这一篇先回答谁来判断任务要不要分发，再拆清多 Agent 编排实际控制的 5 个对象。

本篇基于当前可见上下文生成。你已经提供了真实经历，但还没有写出那次任务的内部结构，所以关于“多 Agent 会不会更快”的结论暂时保留。

## 正文

### 1. 先结算你第 1 课的回答

你提供了两条很有价值的信息：一次 GPT-5.5 任务占掉约 50% 的上下文，执行约半小时；你判断，如果当时有 5.6 Sol 的多 Agent 分发，任务可能早已完成。

把这段回答分成 4 层：

- FACT：那次任务的上下文消耗很高，耗时约半小时。这是你的亲历记录。
- INFERENCE：单 Agent 可能承担了过多上下文，或者串行处理了本可并行的工作。
- UNKNOWN：任务能否拆成互相独立、可单独验收的部分。
- RECOMMENDATION：先画任务结构，再决定分发；用一次真实重跑检验速度和质量。

这里存在一个逻辑跳跃：上下文很大、耗时很长，并不能单独证明多 Agent 一定更快。如果任务由 5 个独立调查组成，分发很可能有效；如果后一环必须等待前一环，多开 Agent 会增加等待、同步和合并。

你已经找到了 Why 的候选答案：减少单一 Agent 的上下文压力和串行等待。现在进入 What，看看系统究竟要分配什么。


-------
### 2. “要不要分发”可以交给 Agent 做第一轮判断

可以交给 Coordinator 做任务分流。前提是你先给它判断规则和授权边界。

一个够用的默认分流规则可以这样写：

```text
先分析任务的依赖、风险、写入范围和验收方式。
边界清楚、互相独立、只读的调查，可以自动委派。
范围明确、文件不重叠的实现，可以提出并行方案。
目标模糊、验收不清、权限敏感或存在产品取舍时，先向用户汇报并等待审批。
```

这样一来，你不用亲自记住每条分流规则。Coordinator 负责第一轮判断，你保留规则制定、例外处理和高风险审批。

可以把决策分成 3 层：

| 决策层 | Agent 可以做什么 | 需要回到用户的情况 |
|---|---|---|
| 建议 | 画任务图、识别依赖、估算协调成本 | 用户决定是否采用方案 |
| 低风险委派 | 自动派只读 Scout，调查互相独立的问题 | 发现目标冲突、权限问题或来源不足 |
| 有写入的并行 | 在职责和文件范围明确后派 Worker | 跨模块修改、不可逆动作、产品取舍和最终审批 |

所以，Agent 可以承担“怎么分”的计算。你负责设定“允许分到哪里”。

### 3. 编排控制 5 个对象

原材料给出 4 个调节旋钮：推理档位、上下文继承、委派权限和协作方式。为了方便实际使用，本课把任务归属单独列出来，形成 5 个编排对象。

| 编排对象 | 要回答的问题 | 常见配置 |
|---|---|---|
| 任务归属 | 谁对哪一块结果负责？任务之间有什么依赖？ | Coordinator、Scout、Worker、Smart worker |
| 推理档位 | 这块工作值得想多深？ | 只读侦察用低档，明确实现用中档，困难判断用高档 |
| 上下文 | 这个 Agent 应该看到多少历史？ | 继承对话，或从 fresh context 开始 |
| 委派权限 | 它能否继续找帮手？能读什么、写什么？ | 叶子 Agent 禁止继续委派；高难 Worker 可在边界内协调 |
| 信息与审批流 | 发现发给谁？冲突由谁裁决？谁批准落地？ | 队友直接通信，Coordinator 汇总，用户审批 |

这 5 项合起来，才形成一支可控的 Agent 团队。只打开多个窗口只能得到并发；任务归属、权限和收拢方式决定并发能否变成协作。

### 4. 用“团队交互”来理解这 5 项

你的类比可以继续使用：

- 任务归属对应团队里的岗位和负责人。
- 推理档位对应把不同难度的工作交给不同资历的人。
- 上下文对应入职交接和项目背景。
- 委派权限对应一个人能否继续调动资源。
- 信息与审批流对应谁可以直接沟通、谁负责汇总、谁拥有拍板权。

这个类比还有一条重要边界：真人团队可以依靠长期关系、默契和组织记忆补齐信息；Agent 主要依赖当前上下文和明确规则。你没写进去的关键限制，它未必知道。

### 5. 回到你那次“50% 上下文、半小时”的任务

先看两种可能结构。

如果任务可以拆成：

1. Scout A 查资料与事实。
2. Scout B 查代码或历史决策。
3. Worker C 根据清楚输入完成一个独立产物。
4. Coordinator 汇总、去重、检查冲突。

那么多个 Agent 能把完整上下文切成几份聚焦上下文，也能减少串行等待。

如果任务是一条强依赖链：

```text
理解问题 → 做出关键判断 → 根据判断继续 → 再根据新结果修正
```

那么分发空间会明显变小。此时更有价值的动作可能是压缩上下文、沉淀 Skill、建立状态摘要，或者只在某个独立调查环节派 Scout。

你当时的判断有可能是对的。当前还缺任务拆分证据。下一步就补这块。

### 本轮只回答一个问题

那次占掉约 50% 上下文、耗时半小时的任务，如果最多拆成 3 个可以独立验收的结果，会是哪 3 个？如果拆不出来，也请直接说卡在哪一层依赖。

不用追求完美拆分，试试就知道了。

## 小结

- Coordinator 可以承担第一轮分流判断，判断规则和授权边界由用户设定。
- 多 Agent 编排控制任务归属、推理档位、上下文、委派权限、信息与审批流。
- 高上下文和长耗时提示了潜在瓶颈，还不能独立证明多 Agent 更快。
- 独立、可验收的结果决定任务有没有并行空间。
- 用户保留规则制定、例外处理、高风险动作和最终审批。
