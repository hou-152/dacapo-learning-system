06｜工程熵：为什么项目会从能改变成没人敢动
======================


本篇基于的反馈
-------


* 你在 Reader 里高亮了“小方法、元方法、元原理”，说明你已经开始把具体技巧抽成稳定方法。
* 你高亮了“任何输出都要接回有限的人、有限的注意力、有限的风险承受能力和具体系统边界”，说明你抓住了熵增里的边界问题。
* 你高亮了“行动接口要回答：谁在什么条件下做什么，做到哪里停”，说明你认可行动接口是降熵关键。
* 你高亮了总公式“降熵方法 = 正确通道 × 合适加工 × 人类代价边界 × 最小行动”。本篇把这个公式迁移到工程系统里。


这一篇要解决的问题
---------


为什么一个代码项目会从“能跑、能改、能理解”，慢慢变成“没人敢动”？这一篇讲工程熵的核心机制：变更不断进入系统，但测试、边界、文档、依赖和责任接口没有同步更新。


正文
--


工程熵最常见的体感是：



> 
> 这个项目还能跑，但没人敢改。
> 
> 
> 


这句话很准确。系统并没有彻底坏掉，业务还在运行，页面还能打开，任务还能执行。问题是每一次修改都变得越来越贵：要读更多上下文、猜更多隐含规则、担心更多副作用、等更多人确认。


工程熵增加的核心是变更成本，代码行数只是表层信号之一。


### 1. 工程熵的第一层：上下文变厚


一个项目刚开始时，逻辑通常很薄。


一个页面对应一个接口，一个接口对应一张表，一个配置只影响一个环境。你想改一个地方，很快能知道它影响哪里。


项目运行一段时间后，上下文会变厚：


* 一个字段同时被页面、报表、导出、权限、缓存使用。
* 一个接口兼容旧客户端、新客户端和临时脚本。
* 一个配置在测试环境、生产环境、灰度环境含义不同。
* 一个函数名字很清楚，但里面藏了 3 个历史特殊规则。
* 一个看似废弃的任务，其实每周还被某个自动化调用一次。


上下文变厚以后，工程师的第一反应会变成“先别动”。常见原因是变更成本和风险边界都变高了。


这就是工程熵的第一种表现：理解成本上升。


### 2. 第二层：依赖变密


工程系统会自然长出依赖。


一开始，模块 A 调用模块 B。后来为了赶进度，模块 C 也直接读 B 的内部字段。再后来，脚本 D 复用了 C 的中间结果。再后来，一个 agent 工具也开始依赖脚本 D 的输出格式。


这时，你再改 B，就会牵动一串隐形依赖。


依赖变密会带来三个后果：


第一，局部修改变成全局风险。


第二，测试范围变得难判断。


第三，删除旧逻辑变得很困难。


工程熵可以由很多动作带来：复用、抽象、自动化、脚本、配置，都可能增加依赖密度。一个系统里最危险的部分，经常是“大家都在用，但没人完整知道谁在用”的东西。


### 3. 第三层：验证变弱


一个系统能不能安全修改，很大程度取决于验证能力。


验证能力强时，你改完能很快知道有没有破坏关键行为。测试会报错，类型会提示，监控会报警，日志能定位，回滚路径清楚。


验证能力弱时，你只能靠人脑模拟：


* 这条分支是否会影响老用户？
* 这个字段为空时有没有问题？
* 这个脚本是否只在周末跑？
* 这个异常是否以前就有？
* 这个 agent 输出格式有没有被别处解析？


人脑模拟越多，工程熵越高。


AI 编程会把这个问题放大。AI 很擅长生成修改，但如果验证系统弱，它生成得越快，人类要验证的东西越多。机器侧生成成本下降，人类侧审查、测试和回滚成本上升。


这和前面几篇的信息熵增是同一个结构。


### 4. 第四层：文档和真实系统分叉


文档本来是降熵工具。


好的文档能告诉你系统边界、核心流程、不能碰的地方、常见失败模式和验证方法。它让新人少猜，也让老人不用靠记忆维护系统。


但文档会过期。过期文档比没有文档更危险，因为它给人一种错误确定性。


常见分叉包括：


* README 写的启动命令已经跑不起来。
* 架构图里没有新增的队列和定时任务。
* 环境变量表漏了新增开关。
* 接口文档说字段可选，真实线上要求必填。
* 旧注释解释了过去的逻辑，当前代码已经变了。


文档和真实系统分叉以后，工程师会开始不信文档，只信“问老人”和“看线上”。这会把系统知识从公共结构退回个人记忆。


个人记忆越重要，组织熵也会同步上升。


### 5. 用降熵公式看工程系统


现在把上一篇公式搬过来：



> 
> 降熵方法 = 正确通道 × 合适加工 × 人类代价边界 × 最小行动
> 
> 
> 


用在工程系统里，它可以变成四个问题。


第一，正确通道：这个问题属于理解、修复、重构、删除、验证，还是归档？


很多工程任务一开始就分错通道。一个线上 bug 被当成重构做，一个架构债被当成临时修复做，一个没人用的旧模块被当成继续维护做。通道错了，后面都会变乱。


第二，合适加工：现在需要的是依赖图、测试用例、日志、文档、类型，还是删除清单？


如果你要理解系统，先画依赖图。  

如果你要修 bug，先写复现用例。  

如果你要删旧逻辑，先查调用链和运行记录。  

如果你要接 AI agent，先固定输入输出协议。  

如果你要重构，先建立回归验证。


第三，人类代价边界：改错了会影响谁，怎么发现，怎么回滚？


工程师不敢动，很多时候是因为代价边界不清。知道错了会怎样，知道怎么退回来，人就敢做更小的修改。


第四，最小行动：15 分钟内能做的第一步是什么？


工程系统的最小 MVP 通常很小：


* 跑一次测试。
* 复现一个 bug。
* 加一条日志。
* 画出一个函数的调用链。
* 给一个边界条件补测试。
* 把一个旧配置标成候选删除。
* 给一个 agent 输出补 schema。


这些动作不一定一次性解决工程熵，但它们会让系统从“没人敢动”进入“开始恢复可验证性”。


### 6. 一个完整例子：AI agent 输出格式变乱


假设你有一个 AI agent，每天生成一份 Markdown 报告。最初只有人读，所以格式比较自由。


后来另一个脚本开始解析报告里的标题。再后来日报系统开始抓取某个列表。再后来你让另一个 agent 根据这份报告生成任务。半年后，没人敢改报告格式。


这里的工程熵在哪里？


* 上下文变厚：报告从“人读”变成“人和机器都读”。
* 依赖变密：多个脚本和 agent 都依赖它的隐含格式。
* 验证变弱：没有 schema，没有解析测试，没有样例快照。
* 文档分叉：README 还写着“自由 Markdown 输出”。
* 人类代价边界不清：改一行标题可能影响日报、任务生成和后续 agent。


按降熵公式处理：


正确通道：这个问题属于输出协议治理，范围超过单纯改文案。


合适加工：需要列出消费者、补 schema、加快照测试、更新 README。


人类代价边界：先确认哪些系统读取报告；改动前保留旧格式兼容；失败时回滚到旧模板。


最小行动：15 分钟内先收集 3 个最近输出样例，并找出所有解析这个文件的脚本。


这个最小行动不大，但它把系统从“凭感觉改”拉回“有边界地改”。


### 7. 工程降熵的核心动作


工程降熵的重点是让系统可理解、可验证、可恢复、可删除。代码优雅有价值，但它要服务于这些目标。


你可以记住四个动作：


第一，显式化边界。


写清楚输入、输出、调用者、责任范围。


第二，建立验证。


测试、类型、schema、日志、监控、快照，都是让系统能安全变化的结构。


第三，降低依赖密度。


减少隐式共享，拆开互相缠绕的路径，给高风险接口加稳定协议。


第四，制造最小可动点。


别一上来“大重构”。先找一个 15 分钟能开始、风险可控、能增加理解或验证的小动作。


工程降熵的现实目标是：每次改动以后，系统比之前更容易理解一点、更容易验证一点、更容易恢复一点。


小结
--


* 工程熵的体感是项目还能跑，但没人敢改。
* 它主要增加理解成本、依赖风险、验证成本和文档分叉成本。
* AI 编程会放大这个问题：生成更快时，验证系统弱就会把成本转移给人。
* 工程降熵可以套用总公式：正确通道 × 合适加工 × 人类代价边界 × 最小行动。
* 真正有效的工程降熵，是让系统更可理解、可验证、可恢复、可删除。
