这一篇要解决的问题
---------


很多 AI 工具看起来都在提高效率：写得更快、总结更多、自动化更多。但它们有时只是把生产成本降下来，把验证、恢复、判断和责任成本转移给人。我们要学会判断一个工具的“净降熵”。


正文
--


“净降熵”这个词可以先理解成一句很实用的话：



> 
> 一个工具带来的总秩序，大于它制造的总混乱。
> 
> 
> 


更具体一点：



> 
> 净降熵 = 减少的判断、验证、沟通、恢复成本 − 新增的阅读、审查、维护、误用成本
> 
> 
> 


如果一个 AI 工具让你生成快了 10 倍，但让你审查、修错、回滚、解释、维护的成本也涨了 10 倍，它可能只是把熵从生产端转移到了验证端。


### 1. 只看“产出更多”会误判


AI 工具最容易展示的指标是产出：


* 一分钟生成 5 个方案。
* 一次总结 20 篇文章。
* 自动写 300 行代码。
* 每天生成一份完整日报。
* agent 自动跑完整个任务。


这些都很诱人，因为产出是可见的。问题是，熵增经常藏在产出之后。


你要继续问：


* 谁来读这些方案？
* 谁来判断哪一个能用？
* 谁来验证代码有没有破坏旧行为？
* 谁来负责日报里的错误判断？
* agent 失败后谁来恢复现场？
* 后续维护这些自动化的人是谁？


这些问题指向工具的隐性成本。


一个工具的真实价值，要看它减少了多少总成本。


### 2. 净降熵评估的五类成本


你可以用五类成本评估一个 AI 工具、agent、日报或自动化工作流。


第一，判断成本。


它有没有帮你更快判断什么重要、什么可丢、什么该行动？如果它只是生成更多选择，判断成本可能上升。


第二，验证成本。


它有没有帮你确认结果可靠？比如测试、引用、证据链、schema、样例、反例。没有验证结构的自动化，通常会把成本推给人。


第三，沟通成本。


它有没有让团队更容易对齐？比如输出格式稳定、责任人明确、结论和证据分层。模糊总结会增加沟通成本。


第四，恢复成本。


错了以后能不能回滚、复现、定位、恢复？这里就是你提到 Git 的地方。Git 的价值超过保存代码历史，它让人敢改，因为系统有恢复路径。


第五，维护成本。


这个工具以后谁维护？配置、提示词、脚本、依赖、权限、账号、数据源、输出格式是否会变成新的负担？


净降熵评估要看这五类成本的总和。


### 3. Git 为什么是降熵工具


你在 Reader 里写“git 的重要性”，这个点非常好。


Git 的核心价值超过“代码备份”。它降低了工程行动的心理压力。


没有 Git 时，改代码像在原稿上直接涂改。你会怕改坏，怕找不回来，怕不知道自己动了哪里。


有 Git 后，系统多了几层降熵结构：


* diff：你能看到自己改了什么。
* commit：你能把变化打包成一个可解释单位。
* branch：你能隔离实验，不直接污染主线。
* revert：你能撤回错误。
* blame / log：你能追踪变化来源。
* PR：你能让别人审查、讨论和验证。


这些结构降低了恢复成本和协作成本，所以人更敢做小步修改。


这就是前面讲的“人类代价边界”。Git 给行动加了边界：错了可以找到、可以比较、可以回退。


所以，Git 是典型的工程降熵工具。它不直接替你写代码，但它让系统更可改、更可查、更可恢复。


### 4. AI 工具什么时候净增熵


AI 工具有时会净增熵。常见情况有四种。


第一，生成很多候选，却没有筛选规则。


比如让 AI 生成 20 个标题、10 个方案、5 个架构，但没有评价标准。你从空白焦虑变成选择焦虑。


第二，生成代码，却没有测试和回滚。


代码变多了，验证压力也变大。没有测试、类型、日志和 Git 小步提交，AI 写得越快，人越不敢合并。


第三，生成日报，却没有行动接口。


每天都有完整总结，但没有“影响哪个判断、谁做什么、什么时候停”。这类日报会堆积阅读负担。


第四，自动化任务，却没有失败恢复。


agent 能跑一长串动作，但失败时没人知道它改了什么、停在哪、怎么恢复。自动化越长，恢复成本越高。


这些场景共同的问题是：工具降低了生产成本，但提高了判断、验证、恢复或维护成本。


### 5. AI 工具什么时候净降熵


一个 AI 工具开始净降熵，通常有五个信号。


第一，它减少选择。


比如它把 50 条信息压成 3 条必须处理的判断，并说明为什么。


第二，它附带证据和反例。


比如每个结论都有来源、样本、限制、反方观点，验证成本下降。


第三，它输出稳定格式。


比如固定 schema、固定字段、固定层级。机器和人都能读，后续维护成本下降。


第四，它有失败边界。


比如它只改一个文件、只生成草案、不直接写生产库、保留 diff、可回滚。


第五，它能形成最小行动。


比如它把“深入研究”压成“15 分钟内先查这 3 个字段”。


这些信号共同说明：工具已经开始帮系统减少总成本。


### 6. 一个净降熵检查表


以后你评估任何 AI 工具、agent、日报、工作流，可以用这张表。



```
1. 它进入哪个系统？
   个人学习 / 投资判断 / 内容生产 / 工程开发 / 团队管理 / 其他

2. 它减少了哪类成本？
   判断成本 / 验证成本 / 沟通成本 / 恢复成本 / 维护成本

3. 它新增了哪类成本？
   阅读成本 / 审查成本 / 配置成本 / 误用成本 / 依赖成本 / 恢复成本

4. 它有没有证据和验证结构？
   引用 / 测试 / schema / diff / 日志 / 反例 / 样例

5. 它有没有失败边界？
   能否撤回 / 能否回滚 / 影响范围多大 / 谁负责

6. 它有没有最小行动？
   15 分钟内能开始的第一步是什么？

7. 总判断：
   净降熵 / 持平 / 净增熵

```

这张表的关键是第 3 题。很多工具只会展示减少了什么，很少展示新增了什么。你要主动把新增成本算进去。


### 7. 用表评估一个例子：AI 代码助手


假设你用 AI 代码助手改一个老项目。


它减少的成本：


* 帮你快速理解某个函数。
* 生成候选修改。
* 补测试草案。
* 解释错误日志。


它新增的成本：


* 你要审查生成代码。
* 你要确认它没有误解业务规则。
* 你要跑测试。
* 你要看 diff。
* 你要确认改动范围没有扩大。


如果项目有 Git、小步 commit、测试、类型、日志，AI 代码助手更可能净降熵。因为恢复成本和验证成本被结构接住了。


如果项目没有测试，文档过期，依赖很乱，AI 一次改 8 个文件，工具很可能净增熵。它让你产生“进展很多”的感觉，但后续审查和恢复压力暴涨。


同一个 AI 工具，在不同系统里效果不同。系统有结构，它更像加速器；系统缺结构，它可能变成熵增放大器。


小结
--


* 净降熵要看总成本，产出数量只是起点。
* 评估 AI 工具时，要同时看判断、验证、沟通、恢复和维护成本。
* Git 是典型工程降熵工具，因为它降低恢复成本、验证成本和协作成本。
* AI 工具净增熵时，常见表现是候选变多、验证缺失、行动接口缺失、失败恢复困难。
* AI 工具净降熵时，会减少选择、附带证据、输出稳定格式、设失败边界、形成最小行动。
