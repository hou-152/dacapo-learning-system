# 01｜先分清：你拥有 100 个 Skill，不等于每次都该带上它们

## 要解决的真实问题

你担心 Skill 太多，也怀疑强模型与 [[Loop Engineering]] 会削弱 Skill 的存在感。当前真正需要判断的不是「Skill 是否还有用」，而是：一个能力究竟应作为可调用库存存在，还是应在每一次任务中常驻进模型上下文。这是 [[交互式学习]] 和 [[Agentic Engineering 工作流]] 共享的一个核心问题——[[第一性原理]] 告诉我们要先定义「能力」到底是什么，再判断它该放在哪里。

## 最小知识地图

### 1. 能力库存与工作记忆是两件事

Skill、工具、规则、示例和历史材料都可以是系统的能力库存：系统知道在需要时可以调用它们。

但一旦把它们全部写进全局规则、每轮提示词或常驻工具清单，它们就从库存变成工作记忆的一部分。模型不是只「知道它们存在」，而是每轮都要阅读、排序并处理它们。

因此，100 个 Skill 的第一个风险不是数量本身，而是它们是否同时竞争当前任务的注意力。



### 2. 为什么常驻越多，未必越强

RSS 的实测案例中，同一模型与同一任务下，Claude Code 首轮会携带约 3.3 万 token 的系统提示、工具 schema 和脚手架，OpenCode 约 0.7 万 token。加入大规则文件、多个 MCP 或子 Agent 后，开销继续叠加。

这不直接证明「Claude Code 更差」。在多步骤任务里，Claude Code 因为能批量工具调用，累计成本可能反而更低。它证明的是：系统设计不能只比较某一层的厚薄；任务轮数、调用方式、缓存稳定性和上下文占用共同决定结果。

### 3. 任务不是越开放，越要多给上下文

GitHub 的代码审查案例给出一个反例：给 Agent 换上更通用、更好维护的工具后，审查成本上升，有用问题反而变少。原因不是工具弱，而是 Agent 开始广泛搜索、猜路径、读大片代码，陷入「一直在看，但没有更接近证据」的浏览循环。

它们把工作流改为：从 diff 形成具体问题 → 用低成本搜索收窄 → 只读取确认或否定该问题所需的最小证据 → 根据 trace 复盘。生产成本约下降 20%，质量没有出现阻止发布的下降。

这告诉我们：强模型不等于不需要 Harness；需要的是让 Harness 把注意力收敛到当前任务，而不是把所有能力一次性暴露出来。

## 费曼到任务

请把你电脑里的 Skill 当成一个工具仓库，而不是一串必须同时开机的软件。选一个你最常做的真实任务，例如「从学习材料形成内容选题」或「把判断转成视频脚本」，试着指出：这个任务一开始真正必须常驻的是什么？又有哪些 Skill 只应在出现特定缺口时才调用？

## 检查站

1. 用自己的话解释：为什么「系统拥有很多能力」不等于「每一轮都该把这些能力注入上下文」？
系统拥有很多能力，不等于每一轮都要把这些能力输出到上下文。

就像你有一个工具箱，里面有很多扳手，但你没必要全天都提着它。因为这个工具箱会经常占据你的注意力，增加你的认知负担——你会不由自主地去想：我这个工具箱要放哪里？每天提着它，还得提防它被丢了或者被人偷拿了。

我用这个比喻想表达的是，虽然我们有一些工具，但并不需要整天都带着它们。我们只需要在特定的任务场景下，比如我现在有个活要去给人修水龙头，再把对应的工具带上就行了。

2. 以你的一个真实任务为例，列出 1 个必须常驻的信息，以及 2 个应按状态调用的 Skill 或能力。

就是常驻的信息。比如说 dbs-learning 这个 skill，我是用来交互式学习的。
而它里面列出一个必须常驻的信息，就比如我使用这个 skill 的前提，是它要有很多高质量的信息源，能够提升我学习东西的速度和斜率。
那好，我必须得常驻一些 RSS 信息源和 AI 内参。这两个非常有价值的信息源，能够帮助它更快地去完成任务，而按状态调用的 Skill 或能力有我的流水线视频工作流
