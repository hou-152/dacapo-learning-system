# 04｜四层架构全景：把记忆分成四层，每层各管一件事

## 这一篇要解决的问题

你上一轮把「语义 + 语境」用自己的话讲了一遍，还举了「考研 vs 不考研」的矛盾例子。这个理解对观点类内容成立，但对事实类内容有另一套解法。这一篇先把这个区别讲清楚，再把 docs 里的四层架构完整铺开：每一层装什么、为什么分层、你的四法嵌在哪。

## 正文

### 先讲清一个区别：事实矛盾和观点矛盾

你的理解（用你的原话概括）：用语义搜出候选的观点、案例、问题；同一问题出现互相矛盾的答案时，让大模型放进具体语境里检索和推导。你参考 dbs-content-system 做的那套，就是这类处理。

这个理解成立，它成立的范围是「观点类内容」。把它再精确一步：

- **事实矛盾**（地址、手机号、订单状态）：只有一条当前有效。用双时间戳直接标记生效时间，查询取当前有效那条，无需推导。这是 03 篇的结论。
- **观点矛盾**（该不该考研）：两条可能同时有效，适用条件不同。靠带语境判断——提问者是谁、什么阶段、什么约束，让模型挑出适用的一条，或者把两条连同各自条件一起摆给用户。

你的例子落在观点矛盾上，所以你的解法是对的。面试时把这两类分开答，考官听到的就是 50k 那套：事实用时间戳，观点用语境。

### 四层架构：为什么要分层

docs 里 50k 候选的记忆是四层。分层的理由一句话：不同数据，访问方式不同、生命周期不同、成本不同。把它们全塞进向量库，就是用一种方式对待所有数据，demo 能跑，生产会炸。

四层从里到外：

**第一层：会话元数据（内存）**

会话 ID、入口渠道这类信息。这一轮会话内有价值，会话结束就归零。放内存，用完就扔，不落库。

为什么：落库要花存储、检索、token 的成本，而它的价值在会话结束时消失。扔得越快，库里越干净。

**第二层：用户结构化数据（JSON）**

身份、偏好、历史关键决策。走 JSON 存储，查询时直接键值拿，不碰语义搜索。

为什么：这些是要「精确相等」的数据（02 篇）。双时间戳挂在这一层，状态冲突在这里解决（03 篇）。

**第三层：近期摘要（向量库）**

把最近几次对话压缩成主题和关键实体，语义检索只在这一层用。

为什么：只有模糊的、换着说法问的东西才需要语义检索。压缩成主题 + 实体还能压 token——全文喂进去贵，摘要便宜。你参考 dbs-content-system 做的那套加工（压缩成问答对、洁癖笔记），正是这层的原料工序：把原始对话加工成干净的、可检索的资产，再进向量库。

**第四层：滑动窗口（当前轮原始材料）**

当前这轮的原始对话原文，超了上下文就处理（压缩或淘汰旧的）。

为什么：当前轮必须用原文，靠摘要会丢细节。滑动窗口是「永远在场」的那层，其它三层是「按需取用」的。

### 一个请求进来，数据怎么流动

用户问「我之前说的那个地址改了吗」：

1. 滑动窗口里有这轮的原文，先看。
2. 会话元数据知道这是谁、哪个入口。
3. JSON 层键值拿地址，双时间戳只给当前有效的那条。
4. 近期摘要层语义检索，看有没有相关历史主题（比如「搬家」讨论过几次）。
5. 拼起来生成答案。

每一层各司其职，没有一层包办全部。docs 里那句「不要让向量库一统天下」，说的就是这个。

### 你的四法嵌在哪

- 打时间戳 → 第二层（JSON 字段上的 valid_from / valid_to）。
- 按功能语义打标签 → 元数据，贯穿二、三层。
- 压缩成问答对 → 第三层的原料工序。
- 压缩成洁癖笔记 → 第三层的原料工序。

四法你已经有了，四层是它们的安放位置。你之前在小龙虾上做的事，四法已经用上了，只是还没按层摆放。

## 小结

1. 事实矛盾用双时间戳（只读当前有效），观点矛盾用语境判断（两条可能都有效，按条件取用）。
2. 四层分层的理由：不同数据的访问方式（精确/语义）、生命周期（用完即扔/长期保存）、成本（token）都不同。
3. 四层：会话元数据（内存，用完即扔）、用户结构化数据（JSON 键值 + 双时间戳）、近期摘要（向量库语义检索 + 压 token）、滑动窗口（当前轮原文）。
4. 你的四法各有安放位置：打时间戳进第二层，打标签贯穿，问答对和洁癖笔记是第三层的原料工序。
