# 03｜第二个雷：状态冲突，解法是你已经学过的「打时间戳」

## 这一篇要解决的问题

你上一轮写了三条：语境是你执行中自己感受出来的；你以前以为「标注」是机器学习里那种数字标注；还有别名（一个名字多个叫法）的问题。这一篇先各回一句，然后讲第二个雷——用户先说上海后说北京，新旧状态打架怎么办。解法正好落在你列的四法第一法「打时间戳」上。

## 正文

### 先回你的三条

**「语境是我自己感受出来的」。** 这说明你的经验先于术语存在。你在执行里摸到的那些东西，后来才被叫成混合检索、重排序、Context Engineering。感受是原始证据，术语是通用语言，两者互相印证。这跟你学过的「规则 = 验证过的经验」是同一条路：先有体验，再给它命名。

**「标注」有两种意思。** 你想到的那种，是机器学习里的数据标注（data labeling）：给训练样本打标签（这张图是猫、这句话情感是正面），用来训练模型。知识库里说的标注是另一件事：给每段文字挂元数据字段（来源、日期、主题），检索时用来过滤。同一个中文词，两个不同的动作，你现在的知识库里发生的是第二种。

**别名问题。** 一个实体多个名字——「上下文工程师」和 Context Engineering 指的是同一件事，检索时问「Context Engineering 怎么入门」，要能找到写着「上下文工程师」的段落。这在生产级知识库里叫实体归一（alias / entity resolution），靠别名表把不同叫法映射到同一条记录。它是第三个雷，先埋个钩子，后面专篇讲。

顺带一句：token 译作「词元」，是大模型处理和计费的文本单位。docs 里说「语义检索只在这一层用，还能压 token」，意思就是压缩摘要可以少喂字、省成本。

### 第二个雷：状态冲突

场景照搬你下载的 docs：用户先说「我在上海」，后来又说「我搬到北京了」。按最小链路的做法，两条信息都进了向量库，语义都相近，一检索两条一起出来，Agent 分不清哪条是当前有效的，带着过期信息做决策。

8k 的候选怎么答的：「让用户重新说一遍，或者清一下缓存。」清缓存等于把信息扔掉，还把成本推给用户。用户说过的每句话都应该留在库里。更好的做法：给每条信息记下「从什么时候开始生效、到什么时候失效」，新旧信息都在，任何时刻只有当前生效的那条会被采用。

### 解法：双时间戳

给每个事实挂两个时间：

- valid_from：从哪天开始有效。
- valid_to：到哪天失效。

用户搬家这件事，这样处理：

- 旧地址那条不动，只把它的 valid_to 改成搬家那天。
- 新地址新增一条，valid_from = 搬家那天，valid_to 空着（表示至今有效）。
- 查询时只读「valid_from 已到、valid_to 还没到」的那条，也就是当前有效的地址。

这样一来，两条信息都留在库里，但任何时刻只有一条「生效」。这就是你四法里的第一法「打时间戳」在生产级的用法：时间戳打给事实本身，标注它从何时生效、到何时失效。

顺便把上一篇接上：地址这种字段，本来就该放在结构化层（JSON），双时间戳就是挂在结构化字段上的两个时间。精确数据走 JSON，时间戳管「哪条当前有效」，两件事正好配成一对。

### ledger / view / policy：三个词各管一件事

docs 最后那段还有三个词，它们是这套设计的三个零件：

- **ledger（账本）**：底层只追加、不删除、不覆盖。用户说过的每句话按时间顺序记进去，历史永远可查——地址改过 3 次，3 条全在。
- **view（视图）**：查询时不直接翻账本，而是按当前任务投影出一个「现在有效」的视图。查地址，投影出当前地址；查历史，投影出 3 次搬家记录。账本只有一份，视图按需生成。
- **policy（规则）**：管谁能写、谁能读、什么时候必须删（比如合规要求的遗忘权）。数据本身和数据的规矩分开管。

三个词串起来：ledger 保证历史不丢，view 保证查询又快又对，policy 保证数据可控。

### 回头看你的「文本处理四法」

你把它们列出来的时候，其实已经站在生产级门口了：

1. 打时间戳 → 解决状态冲突（本篇）。
2. 按功能语义打标签 → 元数据标注（02 篇）。
3. 压缩成问答对 → 把一段内容压缩成「问题 + 答案」的形式，检索命中率更高，后面落地你的库时用得上。
4. 压缩成「洁癖」笔记 → 把口语、口水话清干净，只留可检索的干货。

四法里前两法已经对上了技术名词，后两法是你自己的库落地时的工序。多模态融合是另一条线（图片、语音也进库），先放一放，前沿篇再提。

## 小结

1. 状态冲突：同一实体有新旧多条信息，语义检索会把它们一起捞出来，Agent 分不清哪条当前有效。
2. 解法是双时间戳：给每个事实挂 valid_from 和 valid_to，改状态时掐断旧条、新增一条，查询只读当前有效。
3. ledger 只追加不删保历史，view 按任务投影出当前有效，policy 管读写和合规。
4. 你四法里的「打时间戳」就是这件事的起点，你的经验已经走到术语前面了。
