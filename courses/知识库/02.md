# 02｜标注和语境装在哪：检索靠的不只是「语义相近」

## 这一篇要解决的问题

你上一轮留了两个具体问题：切块、转向量、存向量库之后，「标注」在哪一步；以及你发现小龙虾 + dbs-content-system 除了语义还看语境。这一篇先把这两件事装回骨架里，再顺势拆开第一个雷——精确查询和语义检索为什么必须分开。

## 正文

### 先接住「我大概懂了」

骨架你立住了：切块 → 转向量 → 存向量库 → 检索 → 生成，检索的核心是「语义相近」。下面往这个骨架里加两个零件，正好是你问的那两个。

### 问题一：「标注」在哪一步

我上一轮的 5 步里没有「标注」，你问它在哪，很合理。答案：标注不单独占一步，它挂在两个位置上。

**挂在「切块」上。** 切的时候顺手给每一段打标签：这段是谁说的、哪天说的、讲的是哪个主题、对应什么问题。

**挂在「检索」上。** 查的时候先用标签缩小范围，再做语义匹配。

用你熟悉的例子讲。书稿 5.1 里那句「每上传一批内容，同步维护一份索引，索引越细越好用」，它在技术上的对应物，就是给每一段挂元数据（metadata）。元数据是「标签」的正式叫法：每段文字的向量旁边，挂着一排字段——来源、日期、主题、对应的问题。

检索的时候，可以先按字段过滤，再在剩下的里面做语义匹配。比如你先标了「这批内容都讲知识库」，问「知识库第一次答得不好该怎么办」时，工具就只在这个主题下面找，命中率比在整个库里漫无目的地找高得多。这就是「索引越细越好用」的机制。

### 问题二：「语境」是不是比「语义」多一层

你观察对了。你用的工具除了语义相近还看语境。把它翻译成技术词，大概对应两件事：

1. **混合检索**：同时用「关键词」和「语义」两种方式找，再把结果合并。关键词负责精确命中，语义负责找到意思相近但用词不同的段落。
2. **重排序**：先粗捞一批（比如 50 段），再用一个更精细的模型，把「问题 + 每一段候选」放在一起看语境，重新打分排序，只留前几段交给大模型。

所以你感觉到的「语境」，其实是「语义相近」后面的第二道工序：语义负责粗筛，语境负责精挑。你之前用的工具把这两道都做了，所以它看起来比只算向量距离的「更懂」。

### 落到第一个雷：精确查询和语义检索为什么必须分开

现在可以拆面试题里的第一个雷了。

手机号、订单号这种信息，靠语义相近没用。「138xxxx」和「400xxxx」语义上都算「电话」，向量离得近，但你要的是精确相等。反过来，「怎么判断内容被限流」这种问题，靠精确匹配也没用，因为原文里没有这句话，只有意思相近的一段。

所以这是两个不同的动作：

- **精确查询**：要「相等」。手机号精确等于 138xxxx，订单号精确等于某串数字。适合用结构化存储（JSON、关系库、键值），直接按字段拿。
- **语义检索**：要「相近」。适合模糊的、换着说法问的问题，走向量库。

两个动作混在一起，就是 demo 里最容易踩的坑：拿语义检索去查手机号，查不准。

这也正好解释你下载的 docs 里四层架构为什么那么分：

- 第二层「用户结构管理」（身份、偏好、手机号、订单号）走 JSON，用键值精确拿——因为它要的是相等。
- 第三层「近期摘要」走向量库，用语义检索——因为它要的是相近。
- 你的「标注」在两层都起作用：结构化层用字段名当标签，摘要层用主题、实体当标签。

你上一轮问的「标注在哪」和「语境」，到这一层就合上了：标注（元数据 + 过滤）管精确，语义 + 语境（混合检索 + 重排序）管相近，两个动作各归其位。

## 小结

1. 标注不单独成步，挂在切块（打标签）和检索（按标签过滤）两个位置，正式名叫元数据。
2. 你感觉到的「语境」，技术上是混合检索 + 重排序，「语义相近」只是第一道粗筛。
3. 精确查询要「相等」，语义检索要「相近」，两个动作必须分开存储、分开查找。
4. docs 里四层架构的分工，就是这两个动作各归其位的结果。
