# 07｜边界：你的飞轮是一套自迭代系统，RSI 的断点也是它的断点

## 这一篇要解决的问题

你的 06 反馈里有两件大事：作业 05 的「建议」你交了一份完整的飞轮方案；你把整门课的方法论落回了你的真实主线。这一篇先收作业、校准你两个概念修正（元数据 / 数据容器、触发的双重职责），然后把内参的 RSI 断点直接压到你的飞轮上：哪里会断、哪里要人死守、哪里可以放手。

## 正文

### 先收作业 + 校准两个概念

**1. 作业 05 三件交付物齐了。** 任务说明（六要素全文）✓、真实回执（02:30 执行成功的记录）✓、你的建议 ✓。而且这份建议超规格：它不是一句话，是一套最小闭环。课程作业到这里正式完成。

**2. 「数据容器」说小了，你修正得对。** 你的新表述（脚本数据 + Meta 文件 + 运行机制）就是 05 那张家谱表。王自如的「结构化 is everything」约等于元数据——这个等价式成立，可以再精确一步：元数据是结构化的最小载体，数据是元数据的规模化。「数据容器」把 skill 说成了仓库，「编排 + 适配 + 验证」把门卫和质检也算进去了。

**3. 「一个是触发，一个是检验」——你抓住了一个我在 05 没讲透的点。** description 有两个职责：触发（把 skill 推荐给合适的请求）和守门（挡住不合适的请求）。写得太窄，该来的时候不来（undertrigger）；写得太宽，不该来的时候来一堆（误触、烧 token）。aihot 的「不要 undertrigger」在调第一端；case study 的「只在小红书截图时来」在调第二端。你 06 说「把这段话和 Skill 做匹配」时其实看到了两步：先判断该调用（触发），再确认调用没错（检验）。

**4. 元 Skill 的想法先放进问题池。** 你项目里已经有三个候选：skill-darwin-lite、huashu-nuwa、以及你自己写的「未来薄 Skill 候选规格」（audit-intelligence-environment）。按你自己 CONTEXT 里的规则：好奇能开问题，立项要复发型问题。等这个想法第二次以「需要」的形式出现，再立项。dbs-learning 封装进去这件事同理——它现在跑得好好的，为封装而封装会先付一笔迁移成本。

### 你的飞轮，已经是一套自迭代系统

把你写的飞轮和这门课的机器逐件对上：

| 你的飞轮环节 | 课程里的对应 |
|---|---|
| 一篇现实选题 → 一个 Task Packet | 六件套（你从「没印象」到亲手写进自己的方案） |
| 一次独立审计 | 验证层（王自如 validation + 四步验收） |
| 用户发布 → T+7 反馈 | 真实回执（欣烨：没有真回执的自动运行是噪音） |
| 提炼一条规则 | 恒的四步第 2 步 |
| 下一篇验证 | 恒的四步第 4 步 |
| 经验库三层（观察 / 教训 / 策略） | 观察层 = experience-log；教训层 = 米罗的 memory 沉淀；策略层 = 带验证日期的规则库 |

这套设计比课程里任何一位讲者给的都完整。特别是「每圈只提炼 1 条可验证规则、下一篇真实文章再验证它」——这就是把恒的四步从「随便写」收紧成「写一条、验一条」。

### RSI 的断点，就是你的飞轮的断点

内参那篇的结论：工程满分、研究不及格。agent 能跑完全部工程（综述、实验、汇总），但两篇论文都被原作者拒了。失败的四个具体形态，搬到内容生产里一个不差：

| RSI 失败形态 | 内容生产的同款 |
|---|---|
| 过早承诺 | 选题过早锁定，数据不行还硬写 |
| 有好假设守不住 | 一个好角度被第一版差数据否定 |
| 无法回溯 | 只做小幅微调，换不了整体路线 |
| 不吸收反馈 | 把反馈当噪声，缩小主张、加限定条件 |

你飞轮里的两道关卡正好压住其中两个：**独立审计**压「不吸收反馈」，**T+7 真实反馈**压「守不住好假设」——差数据由真实读者来判，而不是模型自己否自己。剩下两个（过早承诺、无法回溯）没有机制压得住，它们落在人身上：选题判断和路线决策。这就是内参说的「判断力与品味」的位置：可判分与开放的分界线，放在你的系统里，就是选题和发布。

### 三条死守、三条放手

给你的飞轮划一条边界，按「验证信号可判分吗」分：

**死守（人验收，系统只给建议）：**

1. 选题。判断「什么现实新现象值得用树林框架判断」——开放问题，没有评分函数。
2. 发布。文章以你的名义见人，责任在你，不在 agent。
3. 策略层入库。一条规则要进「已验证有效」那层，必须由你确认它真的在下一篇里证明了——坏规则会带偏后面每一篇。

**放手（系统自迭代）：**

1. 观察层记录（experience-log 自动写）；
2. 教训层提炼（跨任务错误模式）；
3. 初稿生产（在 Task Packet 和审计的框架内）。

你的「减法」清单（砍第一版主线、砍无反馈批量生产、砍未证明架构）本质上是同一条边界提前生效：**没有可判分验证信号的东西，暂不进入主线。** 你已经在用 RSI 断点的结论做减法了。

### 今日最小动作

1. 把 `docs/writing-system-flywheel.md` 从你的工作区拷进本工作目录（这里还没见到它），08 收尾会引用。
2. 用「三条死守 / 三条放手」对照你的飞轮，标出哪一环节还没有明确写「人验收」——大概率是策略层入库那一条。
3. 给策略层补一个最小格式，你其实已经写出了大半：适用条件 + 动作 + 证据 + 最近验证日期。再补上「由谁验证」一行。

## 小结

1. 作业 05 三件交付物齐了；你的建议超规格——是一套最小闭环。
2. description 有两个职责：触发和守门；窄了 undertrigger，宽了误触烧 token。
3. 你的飞轮和课程机器逐件对应，且更完整；「每圈一条规则、下一篇验证」是恒四步的收紧版。
4. RSI 四个失败形态在内容生产里一个不差；审计和 T+7 反馈压住两个，选题和路线决策是人的判断力位置。
5. 边界按验证信号分：选题、发布、策略层入库死守；观察记录、教训提炼、初稿生产放手。
