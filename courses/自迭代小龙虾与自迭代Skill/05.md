### 先接住你的反馈

### 王自如的三句话，把 skill 的家谱补全

王自如的原话三句：

1. Skill 的本质 = 渐进式披露的 prompt + 运行脚本，没工具它什么都干不了。
2. Skill 只能做一定程度的编排和精细化适配，稳定产出需要结构化数据——「结构化数据 is everything」。
3. 好的 skill 四部分 = MD 文档 + 运行脚本 + 工具链 + 验证机制，结尾一定要 validation，agent 要写库、落库。

和 04 的四部件对照：

| 04 的四部件 | 王自如的四部分 | 关系 |
|---|---|---|
| front-matter / 触发 / 流程 | MD 文档 | 同一件事：文本层 |
| —— | 运行脚本 | 04 没讲，文本之外的可执行件 |
| —— | 工具链 | 04 没讲，干活的手 |
| 验证钩子 | 验证机制 | 同一件事 |
| 车险 skill 里提过的数据 | 他反复强调的结构化数据 | 数据层 |

他的四部分是「一个完整 skill pack」，04 的四部件是「文本内部的四段」。合起来是一个 skill 的完整家谱：文本（front-matter / 触发 / 流程）+ 脚本 + 工具 + 验证 + 数据。dbs-learning 是纯文本型（没有自己的脚本工具）；车险 skill 是数据重型（大半价值在数据）；配上 Brave API 才有的「每天早报」skill 是工具型。三条都对，只是重心不同。

### description 和 size gate：两道门，各管一次过滤

系统在你和 skill 之间设了两道门。用具体例子讲：

**第一道门：description（触发匹配）。** 你发「下一篇」，系统拿这三个字去和每个 skill 的 description 比对。dbs-learning 的 description 里写着触发词「下一篇」「继续学」，命中，于是把这个 skill 的全文注入上下文。aihot 的 description 里写着「AI 日报」「今天 AI 圈有什么」，这次不命中，就不加载。一个词决定加载与否——所以触发词写得窄（case study 只在小红书截图时来），省 token 也少误触。这就是你 04 总结的「隐性匹配、隐性调用」。

**第二道门：size gate（体量过滤）。** 上下文是稀缺资源，harness 对「太大」的东西设门：

- 例一：一百个 skill 不会在启动时全塞进来，只有 description 进上下文，正文用到才展开。这是渐进式披露。
- 例二：搜索返回 2 万字，harness 只留头部和尾部各几百 token，全文卸载到文件，模型需要再读。这是工具输出卸载。
- 例三：王自如的「1 万个文档」——规模大到一定程度，这道门就变成检索：把文档向量化，每次只抓和当前对话最相关的那一两句。你在知识库课学的语义检索 + 重排序，就是大号的 size gate。

王自如的原话收在这里：「skill 的逻辑就是在最恰当的时间给最正确的信息。一个文档很好驾驭，一万个文档的时候怎么驾驭？」——这题你已经会一半了，知识库课就是答案。

### 恒的四步：把「改自己」写进 skill 流程

现在到今天的正题。恒在直播里给过一个可以直接抄进 skill 的模板：

1. 执行完成后，回顾本次的输入、过程、结果；
2. 提取 1-2 条可复用的经验（什么有效、什么无效）；
3. 将经验追加到 experience-log.md；
4. 下次执行前，先读 experience-log.md，根据历史经验调整策略。

四步里有三步是「写和读文件」。为什么文件这么重要？回到 01 的公式：模型除了权重和当前上下文，没有别的知识。想给它加知识，唯一的途径是 context injection（把东西塞进上下文）。经验不落文件，下次执行就是从头再来；落进文件、下次先读，经验才算真的进了它的脑子。

金融小龙虾的经验库就是这套模板跑出来的产物，每条都是「某次比赛失误 → 提炼教训 → 写进库 → 下次先读」：

- 冲高不追；开赛首日太保守，40% 现金在短赛是浪费；开盘 30 分钟不追涨；分布建仓；下跌途中不接盘；板块轮动要快。
- 止损网 = 复利连续性；财报日历铁律；周末 gap 预案。
- 超长 prompt 会导致超时 error，任务根本没法执行。
- Success 不等于执行。
- 想记住的必须写文件，session 重启不丢；每个对话先优先读 soul / user / memory 再干活；心跳别只回 OK。

注意最后三条：它们不是交易经验，是「怎么当一只好虾」的经验——恒的虾连「管理自己」的经验都在自迭代。

### 口子放哪，以及两个风险

位置：放在流程正文的倒数第二步——干完活、验收之前。先回顾写日志，再过验证钩子。这样每次执行都以「把经验交回」结尾，然后才判对错。

这个口子有两个风险，各配一句对策：

1. **日志长成垃圾场。** 每条都写、越写越长，超过一定长度还要超时——恒的经验库自己就记着这条。对策：王自如的 validation + 恒的「prompt 要精简」——限制每次只写 1-2 条，过期条目定期合并。
2. **坏经验被当成好经验。** 一次偶然失败总结出的「教训」可能是个案，写进库会带偏下次。对策：判定权在验证层，也就是王自如说的「结尾一定要 validation」、你说的 DBS 正反例——写库前先过一道「这条可复用吗」的判据。

这两个风险就是下一篇动手时你要亲手处理的，也是第三阶段「边界」的主题。

## 小结

1. 王自如的 skill pack 四部分（MD 文档 / 脚本 / 工具链 / 验证机制）和 04 的文本四部件合起来，是一个 skill 的完整家谱；文本、脚本、工具、验证、数据，重心因 skill 而异。
2. 两道门：description 管「该不该来」（触发匹配），size gate 管「该带多少」（渐进式披露、工具输出卸载、检索）。
3. 恒的四步 = 回顾 → 提取 1-2 条 → 追加 experience-log.md → 下次先读；原理是模型唯一的加知识途径是 context injection。
4. 口子放流程倒数第二步：干完活先写日志再验收；两个风险是日志垃圾场和坏经验入库，各配一条对策。
5. 你 04 的总结基本全对；DBS 3 正 2 反就是「什么算对 / 算错」的最小样本集。
