### 你问的：触发匹配和隐式触发的区别

先把三种进入方式分开，再放两道门。

**显式点名。** 你直接说 skill 名或打斜杠命令，比如 `/dbs-learning`。系统不匹配，直接加载。用户全程知道自己在叫谁。

**触发匹配。** 第一道门的机制本身：系统拿你的消息去和每个 skill 的 description 比对，命中才加载，不命中就不动。你在 05 见过它的例子：「下一篇」命中 dbs-learning 的触发词，不命中 aihot。

**隐式触发。** 触发匹配命中的一种来源：你既没点名、也没说触发词，但 description 里写了意图描述，匹配器靠语义把你接住。你在本会话顶部就能看见实例——aihot 的 description 明说「即使用户只说『AI 圈』『AI 新闻』，或者只是问『今天发生了什么』且上下文是 AI……也应该触发本 Skill。不要 undertrigger」。这句话的存在就是为了让你随口一句「今天 AI 圈有啥」也能被接住。dbs-learning 的「触发信号」一节同理。

所以区别一句话：**隐式触发和显式点名是「怎么进来的」两种来源，触发匹配是「进门的那道检查」。** 隐式触发是触发匹配的一种命中来源，显式点名干脆绕过匹配。

再看你 05 的猜测：「命中了什么样的关键词，然后 Context Gate 做渐进式披露」——这里混进了两道门，拆开：

| 门 | 回答的问题 | 发生在 |
|---|---|---|
| 第一道门：触发匹配 | 该不该来 | 你发消息的瞬间，description 比对 |
| 第二道门：size gate（你说的 Context Gate） | 该带多少 | 匹配之后：正文按需展开、大段输出卸载、一万文档变检索 |

关键词命中只是第一道门的一种匹配来源；意图语义命中是另一种（隐式触发）。两道门顺序独立：先匹配决定来不来，来了之后 size gate 决定带多少。王自如那句「渐进式披露」就是第二道门的标准操作。

### 殊途同归：把它讲成一条原理

你说「很多东西都是殊途同归的」，这个观察是对的，它背后有一条原理。

回到 01 的公式：模型的知识只有两处——权重和当前上下文。上下文稀缺、还会腐坏。所以你见过的所有机制，全在解同一道题：**在正确的时间把正确的信息放进上下文。**

- 触发匹配：决定「哪个 skill 的信息」放进来；
- size gate：决定「放多少」；
- 记忆检索：一万个文档版本的 size gate；
- 经验日志：把「这次学到的」变成「下次的上下文」。

王自如那句话就是这道题的总称：「在最恰当的时间给最正确的信息」。机制们长得不一样，因为它们对付的是同一道题的不同规模。

更具体的一层：Meyo 帖子说的三层（项目级独立 session / 角色级按需注入 / 里程碑快照），和你写进 experience-log 的经验（独立 session / 按需注入 / 快照 / 人工验收）几乎逐条重合。再把欣烨的 7 次超时案例放进来——他的失败是隔离过度（任务需要原对话上下文，却被放进了读不到它的会话），Meyo 帖子的痛点是隔离不足（8 个项目共享一份膨胀的上下文）。两个方向合起来，就是你的 log 里那句「先隔离、按需注入」。你提取的这条经验比两边的原始案例都完整，这正是四步模板的价值：它让你把两个方向的教训合成了一条规则。

### 可选收尾动作：把四行模板安进一个长期 skill

你在工作区跑过四步模板，但它还是一次性的复盘，没变成「以后每次都执行」的流程。收尾动作是：挑一个你会反复用的 skill，把四行抄进它流程的倒数第二步（干完活、验收之前）：

```text
1. 执行完成后，回顾本次的输入、过程、结果；
2. 提取 1-2 条可复用的经验（什么有效、什么无效）；
3. 将经验追加到 experience-log.md；
4. 下次执行前，先读 experience-log.md，根据历史经验调整策略。
```

候选我建议选 dbs-learning：你正用它，它的「反馈摘要」表本来就是雏形，加上四行，以后每篇生成完会自动把反馈沉淀进计划。配两条纪律：每次只写 1-2 条；写进去之前先让人过目一眼。

1. 输出窗口

2. 减法
我建议砍三件事：
