# 研究：ai-native-helpdesk 验证钩子留痕实现（背景输入 v0.1）

> 用途：迭代候选 ② 的研究底稿，作为聊天室讨论的背景输入。状态：研究稿，未动 skill。

## 一、现状（证据）

- 对话宪法 #6 要求每条回答结尾给 1 句验证信号；#8 定义完成标准。
- 6 个子 skill 全部含 validation 语言（本轮 grep 实测）。
- 但没有任何运行回执/留痕机制：验证信号发出后无记录、无回程，产品级验证状态自称 UNKNOWN（front-matter 原文）。
- 结论：验证钩子是「开环」的——有输出端，没有把输出接回输入端。

## 二、四个候选方案（含各自的可证伪点）

| 方案 | 做法 | 优点 | 代价 | 可证伪点（什么观察能证明它失效） |
|---|---|---|---|---|
| A 每任务回执日志文件 | 每次处理完写一个回执文件 | 痕迹最全 | 违背薄入口定位；文件噪音；每次写文件本身要过 artifact gate | 日志与对话内实际验证信号对不上 |
| B 对话内自证 | 验证信号与判模依据留在对话里 | 零新增产物 | 跨会话不持久，回路每轮断一次 | 会话结束后查无痕迹（天然可证伪，且必伪） |
| C 最小回执账本 | 3 个计数器：路由次数 / 验证信号次数 / 用户确认次数，任务末尾更新 | 薄；偏差 = 路由−验证−确认，一眼可见 | 只显示偏差、不校正 | 账本计数与对话回放对不上 |
| D 抽样回放测试 | N 条测试消息定期回放，测判模命中率 | 直接测路由质量；可进 CI | 需要维护测试集 | 回放命中率跌破阈值 |

## 三、初步研究判断

- A 先否：该 skill 自己的 artifact gate（薄入口、够用即停）会先毙掉它。
- B 不是方案，是现状的描述——它已经存在，问题正是它不持久。
- C 是「账本」（观察层），D 是「执行」（校正层）：C 记录偏差，D 把命中率喂回判模。两者合起来才闭环。
- 留痕本身要遵守它自己的对话宪法：只测能改变决策的变量，别做成第二个行数规范。

## 四、与元Skill 流程的关系

留痕实现若通过裁决，进入迭代流程：一条窄假设（加 C 计数器）→ 候选 SKILL.md v1.3 草案 → 盲测（回放测试对账本）→ 用户批准替换或回滚。
