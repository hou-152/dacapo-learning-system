### skill 是什么：先给它一个小的定义

Skill 是一份「程序化知识文本」：告诉 agent 什么时候来、来了干什么、干成什么样算对。它没有代码那么重——大多数 skill 就是一个 markdown 文件，几百行字。你在这个会话顶部就能看见一个活样本：dbs-learning 的完整内容（触发信号、工作流程、文件存放规则、验收用例）。现在翻回去看它一眼，下面每拆一个部件，都拿它对。

### 四个部件

**部件一：front-matter。** skill 文件最开头那段 YAML 头（key: value 那种格式），管三件小事：这个 skill 叫什么（name）、什么情况下该加载（description，里面写触发词）、它是什么。系统在你发消息时拿 description 去匹配你的话，匹配上了才把 skill 塞进上下文。你反馈里说的 First Matter 就是这个词。

**部件二：触发规则。** description 里的触发词 + 载入时机。比如 dbs-learning 的触发词是「带我学一个主题」「下一篇」「继续学」，出现学习意图时进入。米罗的 case study skill 触发词更窄：上传小红书帖子、或者帖子加评论区的截图。窄触发是好事——省 token，也少误触发。

**部件三：流程正文。** 来了之后按什么步骤干活、守什么边界、输出什么口径。dbs-learning 的流程就是「确认课题 → 读取已有进度 → 判断梯度 → 生成文章 → 更新计划」那几段。米罗的车险反套路 skill 流程：从沉淀的车险避坑数据里找到对应情形，一步步列出反套路。

**部件四：验证钩子。** 干完怎么算对。dbs-learning 里的「验收用例」就是这一层；你 ITERATION-HARNESS 里的 success_gate 也是。多数 skill 缺这一层——缺了它，改没改对、跑没跑好都没有判据，进化就无从谈起。

一张表收住：

| 部件 | 回答的问题 | dbs-learning 里的样子 |
|---|---|---|
| front-matter | 我是谁、何时被叫来 | 头部 YAML（name / description） |
| 触发规则 | 什么话会叫我 | 「触发信号」一节 |
| 流程正文 | 来了干什么 | 「工作流程」「文件存放规则」 |
| 验证钩子 | 怎么算干对 | 「验收用例」一节 |

### 用米罗的两个 skill 验证这套拆法

**车险反套路 skill。** 米罗先上视频网站征集了一堆车险避坑指南，写进 skill 的「数据」；真出事故时，skill 从数据里找到对应情形，一步步列反套路。拆开看：触发 = 出险理赔；流程 = 查数据 + 列反套路；数据 = 他征集的车险避坑。这个 skill 的价值大半在数据里，skill 本身只是个调用器。

**case study skill。** 触发 = 上传小红书帖子截图；流程 = 分析案例 + 推导遇到类似情况的正确处理办法；产物 = 按孩子年龄段积累的案例库。米罗的理由很实在：这些案例孩子可能十几岁才遇到，自己现在看完很快就会忘，所以存给虾，以后系统性提取。

两个样本说明同一件事：skill 不神秘，它就是把「什么时候来、来了干什么、怎么算对」写清楚的一份文本。**skill 自己不会进化**——它会一成不变地重复同一套流程，直到有人改它，或者它被允许改自己。

### 给下一课埋一个口子

## 小结

1. Skill = 一份「什么时候来、来了干什么、怎么算对」的程序化知识文本，多数就是一个 markdown 文件。
2. 四个部件：front-matter（头部 YAML）、触发规则（触发词）、流程正文（步骤边界口径）、验证钩子（验收用例）。
3. 米罗的两个 skill 验证了拆法；车险 skill 的价值大半在数据，case study skill 的价值在案例库。
4. Skill 自己不会进化；进化靠回写口子，大多数 skill 没留这个口子。
5. 你的任务已建好且比要求更严；到点按第三、四步验收，回执贴进反馈。
