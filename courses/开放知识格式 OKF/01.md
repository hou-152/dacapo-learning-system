01｜为什么 AI agent 需要一种知识格式
========================


这一篇要解决的问题
---------


这篇先解决一个基础问题：OKF 这类东西为什么有价值。先把问题看清楚，再进入格式细节，后面读 YAML、Markdown 目录、概念文件时才有抓手。


正文
--


Google Cloud 这篇文章的核心场景很具体：基础模型能力越来越强，但 agent 在真实组织里工作时，经常卡在上下文上。


一个 agent 想回答“如何从事件流里计算每周活跃用户数”，它光有模型能力还不够。它还要知道很多组织内部知识：


* 哪张表记录事件流；
* 字段含义是什么；
* 哪些事件算活跃；
* 指标口径由哪个团队维护；
* 上游系统有没有弃用字段；
* 过去的运行手册里有没有处理异常数据的规则。


这些知识常常散在多个地方：数据目录、团队 wiki、共享云盘、代码注释、Notebook、资深工程师的脑子。每个地方有自己的入口、权限、字段、搜索方式和导出方式。agent 要做一次可靠判断，就要临时把这些碎片拼起来。


这里出现了第一个问题：上下文组装变成重复劳动。


同一个团队可能会为客服 agent、数据分析 agent、编码 agent、运营分析 agent 分别整理一遍“指标口径”“表结构”“API 关系”“运行手册”。每个项目都重新接一堆源系统，每个供应商也都在做自己的目录、知识图谱和 SDK。知识本身被锁在产生它的工具里，迁移到另一个 agent 项目时，又要重来。


OKF 想解决的就是这个重复问题。它提出一个很轻的约定：把知识整理成一个 Markdown 文件目录，每个概念一个文件，再加少量 YAML 前置元数据。这样一来，人能读，agent 也能读；文件能放进 Git，也能打包分发；不同工具可以围绕同一批文件做生产、浏览、搜索和推理。


可以把 OKF 暂时理解成一种“给 agent 用的知识包格式”。


这里的“格式”很关键。一个平台会要求你进入它的账号体系、API、权限模型和数据模型。一个格式只规定文件长什么样、哪些字段有共同含义、链接如何表达关系。生产者和消费者就能分开演化：


* 数据团队可以写一个导出脚本，把 BigQuery 表、视图、指标口径生成 OKF 文件；
* 文档团队可以手工维护关键概念；
* agent 可以读取这些文件回答问题；
* 可视化工具可以把这些文件渲染成知识图谱；
* 另一个组织也可以拿同一套文件做自己的检索或治理。


文章里提到的 LLM wiki 模式也很值得注意。很多团队已经在做类似事情：给编码 agent 准备 AGENTS.md 或 CLAUDE.md，把项目背景、约定、日志、索引写进仓库；有人用 Obsidian、Notion、Git repo 存项目知识；也有人把数据目录变成“元数据即代码”。这些实践都在靠文件组织上下文。


它们的问题在于缺少共同约定。大家都在写 Markdown，都在加元数据，也都在做链接，但字段名、文件名、目录结构和语义边界各不相同。一个团队的 wiki 到另一个工具里，通常还要重新解释。OKF v0.1 的意义，就是把这类实践里最小的一层接口固定下来。


第一篇先记住一个判断：


当 agent 的能力受限于“找不到正确上下文”时，继续堆模型能力通常收效有限。更直接的动作，是把高频、稳定、可复用的组织知识整理成可读、可迁移、可链接、可版本管理的文件包。


这也是 OKF 和普通文档整理的区别。普通文档多半服务人的阅读；OKF 风格的知识包同时服务人的维护和 agent 的消费。它要求每个知识点有稳定位置，有少量结构化字段，有清楚链接，有可追踪变更。这样 agent 后续读到的不再是一堆散乱网页，而是一组可以逐步浏览、交叉引用、持续更新的知识文件。


这件事对你的学习价值在于：以后你看到任何“AI 知识库”“企业知识图谱”“agent memory”“项目上下文工程”方案时，都可以先问 4 个问题：


1. 这批知识能不能脱离平台独立存在？
2. 人和 agent 能不能读同一份内容？
3. 知识之间的关系能不能用普通链接表达？
4. 更新历史和责任边界能不能被版本管理？


如果答案都很弱，这个方案可能只是把知识搬进了另一个封闭系统。答案越强，它越接近 OKF 文章想推动的方向：知识先成为开放格式，再被不同工具消费。


小结
--


1. AI agent 在组织里经常受限于上下文，而上下文通常散在数据目录、wiki、代码、文档和人的经验里。
2. 重复组装上下文会让每个 agent 项目都重新劳动，也让知识被锁在原工具里。
3. OKF 的基本主张是用 Markdown 目录和少量 YAML 元数据承载知识，让人和 agent 读同一份文件。
4. 格式的价值在于降低迁移成本，让生产者、消费者和可视化工具可以围绕同一批知识文件协作。
5. 读 OKF 时先抓住“可迁移的上下文包”这个判断，再去看字段和规范细节。
