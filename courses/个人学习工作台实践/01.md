# 01｜一条反馈怎样走完到下一篇的路

## 这一篇要解决的问题

这一篇接住你在原课 04、05、07 留下的三个问题：对话里说出的反馈为什么没有自动回填；log 那套东西为什么早就没用了，默认设置为什么没有走通，token 反而被占用；Agent loop 的形态到底该怎么使用，多模型之间怎么调用与调动，多 Agent 之间怎么协调。

处理方式是把一条反馈从「说出来」到「进入下一篇」拆成六个站点，逐个标出输入、产物、判断方和失败表现。看完这张站点表，你能直接定位默认回路卡在哪一站，也能判断哪些环节适合交给程序，哪些环节适合留在人这一侧。

## 正文

### 先处理一个前提：那条约束还没有被证伪

你在 04 里提到，之前的约束形成于你赶 DDL 的情况下，能否被证伪还没有验证。01 把它当作当前设计输入，不写成已验证结论。

站点表按「假设约束成立」推演。如果约束后来被证伪，受影响的站点主要是归属和清洗，因为这两站决定一条反馈按什么规则进入课程。证伪检查放到后面的文章，不在这一篇里下结论。

### 一条反馈的六个站点

先拿一条假设反馈来走流程，只为让每一站的输入和输出都能看见：

> 这个概念我没看懂，它和上一节的例子对不上。

这条反馈要进入下一篇，会依次经过六站：

| 站点 | 输入 | 产物 | 主要判断方 | 失败表现 |
|---|---|---|---|---|
| 捕获 | 对话、文档、语音转写 | 待处理项，带来源 | 程序扫描 | 反馈留在聊天记录里，扫描不到 |
| 归属 | 待处理项 | course / lesson 绑定 | 程序；用户确认 | 知道有反馈，但不知道放进哪一课 |
| 清洗 | 原话与上下文 | 清洗记录：溯源、对照、矛盾点 | 模型辅助；用户确认 | 引用材料和用户原话混在一起 |
| 入课 | 清洗记录 | 已回填反馈 | 程序 | 队列里有，文章或反馈库没有 |
| 取用 | 未处理项、疑问卡 | 下一篇生成输入 | 生成 Agent | 下一篇重复上一版，没有接住反馈 |
| 结清 | 疑问与触发条件 | 已结清，或继续待触发 | 用户确认 | 疑问只有标题，没有依据可关闭 |

六个站点里，程序能稳定承担的是搬运和对照：扫描入口、写入待处理、按绑定归课、把未处理项拼进生成输入。需要判断的是归属是否成立、清洗是否失真、疑问是否具备结清依据。你提到自动化很多东西没法铺开。按站点看，能铺开的是规则稳定的搬运和对照；判断环节每换一个情境就要重新看一次，铺开成本高。

05 里你提到的四个最小动作——判断中间产物、生成数据、占位学习、反馈区——可以先放进这张表里逐项对应；具体对应关系放到 02，因为要先确定每一站的职责边界。

### 为什么 log 留痕，却推不动下一步

日志按时间追加，回答「发生过什么」。工作台每次生成前要回答「哪一条还没处理、它属于哪里、下一步等什么」。这两个问题的形状不同。

日志越长，重新判断的成本越高。全量重读时，已经处理完的项也在里面，token 花在重复阅读和重新分类上。带状态的队列只让未完成项进入生成输入；处理完的项留在记录里，不参与下一轮判断。

举个例子。队列里有一条记录：

- course：个人学习工作台实践
- lesson：01
- status：待处理
- source：某次对话的定位

生成 02 前，程序只取 status=待处理 的项，加上相关疑问卡，拼成生成输入。日志式做法要先把过去所有记录读一遍，再猜哪些是新的。前者每轮只读增量；后者每轮读全量。token 的差别就出在这里。

日志仍然适合审计和回溯，也适合保存原话。推进下一步需要的是状态。你提到之前关于 log 的判断是很多东西会被遗忘、没有越用越好；如果把状态队列接上，已处理项不会被反复喂给模型，未处理项也不会因为翻不到而消失。

### 默认回填需要三个条件同时成立

你说的默认设置没有生效，可以拆成三个条件来检查：

1. 入口被调用。每次生成下一篇前，真的运行了 scan 和 process。没有这一步，收件箱里有什么都不会进入判断。
2. 绑定存在。反馈或对话带有课程、篇目或明确来源。绑定缺失时，程序把它留在待处理，避免凭语义相似度猜篇。
3. 生成前读取。生成 Agent 的输入里包含已回填反馈、疑问卡和反馈上下文。

三个条件里任何一条不成立，默认行为就不会发生。检查默认回路时，按这三条逐项看，比讨论「它为什么不智能」更快。

回到你问的「会不会帮我回填到学习反馈里面去」。带来源定位的逐字回填可以由程序写入。归属不清的反馈保留待处理，等一次明确选择。这样处理能避免两种错误：把别的课的反馈写进这一课；把材料里的第一人称当成用户履历。归属不清的项会停在待处理，等你给一次判篇输入；其余环节可以自动走。

### 无限画布和 Obsidian 形态放在这条链路的哪里

你在 05 里提到，要的形态更接近无限画布加 Obsidian，或者一个 AI 插件、Plugin。把六个站点映射到画布，先得到三样东西：

- 节点：反馈、文章、疑问。
- 连线：反馈属于哪一课；疑问由哪条反馈触发；依据解决哪个疑问。
- 状态：待处理、已回填、待触发、已结清。

你说自己交互式学习的课大概有 60% 甚至 70%、80% 后面没再翻过，打不打开取决于后面有没有产生新疑问；资料还在，疑问往往找不到。画布能处理的是「疑问找不到」这一段：疑问作为节点一直存在，触发条件写在节点上；新的交互满足条件时，疑问重新进入视野。当疑问重新出现，课程有了被打开的理由。目录提醒提供的是另一种入口。

你在 04 里提到，词汇表可以承担溯源、补充上下文和矛盾清洗，手写笔记存下来可以当链路图。两者可以放在画布旁边：词汇表服务清洗站，链路图服务归属站和取用站。内驱力那一层很难用程序解决；目前能挑的是 A 问题和 B 问题直接相连的疑问，先把这类疑问做成可见节点。具体前端交互和可视化实现放到后面的文章，01 先确定节点、连线、状态三件套。

### 多模型与多 Agent：先按站点分工

你问的是多模型之间怎么调用与调动，多 Agent 之间怎么协调。一个可检查的起点是按站点分配角色，让每个角色有明确的输入和输出。

| 站点 | 需要的能力 | 可以交给谁 | 输出物 |
|---|---|---|---|
| 捕获 | 读对话、文档、语音转写 | 程序加模型 | 待处理项，含来源 |
| 归属 | 访问课程目录，判断绑定 | 程序；模型辅助 | course / lesson，或保留待处理 |
| 清洗 | 长上下文、对照、溯源 | 模型加人确认 | 清洗记录 |
| 生成 | 教学写作，接住反馈 | 模型 | 下一篇草稿 |
| 校验 | 读输入与产出，查漏 | 另一个模型或人 | 通过或退回意见 |
| 结清 | 判断触发条件与依据 | 人确认 | 已结清或继续待触发 |

协调的最小要求：每个角色的交接物落在磁盘上，包含来源、状态和下一步。换模型、换 Agent、重跑时，后来者读文件就能接上，不必翻对话记忆。你提到可以让新模型 jev 辅助判断；它放在归属、清洗或校验站点都可以，产物要落成同样的记录。

你在 05 里说自己更倾向于「事事都知道」这个方向，先 just do it、try。这个选择可以直接用在闭环跑通上：先让一条反馈走完六个站点，记录每一站的输入输出，再决定哪一站换模型、哪一站加 Agent。这样每换一次都有对照。原生 App、软件加 App、AI 插件之间的选型，以及 GitHub 上开源项目的具体采用，放到闭环跑通之后。你说过有些开源项目完成度可能更高，该用就用；选型比较需要一张能跑的最小回路作为参照。ELI5 这类轻量 Skill 也一样，先看它服务哪个站点，再决定是否接进默认链路。

### 阅读留在人这一侧

你在 07 里说，写、编代码这类事情可以外包出去；如果自己坚持做，就要跟 AI 聊清楚，交互式学习的反馈必须要有。你还说，不应该外包的其实是阅读。按站点看，扫描、搬运、对照、生成草稿可以交给程序；阅读、判断和反馈留在人这一侧。

这条分工和「事事都知道」并不冲突。程序可以把该知道的都摆在画布上，阅读和取舍仍然由你完成。你说过这个工作台本身就是一个实践过程，不介意它做出什么代码，有就改，交互学习的记录都在；记录在，替换实现时就不必从头解释。

你提到想把这条链路接到 DBS 的 content-system 和内容工厂，做成费曼闭环产出。接入内容系统要等站点和交接物稳定下来；01 先把捕获、清洗、取用、结清定义清楚。

### 怎么检查默认回路在跑

下次生成下一篇前，看三个点：

1. 收件箱里有没有带来源的新反馈。没有，说明捕获没发生。
2. 这些反馈有没有绑定课程和篇目。没有，说明归属停在待处理。
3. 生成输入里有没有它们，以及相关疑问卡。没有，说明取用没发生。

三个点都通过，默认回路就在运行。任何一点没通过，问题就定位到对应站点，讨论范围可以缩到那一站。

## 小结

1. 一条反馈到下一篇要经过捕获、归属、清洗、入课、取用、结清六站；每站都有输入、产物、判断方和失败表现。
2. log 适合留痕和审计，状态队列负责推进下一步。只让未处理项进入生成输入，token 花在增量上。
3. 默认回填需要三个条件同时成立：入口被调用、绑定存在、生成前读取未处理项和疑问卡。
4. 无限画布加 Obsidian 的形态先承载节点、连线和状态，解决「疑问找不到」这一段；前端实现和选型放到后面。
5. 多模型和多 Agent 可以先按站点分工，交接物落在磁盘上；jev 这类新模型放在判断站点时，也要产出可检查记录。
6. 阅读、判断和反馈留在人这一侧；扫描、搬运、对照和草稿交给程序。
