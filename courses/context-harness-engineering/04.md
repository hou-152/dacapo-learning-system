## 正文

### 双文件约定

先把最简单的部分定下来：

```text
project/
├── AGENTS.md    # 真源
└── CLAUDE.md    # 一句话：本项目以 AGENTS.md 为准，请先读 AGENTS.md
```

`CLAUDE.md` 只写那一句。这样 Claude Code 和 Codex 读的是同一份东西。

理由是防漂移。如果两份文件都写实质内容，它们一开始可能一致，三周之后一定不一致——你改了一份，忘了另一份。到那时你有两个真源，也就是没有真源。

---

### AGENTS.md 是索引，不是仓库

官方那篇里点破了一个很常见的误解：

> 「A common myth is that you want to make these a central repository for every known practice.」

推荐的形状是另一种：**a tree of files loaded at the right time**——一棵在正确时机被加载的文件树。

这句话里的重点在 *at the right time*。把所有实践堆进一个常驻文件，等于让每一次请求都背着全部内容跑，包括这次完全用不到的部分。

背后的假设是「不常驻就等于不存在」。这个假设不成立——agent 会读文件，它只是需要知道去哪里读。而「去哪里读」这件事，正是 AGENTS.md 该干的活。

所以 AGENTS.md 的职责就两条：

1. 说清这个项目是什么
2. 说清什么问题去哪个文件找答案

---

### 三分法：留、搬、删

03 给的单行测试是一维的：*少了这一行，一个强模型会表现得更差吗？* 通不过就删。

落地的时候还需要第二个维度：**这件事是不是每次都要用？**

两个维度交叉，得到一张判断表：

| | 每次都要用 | 偶尔才用 |
|---|---|---|
| **强模型推不出来** | **留**在 AGENTS.md | **搬**到 docs/ 或 skill，在索引里留个指针 |
| **强模型自己会** | **删** | **删** |

多数人的 AGENTS.md 臃肿，问题出在右上格——那些确实有用、但一次任务里用不到的东西，被塞进了常驻位置。它们不该删，该搬。

删和搬是两件不同的事。03 里那条警告就是这么来的：有人删掉一条看起来像样板文字的 build 注意事项，后来某次会话又痛苦地重新踩了一遍那个坑。那条本该搬，不该删。

举例说明四个格子：

- **留**：「本项目所有文案用中文，代码标识符用英文」——模型推不出来，每次写东西都要用。
- **搬**：「部署流程的六个步骤」——模型推不出来，但只在部署那次任务里需要。进 `docs/deploy.md`。
- **删**：「请写出高质量、可维护的代码」——模型本来就在做。
- **删**：「你是一位资深工程师」——人设不影响这一代模型的行为。

### 一个 before / after

假设原来的 AGENTS.md 里有这么一段：

```markdown
## 开发规范

- 请务必编写清晰、可读、可维护的代码
- 重要：所有函数都要有适当的错误处理
- 请遵循项目现有的代码风格
- 提交前请检查代码是否正确
- 数据库连接串在环境变量 DB_URL 里
- 部署要先跑 npm run build，然后 wrangler deploy，注意 wrangler 版本必须 3.x，
  4.x 会报一个很难看懂的错
- 这个项目用 pnpm，不要用 npm install
```

逐行过一遍那两个问题：

| 原文 | 判断 | 处理 |
|---|---|---|
| 写清晰可维护的代码 | 模型自己会 | 删 |
| 函数要有错误处理 | 模型自己会 | 删 |
| 遵循现有代码风格 | 模型自己会 | 删 |
| 提交前检查代码是否正确 | 模型自己会，而且这类叮嘱会引起过度验证 | 删 |
| `DB_URL` | 推不出来，经常用到 | 留 |
| wrangler 必须 3.x | 推不出来，只在部署时用 | 搬到 `docs/deploy.md` |
| 用 pnpm 不用 npm | 推不出来，经常用到 | 留 |

改完：

```markdown
## 关键事实

- 包管理器：pnpm（不要用 npm install）
- 数据库连接串：环境变量 `DB_URL`

## 去哪里找

- 部署：`docs/deploy.md`（有个 wrangler 版本的坑）
```

七行变五行，但真正的变化不在行数——是每一行都通过了那个测试，而且被搬走的那条坑还在，只是换了位置，并且索引里留了钩子。

行数不是目标。03 里那句话在这里再说一遍，因为落地的时候最容易忘。

### 文档树按什么拆

一个容易走偏的做法是按知识分类拆：前端、后端、数据库、运维。分类整齐，但用起来别扭——agent 做一次任务，往往要在三个文件之间跳。

换一个拆法：**按「一次任务需要什么」拆。**

```text
docs/
├── roadmap.md      # 现在做到哪、接下来做什么
├── tech-stack.md   # 用了什么、为什么这么选
├── deploy.md       # 部署这件事的全部
└── modules/
    ├── auth.md     # 认证这块的全部
    └── billing.md  # 计费这块的全部
```

粒度的判据：**一个文件回答一类问题。** agent 要部署，读 `deploy.md` 就够，不用再跳三个地方。

这个拆法也让 Single Source of Truth 更容易维持——因为「部署」这个话题有且只有一个归属文件，你想把它写到别处时会先意识到不对。

### Single Source of Truth 怎么建

02 给过那个自检问题：

> 关于「这个项目怎么部署」，我能指出唯一那份文档吗？

如果答案是「大概三个地方都提到过」，需要收拾。收拾的时候，冲突通常来自三个地方：

**一、同一话题在多处写过。** 最常见。AGENTS.md 提了一句部署，`docs/deploy.md` 写了完整流程，某个 skill 里又写了一遍。三处都不算错，但迟早会有一处过期。

**二、AGENTS.md 和 skill 互相打架。** 这就是 03 里 overconstraining 的原型——系统指令说别写注释，skill 说要写文档，用户要第三种。模型要花算力仲裁。

**三、旧决策没删。** 三个月前决定用 A 方案，一个月前换成 B，AGENTS.md 里 A 那段还在。这种最难发现，因为它读起来完全合理。

一个可操作的做法：在 AGENTS.md 的索引区，直接写明每个话题的归属文件。

```markdown
## 去哪里找

| 话题 | 归属文件 |
|---|---|
| 部署 | `docs/deploy.md` |
| 技术选型和理由 | `docs/tech-stack.md` |
| 认证 | `docs/modules/auth.md` |
```

这张表有个副作用很有用：下次你想在别处写部署相关的东西，看一眼这张表就知道该写去哪。它把「唯一真源」从一个原则变成了一张能查的表。

### 流动的 context 交给看板

上面所有东西有个共同点：**它们是稳定的。** 项目用什么包管理器、部署怎么走、认证怎么设计——这些不会每天变。

但项目里还有另一类 context，每天都在变：现在在做什么、这个功能为什么要做、上次试过什么没成、这个 bug 的复现步骤。

这类东西塞进文档树会很难受。它们更新太频繁，而且做完就过期了。

它们属于看板。

**一个 issue 就是一次任务的 context 包。** 认真写 issue，等于提前把第四层的 prompt 写好了：

- 标题标清类型：New / Improve / Fix
- **why**：为什么要做
- **what**：具体要什么
- **how**：有想法给方向，没想法说没想法
- **how good**：什么样算做完了
- 其他相关 context

写好之后，日常使用变成一句话：「看一下 110 号 issue。」MCP 打通后，agent 直接去读，做完把进展同步回来，需要的时候自己拆 sub-issue。

这样十个项目、一百个项目的任务 context，都统一在一个地方，不用散在各个项目的文档里。

**工具选择：**

- **Notion**：免费，有看板，有 MCP。个人项目够用。
- **Linear**：付费档更完整，免费版也能用。OpenAI 团队做 Codex 和 ChatGPT 用的也是它。

Linear 属于 **opinionated software**——带强观点的软件。它对「应该怎么用」有自己的主张，因为它相信自己固化的是一套 agent 时代做产品的最佳实践。

这类软件有个额外价值：用它的过程本身是在学一套方法论。如果你想看最前沿的团队怎么组织 agent 驱动的开发，Linear 值得花时间。如果只想解决问题，Notion 够了。

一个人做项目也建议用看板。多人协作时它不可替代——你、你的 agent、协作者、协作者的 agent，共用同一套 context。

### 一个联动效果

第二层写好之后，会有个反直觉的结果：**你的 prompt 可以变短。**

02 说第四层要「把脑子里的东西尽可能倒出来」。但如果项目的稳定信息已经在 AGENTS.md 和文档树里，issue 里又有这次任务的 why / what / how good，那你每次要倒的东西就只剩这次任务特有的部分。

两层是联动的。第二层承担稳定的那部分，第四层就只需要处理增量。反过来，如果第二层是空的，你每次都要在 prompt 里把项目背景重讲一遍——重讲得不完整，输出就飘。

这也是为什么 02 里说第二层是「一次投入，长期复用」。

## 小结

1. AGENTS.md 是真源，CLAUDE.md 只写一句指过去，防止两份文档漂移。
2. AGENTS.md 的职责是索引，不是仓库。官方推荐的形状是「在正确时机被加载的文件树」。
3. 判断用二维表：推不出来 × 每次要用 → 留；推不出来 × 偶尔用 → 搬；模型自己会 → 删。多数臃肿出在把「该搬的」当成「该留的」。
4. 删和搬是两件事。删错一条真实的坑，代价是以后再踩一遍。
5. 文档树按「一次任务需要什么」拆，一个文件回答一类问题。
6. Single Source of Truth 落地成一张归属表，冲突常来自多处重写、层间打架、旧决策没删。
7. 稳定的 context 进文档树，流动的 context 进看板。一个 issue 就是一次任务的 context 包。
8. 第二层写好了，第四层可以变短——两层是联动的。
