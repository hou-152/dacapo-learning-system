# 02｜context 的四层：从系统指令到 prompt

## 这一篇要解决的问题

01 给出了 context 的定义：agent 输出第一个 token 之前接收的一切 input。但「一切 input」这个范围太大，大到没法直接动手。

这一篇把它切成四层，说清每一层由谁控制、多久变一次、你应该在哪一层花时间。

---

## 正文

### 先看整张分层表

| 层 | 内容 | 谁控制 | 变化频率 | 你的投入 |
|---|---|---|---|---|
| 第一层 | system instruction | AI 公司 | 随版本更新 | 几乎为零 |
| 第二层 | 项目文档（AGENTS.md、docs/） | 你 | 项目推进时 | 高 |
| 第三层 | skills、MCP、工具箱 | 你 | 长期积累 | 高，但见效慢 |
| 第四层 | prompt | 你 | 每一次对话 | 最高频 |

四层的顺序是从底到上：第一层最靠近模型，第四层最靠近你的手。有意思的是，投入产出比最高的两层，恰好是你完全控制的第二层和第四层。

---

### 第一层：system instruction

这是 AI 公司在模型最底层写下的指令，规定模型怎么用工具、什么该做、什么不该做，通常还带一堆示例。过去这些指令写得非常长。

一个值得注意的趋势：按 Anthropic 2026 年 7 月 24 日那篇文章的说法，针对 Claude Opus 5 和 Fable 5 这一代，Claude Code 的系统指令被删掉了 80% 以上，coding evals 上没有可测量的损失。（削减的具体机制见 03。）

削减的逻辑是这样的：模型智能越强，事先写死的约束反而越挤占它的判断空间。面对一个顶级模型，啰里啰嗦讲一大通规则，等于把一个高水平判断力换成一堆低水平规则。

这一层你改不了，但它给出的启示可以直接迁移到你自己写的东西上：

写 CLAUDE.md、AGENTS.md 和 skill 时，遵循同样的方向——给清目标、给清边界、给几个好例子就够了。三年前流行的那些技巧（重要的事情说三遍、全部大写强调、用职场话术施压）在今天的模型上基本失效。

**这一层的实际结论：不用管它，但要学它的减法。**

---

### 第二层：项目文档

这是投入产出比最高的一层。

一套已经比较标准的做法：

- 每个项目根目录放一份 `AGENTS.md`
- `CLAUDE.md` 里只写一句话：「请查看 AGENTS.md，以 AGENTS.md 为准」

这样 Codex 和 Claude Code 共用同一份项目说明，避免两份文档各写一套、慢慢漂移。

`AGENTS.md` 本身当成索引来写，只放最核心的部分。具体内容拆到 `docs/` 下面：

```text
project/
├── AGENTS.md          # 索引：项目是什么、去哪里找什么
├── CLAUDE.md          # 一句话：见 AGENTS.md
└── docs/
    ├── roadmap.md     # 路线图、MVP 阶段
    ├── tech-stack.md  # 技术栈
    └── modules/       # 每个模块单独一份
```

形成的是一棵文档树，agent 从根节点进入，按需展开。

这一层背后有个绕不开的概念：**Single Source of Truth**。

一个话题，只在一个地方定义。当同一个话题散落在三份文档、两个 skill、一段 prompt 里，这几处的说法迟早互相冲突。冲突的 context 会让 agent 输出不稳定的结果——同一个问题问两次，答案不一样。

有个自检问题很好用：

> 关于「这个项目怎么部署」，我能指出唯一那份文档吗？

如果答案是「大概在三个地方都提到过」，这就是需要收拾的地方。

---

### 第三层：skills 与 MCP

这一层是你的个人 App Store。

实践中的一个观察：自己结合真实需求写的 skill，价值最高；从网上批量下载的「经验总结」类 skill，收益很低，而且带着实际成本。

成本在哪里：一次性加载几十上百个 skill，会挤占 context window。它们没帮上忙，还占了位置，同时拉低运行质量。所以尝鲜可以，发现没用就关掉。

工具类 MCP 的价值更稳定，因为它带来的是原本拿不到的能力——连接数据源、调用 API、访问外部系统。这类东西是加法。

一个值得建立的习惯，是把自己维护的 skills 和 plugins 收到一个目录下：

```text
~/.agents/
├── skills/
└── plugins/
```

让 Claude Code 和 Codex 都指向这里，再同步到 GitHub 做版本控制。这样你换 harness 的时候，工具箱跟着你走——回到 01 的说法，马具可以换，你带在身上的东西不用重来。

这一层见效慢，因为 skill 是长出来的：某件事你做了三遍，流程稳定了，才值得固化成 skill。刚开始就想凑一个 skill 库，通常会凑出一堆用不上的东西。

---

### 第四层：prompt

这一层是最高频的，也是多数人投入最不足的。

核心动作只有一个：**把脑子里跟这件事相关的东西，尽可能倒出来。**

多数人给 agent 的 prompt 是一句需求。但你脑子里跟这个需求相关的东西远不止一句——为什么要做、做成什么样算好、之前试过什么、有哪些约束、你担心什么。这些全部属于 context，全部影响输出。

这里语音输入的效率优势很明显。Andrej Karpathy 分享过类似的做法：用十分钟语音，把脑子里跟一个主题相关的一切想法全部交给 AI。

关键点在于，倒出来的东西可以很粗糙：

- 表达可以乱
- 用词可以不准
- 观点可以还没打磨完
- 中间可以停顿、绕回来、自我否定

模型天生擅长从大量语言里提取语义。以量取胜，它能从里面挑出有价值的部分。反过来，你憋出一句精炼的需求，信息量反而更小。

倒的时候可以搭一个松散的框架：

- **why**：为什么要做这件事
- **what**：具体要什么
- **how**：有想法的话给方向，没想法就说没想法
- **how good**：什么样算做好了
- **还有什么**：脑子里其他相关的东西，想到就说

---

### 权重怎么分

四层放在一起看，投入优先级大致是这样：

1. **第四层（prompt）** — 每次都用得上，改善立刻见效
2. **第二层（项目文档）** — 一次投入，长期复用
3. **第三层（skills、MCP）** — 长期资产，慢慢长
4. **第一层（system instruction）** — 学它的减法思路，其他不用管

---

### 顺带说一件事：context window 是有限的

现在不少模型的 context window 到了 100 万 token，看起来很奢侈。但它可以类比成人的工作记忆：容量有限，而且越到后段，质量越差。这个现象有个名字叫 **context rot**。

现有的缓解手段：自动压缩、让 agent 自己写笔记、用 sub-agent 分担。但这些都是补救，不是许可。该关的 skill 关掉，该收的文档收拢，比事后压缩更管用。

---

## 小结

1. Context 分四层：system instruction、项目文档、skills / MCP、prompt。
2. 第一层由 AI 公司控制，趋势是不断精简——这个减法思路值得用在你自己写的文档和 skill 上。
3. 第二层投入产出比最高，核心是 AGENTS.md 作索引 + docs/ 展开 + Single Source of Truth。
4. 第三层是个人 App Store，自己写的 skill 价值最高，下载来的 skill 挤占 context window。
5. 第四层最高频，核心动作是把脑子里的东西尽可能倒出来，语音输入在这里效率明显。
6. Context window 大不等于可以浪费，context rot 意味着后段质量下降。
