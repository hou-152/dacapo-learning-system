## 正文

### 问题一：Notion 还是 Linear

对你的情况，答案是 **Notion**，而且这个答案不是「便宜所以选它」。

理由是你的 context 已经在 Notion 里了。日报数据库、阅读库、八个 skill 页面，全都是 Notion 页面。引入 Linear 意味着：

- 任务 context 在 Linear，知识 context 在 Notion
- agent 要同时挂两个 MCP
- 两边的信息迟早要手工对齐

这正好撞上 04 讲的那件事——两个真源等于没有真源。为了一个看板，把已经统一的 context 拆成两半，代价大于收益。

**Linear 值得换的信号**，是下面这些同时出现：

| 信号 | 说明 |
|---|---|
| 多人协作 | 你、协作者、双方的 agent 共用一套任务流 |
| 软件项目为主 | issue 要和 GitHub commit / PR 关联 |
| issue 有真实流转 | 状态、优先级、cycle 这些字段真的在用，不是摆设 |
| 项目数量多 | 十个以上项目的任务需要统一视图 |

你现在跑的主要是内容管线（日报、入库、概念提取），任务形态是「流程按天重复」，不是「issue 按需流转」。这种形态用数据库比用看板更顺手——你已经这么做了。

还有一件事值得说清楚。直播文稿里提到 Linear 是 opinionated software，用它的过程本身是在学一套方法论。这个价值是真的，但它属于**学习成本**，不属于**工具收益**。如果你的目的是学前沿团队怎么组织 agent 驱动的开发，开个免费版跑一个小项目就够，不用把主力工作搬过去。

### 问题二：开源方案照搬还是自测

先把结论摆出来：**结构照搬，内容自测。**

这两类东西的风险完全不同。

**结构层面**，指的是形状和机制：

- 双文件约定（AGENTS.md 真源 + CLAUDE.md 指过去）
- 文件树 + 索引，而不是单个大文件
- 三分法的两个判断维度（推不出来 × 每次要用）
- 渐进披露：把偶尔用的东西放到指针后面

这些可以直接照搬，因为它们**不对你的项目断言任何事实**。「把偶尔用的搬到指针后面」这句话在任何项目里都成立。照搬它，最坏情况是形状不合手，改回来成本很低。

**内容层面**，指的是具体那些规则行：

别人的 CLAUDE.md 是为**他们的**项目、**他们的**harness、**他们那一代**模型写的。搬过来会出三种问题：

1. **规则不适用**。他们的项目用 npm，你用 pnpm，这条规则搬过来是错的。
2. **规则变成冲突**。这是 03 讲的 overconstraining 原型——他那条「别写注释」和你某个 skill 里的「要写文档」打架，模型要花算力仲裁。
3. **规则针对的是旧模型**。这条最隐蔽。

第三条值得展开。03 里提到过一个细节：同一批人早先建议常驻 200–400 行，后来给这条建议加了个日期注解，而不是偷偷改掉。这个动作说明了什么——**当时的建议在当时是对的，权衡变了而已。**

所以你在 GitHub 上看到一份半年前的 agent 精简方案，你搬过来的不只是配置，是**一个在不同权衡下做出的决定**。那份方案可能是为了给老模型加护栏而写的，而这一代模型删掉护栏反而更好。

**自测方法（按成本从低到高）：**

| 方法 | 怎么做 | 成本 |
|---|---|---|
| 问 agent 读到了什么 | 让它复述当前生效的规则。复述不出来的行，说明没在起作用 | 一次对话 |
| 跑 `/doctor` | 官方给的工具，rightsize 你的 skills 和 CLAUDE.md | 一条命令 |
| 删一段跑一次 | 删掉某段，跑一个典型任务，看行为有没有变差 | 一次任务 |
| A/B 同一任务 | 带这段 / 不带这段各跑一次，对比输出 | 两次任务 |

第三条最好用，也最容易忽略——因为它要求你先承认「这段可能没用」。

**为什么值得测**，回到 03 那个成本模型：一条写歪的常驻规则，是未来几个月每次请求上的一笔小额税。测试是**一次性成本**，不测是**长期成本**。而且因为它一直在，你会慢慢注意不到它。

一个折中做法：结构直接照搬，内容分两批。明显通不过单行测试的（人设、通用常识、全大写强调）直接删，不用测。剩下拿不准的，用「删一段跑一次」逐段过。

### 进入 context window 管理

#### 为什么会 rot

先给现象一个名字。这个词从 needle-in-a-haystack 类基准测试里来：随着 context 里 token 数增加，模型准确召回信息的能力下降。

Chroma 在 2025 年测了 18 个前沿模型（包括 Claude Opus 4），结论是每一个模型都随输入长度增长而退化，而且退化方式「令人意外且不均匀」。

机制上，Anthropic 给了四层解释：

**一、注意力预算。** 类比人的工作记忆——模型解析大量 context 时动用的是一份有限的注意力预算，每个新 token 都消耗掉一部分。

**二、架构。** Transformer 允许每个 token 关注其他所有 token，n 个 token 产生 n² 个两两关系。长度增长时，捕捉这些关系的能力被「摊薄」（stretched thin）。这里有个内在张力：context 越大，注意力越难聚焦。

**三、训练分布。** 训练数据里短序列占多数，所以模型对「跨越整个 context 的依赖关系」经验更少，专门处理这件事的参数也更少。

**四、位置编码。** 把模型拉伸到更长序列用的是插值技术，代价是位置理解上的一些退化。

合起来的效果，官方的说法是 **a performance gradient rather than a hard cliff**——表现随长度渐降，没有一个突然失效的临界点。所以「还没到上限就没问题」这个直觉是错的：退化在填满之前就开始了。

其实有点像“脑腐”，你知道吗？人的注意力是有限的。

然后，在一篇论文中，他说每个 token 的注意力不一定是平均的

#### 位置也有影响

除了长度，信息**放在哪**也有影响。这就是 lost in the middle 现象：性能在相关信息位于开头或结尾时最高，位于中间时显著下降。这个模式和人类记忆的首位效应、近因效应相似。

实践含义很直接：**关键信息别埋在中间。** 一份长文档，最重要的约束放在开头或结尾；一次长会话，重要的决定值得在后面重新说一遍。

在 context window 里面有提到它是一个 U 型曲线，也就是说，你把信息放在开头和结尾性能最高，中间则显著下降。

况且，它对于零散的信息，你给它一个排版排好的和一个零散的，后者的效果甚至更好一点

#### 三种手段的适用边界

Anthropic 给了三种长程手段，各有各的场景。这张表是这一篇最实用的部分：

| 手段 | 做什么 | 适合什么 |
|---|---|---|
| **compaction**（压缩） | 接近上限时总结会话，用摘要开一个新窗口 | 需要大量来回的任务——它维持的是**对话连贯性** |
| **structured note-taking**（结构化笔记） | agent 把笔记写到窗口外（NOTES.md、to-do 列表），之后再读回来。能跨越 context 重置存活 | 有明确里程碑的迭代开发 |
| **sub-agent**（子 agent） | 专门的子 agent 在干净窗口里做聚焦任务，各自可能烧掉几万 token，只把约 1000–2000 token 的摘要交回。主 agent 持有高层计划并负责综合 | 复杂研究和分析——**并行探索有收益**的场合 |

选择的判据其实是一个问题：**你需要保住的是连贯性、里程碑，还是探索广度？**

- 连贯性 → compaction
- 里程碑 → 笔记
- 探索广度 → sub-agent

#### compaction 保留什么、丢什么

压缩不是无损的，所以保留什么是个设计问题。官方给的划分：

**保留**：架构决策、未解决的 bug、实现细节。Claude Code 的压缩还会带上最近访问过的五个文件。

**丢弃**：冗余的工具输出和消息。

**最便宜的安全操作**：清理旧的工具调用和结果。官方称之为「最安全、最轻的压缩形式」之一。理由很直白——一个工具在历史深处跑过了，那份原始结果没有进一步用途。

**风险**：过度压缩会丢掉一些微妙的 context，而它的重要性往往要到后来才显现。这和 04 里那条「删错一条真实的坑」是同一类错误，只是发生在压缩环节。

#### `/clear`、`/compact`、开新会话

这三个动作的分工：

| 情况 | 动作 | 理由 |
|---|---|---|
| 换任务领域 | `/clear` | 上一个领域的东西全都没用了，留着只消耗注意力预算 |
| 同一任务，一个阶段做完 | `/compact` | 保连贯性，摘要带着走 |
| 开始出现幻觉、反复答错 | 开新会话 | 压缩和清空都救不回来 |

第三条要标注一下：这是一条**实践启发式**，不是被 benchmark 验证过的阈值。有人给出「填充超过 50% 且开始出现幻觉」这样的具体判据，那是作者自己的决策规则。方向可信，数字别当标准。

（顺带说一句，我查到的那个 50% 阈值出自一篇厂商博客，页面里同时在推销自己的产品。这类来源的方向可以参考，具体数字要打折。）

#### 那条核心原则

Anthropic 那篇文章把原则说了两遍，几乎一字不差：

> find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome
> （找到能最大化目标达成概率的、最小的高信号 token 集合）

这句话里有两个词是重点。**smallest** 是约束，**high-signal** 是标准。只追求小，会删掉真正有用的东西；只追求信号强，会把所有相关的东西都塞进去。

还有一句配套的话，值得抄下来贴在显示器上：

> minimal does not necessarily mean short
> （最小化不等于变短）

这句和 03、04 完全咬合。03 的七类删法，本质是把内容搬到指针后面；04 的三分法，「搬」和「删」是两个不同的格子。三篇讲的是同一件事：**减少常驻的量，不减少可获取的量。**

## 小结

1. 你的情况选 Notion——context 已经在那里了，为一个看板拆成两个真源不值得。Linear 值得换的信号是多人协作 + 软件项目 + issue 真实流转。
2. 开源方案：结构照搬（它不对你的项目断言事实），内容自测（它是为别人的项目、harness、模型代次写的）。
3. 最容易忽略的自测方法是「删一段跑一次」，因为它要求先承认那段可能没用。
4. context rot 有四层机制：注意力预算、n² 关系被摊薄、训练分布偏短序列、位置编码插值退化。退化是渐降的斜坡，在填满之前就开始。
5. lost in the middle：关键信息放开头或结尾，别埋中间。
6. 三种手段对应三种需求——连贯性用 compaction，里程碑用笔记，探索广度用 sub-agent。
7. 压缩保留架构决策 / 未解 bug / 实现细节，丢弃冗余工具输出。清理旧工具结果是最便宜的安全操作。
8. 核心原则：最小的高信号 token 集合。而「最小化不等于变短」——减少常驻量，不减少可获取量。

Agent 确实是会存在的。我们要怎么样去通过上下文工程，将我们的 Agent 用得更好呢？

首先，我们要了解我们的上下文工程由什么组成。上下文工程主要由以下几个维度构成：

LLM（大模型）
我们人作为驾驶者，骑着马奔腾在一个辽阔的草原上。大模型从 GPT-4 时代走到 GPT-5 时代，你会很明显地发现它其实在慢慢变得越来越聪明。它的上下文窗口变得更高，智能程度变得越来越强。
取而代之的是，我们在系统文件里对它的强约束和提示词在减少。我们不用强制性地跟它写一大串提示词、教它用什么样的思维。你只要把你的想法用 5 到 10 分钟费曼出来，用 2W1H（What, Why, How）的框架，把需要补充的点补充出来。这其实是一个很好的去掌控这匹“猎马”、榨干 LLM 模型能力的方法。
Harness（治理/驾驭系统）
具体的代表为 Codex 和 Claude Code。Harness 就是我们的 Agent Cloud 平台，它里面有我们的 Agent、Tool、MCP、Skill 这些东西。
这些其实就是我们去驾驭 LLM 的触点和触手，能够让我们很好地去使用大模型的能力。对于我们来说，现在已经有 OpenAI、Stability AI 这些铺垫在前面，我们不用再对大模型做过多的魔改。
伴随而来的趋势是：随着模型变得越来越聪明，Harness 的系统文件在变少，包括我们的 Agent 数量也在变少。我们其实不用对它做很多的约束，不用对它裹小脚、裹小脑。
驾驶者（我们自己）
作为驾驶者，我们要去常常纠正这匹“猎马”，让它不至于乱跑。因为在实践的过程中，它经常会出现目标偏移、产生幻觉、越用越傻的情况。
这时候就需要我们去引导大模型，比如让它 compress（压缩）上下文，或者记笔记（note），把我们具体的目标和过程做成一个 handoff（交接档）保留下来，亦或者我们直接开启子 Agent。
草原（个人上下文）
什么是个人草原？就是你所拥有的个人上下文、你对业务的理解，以及你的各种灵感。
为什么很多人会出现“AI 越用越聪明”的感觉？其实就是因为通过这四个维度的协同，我们能够更好地通过上下文工程去驾驭大模型。
