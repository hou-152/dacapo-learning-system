## 正文

### 问题一：system instruction 和 AGENTS.md 差在哪

两者有一个共同点，这也是容易混起来的原因：**它们都是常驻 context**。每一次请求都带着它们跑，你不需要点什么，它们就已经在里面了。

差别在三个地方：

| | system instruction | AGENTS.md / CLAUDE.md |
|---|---|---|
| 谁写的 | AI 公司 | 你 |
| 影响范围 | 所有用户 | 你的这个项目 |
| 有没有被测过 | 有，改动要过 coding evals | 没有，你改完就上线了 |

第三行是关键。Anthropic 删那 80% 之前，有 coding evals 兜着——删错了，指标会掉，他们看得见。你的 CLAUDE.md 没有这层保护。写歪一行，它变成**每一次请求上的一笔小额税**，收好几个月。而且因为它一直在，你会慢慢注意不到它的存在。

内容上也有分工。system instruction 处理的是「这个模型该怎么当一个 coding agent」——通用行为、工具怎么用、安全边界。AGENTS.md 处理的是「这个项目有什么模型猜不到的事」。

按官方那篇的标准，能留在你自己文件里的东西，是一个强模型**推不出来**的部分：

- 操作者偏好（你要中文、你要先写测试）
- 项目里让人意外的事实（这个 API 的返回值有个坑）
- 带真实阈值的路由规则（超过 500 行就拆文件）
- 具体的集成和环境变量名

反过来，通不过这个标准的东西：把通用常识再说一遍、给模型编人设、全大写强调。这些模型本来就会，或者本来就不吃。

有个单行测试很好用，就是拿这句话逐行问自己的文档：

> 少了这一行，一个强模型会表现得更差吗？

### 问题二：80% 是怎么删掉的

先说诊断。Anthropic 给出的病因是一个词：**overconstraining（过度约束）**。

内部使用记录里出现过这种情况：一次请求里同时存在几条互相冲突的指令——系统指令说别写注释，某个 skill 说要写文档，用户又要第三种东西。

这里有个成本模型值得记住：**一条冗余指令的代价不是零。** 它是一个冲突，模型要花算力去仲裁。

具体删法有七类（按官方那篇的说法）：

1. **禁令换成判断标准**。原来有「不许写注释」「不许写规划文档」这类硬规则，存在的理由是老模型没有护栏时写的注释经常是错的。现在换成一句话：注释的密度和写法跟着周围代码走。
2. **删掉示例**。示例会把模型约束在一个特定的探索空间里。Anthropic 的技术人员 Thariq Shihipar 的说法是，这一代模型比给它的示例更有想象力。改成让接口设计自己承载语义——一个状态 enum 就能教会模型怎么用这个工具，不用配一段示例对话。
3. **全部前置加载换成渐进披露**（progressive disclosure）。
4. **删掉跨层重复**，以及本该写在工具描述里的工具指导。
5. **手工维护的 CLAUDE.md 记忆换成自动记忆**。
6. **散文式的规格说明换成高保真参照物**——一个测试套件、一个可移植的函数、一份 HTML mockup。
7. **删掉显式的验证指令**。原文提到，这类指令会让 Opus 5 过度验证。同样删掉的还有「记得开 subagent」「记得自我纠正」这类提醒，因为这一代模型本来就会做。

然后是更重要的一半：**保留了什么。**

那些本质上是「信息」而非「指令」的内容没有被删，它们**移到了指针后面**：

- 验证和 code review 被搬进各自的 skill，由 Claude Code 按需调用
- 完整的工具定义改成延迟加载，通过 ToolSearch 取
- 确定性的闸门（build、tests、typecheck）留下了——它们是检查，不是「你要小心一点」这种劝告

所以整件事的机制概括成一句话：**把模型能自己推出来的删掉，把是信息的那部分移到指针后面。** 减法只是结果，前提是有地方接。

关于 token 数字：有媒体报道说是从约 800 token 降到 164。这个数字我标为**未核实**——更严谨的那份总结明确说 Anthropic 只给了百分比，没有给基线 token 数。

### 那条推理链对不对

你提到的那条：*「Claude 5 代的系统指令减少了，所以我们把 AGENTS.md 也减少。」*

结论对，理由不完整。

**结论对**的部分：官方那篇确实直接建议你收缩自己的 context 文件，还给了工具——跑 `/doctor` 来 rightsize 你的 skills 和 CLAUDE.md。建议从 agent 定义文件开始下手，那里的水分最多。有个第三方框架给了自己的行数对比：CLAUDE.md 从 260 行到 165 行，18 个 agent 定义从 8798 行到 664 行。（这组数字是那位作者自己的框架，不是 Anthropic 的。）

**理由不完整**的部分：如果只学到「变短就是好」，会删错东西。真正的判据是那条单行测试，以及删掉的东西有没有地方接。官方那边删掉的验证指令，是搬进 skill 了，不是凭空消失。

还有一条警告值得抄下来：**行数本身不是目标。** 写那份第三方总结的作者删过一条看起来像样板文字的 build 注意事项，后来某次会话又痛苦地重新发现了这个坑，只好把它加回去。

以及：以前的做法当时并没有错，只是权衡变了。同一批人早先建议常驻 200–400 行，现在给这条建议加了个日期注解，而不是偷偷改掉。这个态度比结论本身更值得学。

## 进入 A：harness 的结构与差异

### 一个数量级的观察

先摆一个现象。ARC-AGI-3 上有个例子：同一个模型，只调几个 harness 设置，结果差约三倍。（这条来自直播文稿的转述，我**未核实**原始出处，但方向和后面的实测经验一致。）

它说明的事情很简单：agent 系统的表现不只由模型决定。

### harness 由什么组成

01 给过定义：不是模型的部分，都是 harness。展开来看，这些部件在 Agent SDK 里叫 **primitives（原语）**——最小的能力砖块：

| 原语 | 干什么的 |
|---|---|
| agent loop | 那个「思考 → 调工具 → 看结果 → 再思考」的循环本身 |
| runner | 谁来推动这个循环、循环什么时候停 |
| handoff | 一个 agent 把活交给另一个 agent |
| session | 一次会话的边界，什么东西在这次会话里活着 |
| memory | 跨会话留下来的东西 |
| sandbox | agent 能碰到的执行环境边界 |
| shell | 它怎么执行命令 |

日常用 Claude Code 或 Codex 时，你不会逐个操作它们——Anthropic 用 Claude Agent SDK 做出了 Claude Code，OpenAI 用 OpenAI Agents SDK 做出了 Codex，这些部件已经被打包好了。

这也是为什么 02 里说，harness 这一层你花的时间应该少。它是基础设施。

### 为什么换个 harness 差别这么大

实测下来，差异集中在三个变量上：

**变量一：它能访问什么。**
本地桌面 agent（Claude Code、Codex）能访问你电脑上的文件和软件，能 24×7 跑。云端 agent（Claude Cowork、ChatGPT 云端模式、早期的 Manus）用的是 AI 公司的云端电脑——那台机器上装的软件跟你的不一样，你的数据库、你的笔记、你多年积累的素材都不在上面。

回到 01 的比喻：云端 harness 给你一副不错的马具，但把你从自己的草原上搬走了。

**变量二：它受什么约束。**
在 Claude Code 或 Codex 里访问 Notion API、Readwise API，都要考虑 rate limit，不能访问太多，编排设计得带着镣铐跳舞。Notion Custom Agents 访问 Notion 内部数据时不受同样的限速约束——这是它在特定场景下的优势。

选 harness 的时候，「我的数据在哪」经常比「哪个模型更强」更能决定结果。

**变量三：装了什么。**
一台专门给 agent 用的机器，装满工具、接好数据库和大量 context，跟一台干净的云端容器，跑同一个模型也不是一回事。

### 二阶 harness

最后回到 01 提过的那个说法。

你不会去做一个 Codex，也不会去做一个 Claude Code。但当你把几个 skill 组装成一个 agent——比如一个内参编辑 agent、一个阅读处理 agent——按照「不是模型的就是 harness」这个定义，**你做的这个东西本身也是 harness**。

你是在 AI 公司提供的 harness 之上，又叠了一层自己的。这层是你的，换 harness 的时候它跟着你走。

这也解释了 02 第三层为什么值得投入：`~/.agents/` 里那些东西，本质上是你的二阶 harness。

## 小结

1. system instruction 和 AGENTS.md 都是常驻 context，差别在谁写、影响谁、有没有被测过；你的文件没有 evals 兜着，写歪一行是长期收税。
2. 能留在自己文件里的，是强模型推不出来的东西：偏好、意外事实、带阈值的规则、具体的名字。
3. 80% 的删法核心是两步：删掉模型能自己推出来的，把属于信息的部分移到指针（skill、工具描述、延迟加载）后面。
4. 「变短就是好」是误读。判据是那条单行测试，以及删掉的东西有没有地方接。行数不是目标。
5. harness 由 agent loop、runner、session、memory、sandbox 等原语组成，这些 SDK 已经打包好，你花的时间应该少。
6. 换 harness 效果差异大，集中在三个变量：能访问什么、受什么约束、装了什么。「我的数据在哪」经常比「哪个模型更强」更决定结果。
7. 你自己组装的 agent 就是二阶 harness，它跟着你走。
