# Skills 机制研究报告

> 针对 concept-learning、dbs-learning、dbs-theory-grounding 三个 Skills 的核心机制分析

---

## 一、concept-learning：概念提取机制

### 输入→处理→输出流程

**输入**：长文章、课程稿、研报、演讲或转写材料

**处理流程**：
1. **建立论证骨架**：先判断作者试图回答的问题和整体论证结构，避免只凭词频抓名词
2. **承重判断**：识别被作者定义、反复使用、重新解释或用于区分的词语、比喻、机制和框架
3. **淘汰测试**：对每个候选概念问两道题
   - 主旨题：拿掉它，读者是否还看得懂作者的关键论点？
   - 边界题：拿掉它，读者是否还能理解机制的完整边界？
   - 两道题都答"看得懂/能理解"才砍掉
4. **保留原文语境**（context）：呈现概念在原文中的实际语境，优先保留最能体现其含义的原句
5. **费曼解释**：用普通语言解释概念在本文里的实质含义、解决的理解难点、为什么是承重部分
6. **构建架构图**：用 Mermaid 重建概念关系，必须分层（按功能角色归层），只画能由原文支持的关系

**输出**：概念解析辞典（概念名 + context + 费曼一下 + 概念架构图）

### 核心设计原则

1. **承重优先，不是术语清单**：只选择理解全文不可缺少的概念基石，不是所有专业术语
2. **双重测试机制**：主旨题+边界题，确保筛选标准清晰、可执行
3. **原文锚定**：context 必须保留作者原话，避免解释脱离语境
4. **费曼式转译**：用普通语言解释，目标是读者能复述
5. **关系可验证**：架构图只画原文支持的关系，不制造边缘；原文没形成可靠结构时输出空图

### 可复用设计模式

**双测试筛选器（Two-Test Filter）**：
- 设计两个互补的测试维度（主旨+边界）
- 只有通过所有测试才淘汰，确保不遗漏边缘案例
- 适用于需要高召回率的提取任务

**原文锚定+二次解释（Anchor + Interpret）**：
- 先保留原文语境（context），再用目标语言解释（费曼一下）
- 避免解释脱离原意，同时降低理解门槛
- 适用于需要同时保证准确性和可理解性的知识转换

## 二、dbs-learning：交互式学习机制

### 输入→处理→输出流程

**输入**：用户想系统学习的课题

**处理流程**：

**Phase 1：确认课题**
- 确认课题名和存放目录（项目目录 vs 泛目录）

**Phase 1.5：确认知识基础**（仅新课题）
- 如果当前目录是项目目录，轻量检索项目中与课题直接相关的内容
- 区分材料类型：用户观点 vs AI 草稿 vs 第三方材料
- 提供三个选项：基于项目 / 从零开始 / 指定材料
- 用户确认后记录到 `00-学习计划.md`

**Phase 2：读取已有进度**
- 读取 `00-学习计划.md`
- 找到序号最大的文章
- 阅读末尾的「学习反馈」，只提取用户实际填写的内容（过滤模板提示）
- 用 3-5 条总结用户当前理解状态

**Phase 3：判断学习梯度**
- 根据反馈信号选择推进方式：

| 用户反馈信号 | 下一篇处理方式 |
|---|---|
| 没看懂、概念混乱 | 降低抽象度，补例子，放慢节奏 |
| 看懂了但觉得没意思 | 换切入角度，连接用户真实问题 |
| 看懂了并提出应用问题 | 增加案例、判断方法和使用场景 |
| 明显掌握了 | 提高概念密度，进入下一层 |

**Phase 4：生成下一篇文章**
- 固定结构：这一篇要解决的问题 → 正文 → 小结 → 下一篇预告 → 学习反馈

**Phase 5：更新学习计划和索引**
- 更新当前进度、用户反馈摘要、下一篇方向

**输出**：`00-学习计划.md` + `01.md`/`02.md`/`03.md`...（连续学习文章）

### 核心设计原则

1. **自适应学习梯度**：每一篇文章都要接住用户上一轮的理解状态和兴趣方向
2. **反馈驱动调整**：从用户实际反馈中提取信号，动态调整深度、角度、节奏
3. **知识基础显式化**：不假设用户的知识基础，用项目材料或用户确认建立起点
4. **文件组织规范**：固定目录结构、两位数字序号、不跳号
5. **模板过滤机制**：区分模板提示和用户真实反馈

### 可复用设计模式

**反馈信号映射表（Feedback Signal Mapping）**：
- 预定义用户反馈信号与处理策略的映射关系
- 降低判断成本，提高响应一致性
- 适用于需要根据用户反应动态调整的交互式系统

**知识基础显式确认（Explicit Knowledge Foundation）**：
- 轻量检索 → 区分材料类型 → 提供选项 → 用户确认 → 记录到计划
- 避免假设用户已有知识，减少起点错配
- 适用于个性化学习、知识管理系统

**连续编号+状态文件（Sequential Numbering + State File）**：
- 用两位数字序号组织连续内容（01.md, 02.md...）
- 用 `00-学习计划.md` 记录元信息和进度
- 便于追踪、恢复、索引
- 适用于需要管理长期连续任务的系统

## 三、dbs-theory-grounding：理论溯源机制

### 输入→处理→输出流程

**输入**：未经检验的经验判断、案例、使用场景

**处理流程**：

**Step 1：固定原问题**
- 提取原命题、原案例、使用场景、用户希望理论完成的任务

**Step 2：审查原命题**
- 逐项检查风险：绝对化、因果跳跃、定义偷换、经验普遍化、反向推断
- 作出状态判断：保留 / 收窄 / 重构 / 放弃

**Step 3：定义理论需要解释的机制**
- 把「找名人」改写为 1-3 个理论检索问题（为什么...？什么机制...？）

**Step 4：建立候选池**
- 提出 2-4 个候选理论
- 按 5 个维度评分：机制匹配（0-3）、来源可靠（0-2）、人物辨识度（0-2）、可用于表达（0-2）、边界清楚（0-1）
- 总分低于 7 分不得入选；机制匹配 < 2 或来源可靠 < 1 直接淘汰
- 去重：两个理论解释同一机制时只保留机制匹配分更高的

**Step 5：确定人物、理论与核实层级**
- 默认先用已有知识，只有外部事实会实质改变结论时才联网核实
- 人物定位：[国家或学术归属][相关身份][中文名]（[外文通行名]）
- 理论卡：理论名称、要解决的问题、核心机制、原始出处、核实状态

**Step 6：用理论重释案例**
- 逐句映射：案例原句 → 理论对应概念 → 理论解释 → 修正后的判断

**Step 7：写适用边界与反例**
- 适用场景、不适用场景、反例（什么情况会推翻当前解释）

**Step 8：生成标准输出**
- 根据读者类型调整（研究者 vs 课程老师/客户）
- 给当事人的版本：总体判断 → 理论选择说明 → 理论锚点 → PPT 可用版

**输出**：理论锚点文档（包含总体判断、理论卡、案例解释、适用边界、PPT 可用版）

### 核心设计原则

1. **先审命题，再选理论**：不是找名人配案例，而是用理论解释机制
2. **匹配度优先于名气**：理论必须解释案例核心机制，名气不能弥补理论错配
3. **默认离线，按需联网**：先用已有知识，只有外部事实会实质改变结论时才联网
4. **控制理论数量**：同一组案例默认只保留 1 个主理论，辅助理论必须解释新机制
5. **逐句映射，不贴标签**：理论解释必须对应到案例的具体句子或事实
6. **显式边界与反例**：任何理论都不能推出无限结论，必须写出不适用场景

### 可复用设计模式

**多维评分筛选器（Multi-Dimensional Scoring Filter）**：
- 设定多个评分维度和权重
- 设定硬门槛（某些维度必须达标）和总分门槛
- 适用于需要综合评估多个因素的选择任务

**命题审查→理论匹配→案例重释（Claim Audit → Theory Match → Case Reinterpretation）**：
- 三阶段流程：先审查原命题是否成立 → 再匹配理论 → 最后用理论重释案例
- 避免直接套用理论，确保理论与案例真正匹配
- 适用于需要为经验判断寻找理论依据的场景

**核实层级显式化（Explicit Verification Levels）**：
- 明确标注知识来源：用户材料 / 本地资料 / 基于已有知识 / 原始来源已核实 / 尚未核实
- 不因联网成本而降低透明度，不把推测包装成事实
- 适用于需要可信度分级的知识管理系统

**逐句映射表（Sentence-Level Mapping）**：
- 用表格形式逐句对应：原句 → 理论概念 → 解释 → 修正判断
- 避免只在案例前贴理论标签，确保理论真正解释了案例
- 适用于需要精细验证对应关系的分析任务

## 四、三者之间的协作点

### 1. 信息流向的协作

```
concept-learning         dbs-learning           dbs-theory-grounding
     ↓                        ↓                         ↓
  提取概念基石    →    组织成学习文章    →    为经验判断补理论依据
（原文 → 概念）    （概念 → 教学序列）    （判断 → 理论 → 案例）
```

**协作场景 A：从原始材料到学习课程**
- 用 `concept-learning` 从长文章中提取核心概念
- 用 `dbs-learning` 把这些概念组织成连续学习文章
- 用 `dbs-theory-grounding` 为其中的经验判断补充理论依据

**协作场景 B：从用户反馈到知识沉淀**
- 用 `dbs-learning` 收集用户学习反馈
- 用 `concept-learning` 从反馈中提取用户真正理解的概念
- 用 `dbs-theory-grounding` 为用户提出的应用问题寻找理论支撑

### 2. 共享的设计模式

**模式 1：双重验证机制**
- `concept-learning`：主旨题 + 边界题
- `dbs-theory-grounding`：机制匹配硬门槛 + 总分门槛
- 共同特征：设置两道关卡，避免单一标准遗漏边缘案例

**模式 2：原文锚定**
- `concept-learning`：保留 context（原文语境）
- `dbs-theory-grounding`：逐句映射（案例原句 → 理论解释）
- 共同特征：解释必须对应到原文具体位置，不允许脱离语境的抽象总结

**模式 3：显式状态管理**
- `dbs-learning`：用 `00-学习计划.md` 记录知识基础、当前进度、反馈摘要
- `dbs-theory-grounding`：显式标注核实状态（用户材料 / 本地资料 / 已有知识 / 已核实 / 尚未核实）
- 共同特征：把隐含的假设和状态显式化，便于追踪和验证

**模式 4：禁止过度概括**
- `concept-learning`：只选理解全文不可缺少的概念基石，不是术语清单
- `dbs-theory-grounding`：拒绝推出「文案永远应该更具体」一类无限结论，必须写出不适用场景
- 共同特征：防止从有限样本推出无限结论，强制标注边界

### 3. 协作的技术债

**问题 1：概念粒度不一致**
- `concept-learning` 提取的概念可能过于抽象，不适合直接进入 `dbs-learning` 的教学序列
- 需要中间层：「概念 → 可教学的知识单元」的转换机制

**问题 2：反馈循环未闭环**
- `dbs-learning` 收集了用户反馈，但没有机制把反馈中的误解或新理解反哺到概念库或理论库
- 建议：增加「反馈 → 概念修正」或「反馈 → 理论补充」的回路

**问题 3：理论锚定的触发时机不明确**
- `dbs-learning` 生成的文章中可能包含经验判断，但没有自动触发 `dbs-theory-grounding` 的机制
- 建议：在 `dbs-learning` 的 Phase 4 增加「经验判断检测 → 建议调用 theory-grounding」的分支

### 4. 可能的协作优化

**优化 1：建立概念→教学单元的映射库**
- 记录哪些概念适合什么样的教学梯度
- 记录用户对不同概念的典型反馈模式
- 供 `dbs-learning` 在 Phase 3 判断学习梯度时参考

**优化 2：建立理论→概念的反向索引**
- 当 `dbs-theory-grounding` 为某个判断找到理论依据后，把理论名称和核心机制反向索引到相关概念
- 供 `concept-learning` 在构建概念架构图时参考

**优化 3：用户反馈驱动的概念与理论迭代**
- `dbs-learning` 收集到「用户没看懂」的反馈后，触发 `concept-learning` 重新提取该部分的概念
- 如果概念已经足够清楚，但用户仍然没看懂，触发 `dbs-theory-grounding` 为概念补充理论支撑

## 五、可复用设计模式总结

### 提取与筛选类模式

1. **双测试筛选器（Two-Test Filter）**：设置两个互补的测试维度，只有通过所有测试才淘汰
2. **多维评分筛选器（Multi-Dimensional Scoring Filter）**：多维度评分 + 硬门槛 + 总分门槛
3. **淘汰测试（Elimination Test）**：问"拿掉它会怎样"，而不是"加上它有什么用"

### 验证与锚定类模式

4. **原文锚定+二次解释（Anchor + Interpret）**：先保留原文语境，再用目标语言解释
5. **逐句映射表（Sentence-Level Mapping）**：用表格形式逐句对应原句、概念、解释
6. **核实层级显式化（Explicit Verification Levels）**：明确标注知识来源和核实状态

### 反馈与调整类模式

7. **反馈信号映射表（Feedback Signal Mapping）**：预定义用户反馈信号与处理策略的映射关系
8. **知识基础显式确认（Explicit Knowledge Foundation）**：轻量检索 → 区分材料类型 → 用户确认 → 记录
9. **自适应梯度（Adaptive Gradient）**：根据用户反馈动态调整深度、角度、节奏

### 组织与管理类模式

10. **连续编号+状态文件（Sequential Numbering + State File）**：两位数字序号 + 元信息文件（00-）
11. **三阶段流程（Three-Stage Process）**：审查 → 匹配 → 重释（先判断再行动，不直接套用）
12. **边界强制标注（Mandatory Boundary Annotation）**：适用场景 + 不适用场景 + 反例

## 六、核心洞察

### 1. 从"提取"到"解释"到"组织"的递进

三个 Skills 形成了一个完整的知识处理链条：
- **concept-learning**：从原文提取概念（what）
- **dbs-theory-grounding**：为判断补充理论解释（why）
- **dbs-learning**：把知识组织成可教学的序列（how to learn）

### 2. 显式化是核心设计原则

三个 Skills 都在对抗隐含假设：
- `concept-learning`：不假设读者已经理解术语，要求保留原文语境
- `dbs-learning`：不假设用户的知识基础，要求显式确认并记录
- `dbs-theory-grounding`：不假设理论与案例的匹配关系，要求逐句映射

### 3. 双重验证机制的普遍价值

所有涉及筛选的环节都采用了双重验证：
- 不依赖单一标准（容易遗漏边缘案例）
- 不依赖主观判断（难以复现）
- 用两个互补的测试构成筛选器

### 4. 反馈驱动优于预设路径

`dbs-learning` 的核心不是预设一个完整的课程大纲，而是根据用户每一步的反馈动态调整。这种设计比静态规划更适合个性化学习场景。

### 5. 边界意识是质量保证

三个 Skills 都强制要求标注边界：
- `concept-learning`：边界题（拿掉它，读者是否还能理解机制边界）
- `dbs-learning`：不适用场景（什么时候学习梯度判断会失效）
- `dbs-theory-grounding`：不适用场景 + 反例（什么情况会推翻当前解释）

这是对过度概括的系统性防御。
